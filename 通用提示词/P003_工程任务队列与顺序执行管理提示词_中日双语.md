# P003｜Claude Code 工程任务队列管理提示词（中文・日本語）

**用途**：在特定工程中设计多任务顺序执行、验证、记录及恢复机制。  
**使用方法**：在目标工程目录启动 Claude Code，选择以下中文版或日文版发送一次。两种语言为同一要求，**不要重复执行**。  
**当前阶段**：只调查并提出方案；未经确认不得创建文件、修改业务代码或开始执行任务。

---

## 中文版｜发送给 Claude Code

请为**当前打开的工程**设计统一的任务队列管理机制，使我能够一次登记多个任务，并在我授权启动后，按优先级和依赖关系顺序执行、验证、记录进度及恢复工作。

### 1. 先调查现状
- 确认当前工程根目录、已有的 `CLAUDE.md`、任务清单、进度记录、交接文档及相关执行规则。
- 核实 CORE-001 是否**实际可读取且已纳入当前执行规则**；不得因为 GitHub 上存在该文档就假定已加载。
- 优先沿用已有的有效机制，不创建重复文件或第二份总则。
- 区分工程级规则与用户级通用规则；任务清单原则上归属于当前工程。

### 2. 设计任务队列
若工程内没有合适的统一清单，可建议使用 `TASKS.md`，但先不要创建。每项任务至少包括：
- 任务编号、名称、目标、优先级；
- 依赖任务及执行前提；
- 输入资料与版本基准；
- 预期成果、保存位置和验收标准；
- 状态、执行记录、验证结果与可定位证据；
- 阻塞原因、待确认事项和下一步。

建议状态：`待执行`、`执行中`、`阻塞`、`待验证`、`已验证完成`。不得仅凭生成文件或自我声明将任务标记为完成。

### 3. 设计顺序执行规则
- 按依赖关系和优先级选择下一个**可执行**任务；依赖未完成时不得抢先执行。
- 一次只执行一个任务，按 CORE-001 的 PDCA 要求开展计划、执行、检查和改进。
- 必要验证通过后，记录成果与证据、更新状态及交接信息，再进入下一项。
- 若缺少资料、权限不足、验证失败或需要人工决策，记录阻塞及原因，不得擅自越权。
- 默认遇到阻塞即暂停并报告；只有得到明确授权，才能跳过阻塞项执行其他独立任务。
- 用户可要求暂停、调整优先级、取消或恢复任务；必须保存已完成部分和当前状态。

### 4. 设计持久化与恢复
- 使用工程已有的记录位置；如需新增文件，说明每个文件的职责、路径、格式和必要性。
- 每次实质进展后及时保存任务状态、关键决定、成果位置、验证记录、待确认项和下一步。
- 新会话恢复时先读取记录，再核实实际文件与状态，不能把历史报告直接当作当前完成事实。
- 说明 Claude Code 的实际限制：会话中断、上下文耗尽、权限确认或工具故障可能导致暂停；不得承诺无人值守无限运行。

### 5. 本轮只提交设计方案
请先输出：
1. 当前工程中已发现的任务及记录机制（注明实际核查范围）；
2. 建议采用的文件结构，以及与 CORE-001、工程 `CLAUDE.md` 的关系；
3. 任务条目示例、状态流转及执行顺序；
4. 自动继续、暂停、阻塞、恢复的具体规则；
5. 拟创建或修改的文件清单及其理由；
6. 需要我确认的最少关键问题。

**本轮禁止**：创建、覆盖、删除文件；修改业务代码；实际启动任务队列。先等待我确认设计方案和授权范围。

## 日本語版｜Claude Code に送信するプロンプト

**現在開いているプロジェクト**を対象に、統一的なタスクキュー管理の仕組みを設計してください。複数のタスクを一括登録し、私が実行を承認した後、優先順位と依存関係に従って順次実行・検証し、進捗を記録して再開できるようにすることが目的です。

### 1. 現状を先に調査する
- 現在のプロジェクトルート、既存の `CLAUDE.md`、タスク一覧、進捗記録、引継ぎ資料、関連する実行ルールを確認する。
- CORE-001 が**実際に参照可能で、現在の実行ルールに組み込まれているか**を確認する。GitHub に存在するだけで読み込み済みと判断しない。
- 既存の有効な仕組みを優先して利用し、重複ファイルや第二の共通総則を作らない。
- プロジェクト固有のルールとユーザー共通ルールを区別する。タスク一覧は原則として当該プロジェクトで管理する。

### 2. タスクキューを設計する
適切な統一リストが存在しない場合は `TASKS.md` を提案してよいが、この段階では作成しない。各タスクには少なくとも以下を含める。
- タスク ID、名称、目的、優先順位
- 依存タスクと着手条件
- 入力資料とバージョン基準
- 期待成果、保存先、受入基準
- 状態、実行記録、検証結果、特定可能な根拠
- ブロック理由、要確認事項、次の作業

推奨ステータス：`未着手`、`実行中`、`ブロック中`、`検証待ち`、`検証済み完了`。ファイル生成や自己申告だけで完了扱いにしない。

### 3. 順次実行ルールを設計する
- 依存関係と優先順位に従って、次に**着手可能な**タスクを選ぶ。依存タスクが未完了なら先行実行しない。
- 一度に実行するタスクは一つとし、CORE-001 の PDCA に従って計画・実行・検証・改善を行う。
- 必要な検証が通った後、成果と根拠を記録し、状態と引継ぎ情報を更新してから次へ進む。
- 資料不足、権限不足、検証失敗、人的判断が必要な場合はブロック理由を記録し、無断で権限を越えない。
- ブロック時は原則として停止・報告する。別の独立タスクへ進むのは、明示的な許可がある場合に限る。
- ユーザーは一時停止、優先順位変更、取消し、再開を指示できる。既存の成果と状態を保持する。

### 4. 永続化と再開を設計する
- 既存の記録先を利用する。新規ファイルが必要なら、それぞれの役割、パス、形式、必要性を説明する。
- 実質的な進捗ごとに、タスク状態、重要な判断、成果の場所、検証記録、要確認事項、次の作業を保存する。
- 新しいセッションでは記録を読み、実ファイルと状態を再確認する。過去の報告を現在の完了事実とみなさない。
- Claude Code の制限を明記する。セッション中断、コンテキスト上限、権限確認、ツール障害などで停止する場合があり、無人で無期限に動作すると約束しない。

### 5. 今回は設計案のみ提出する
以下を提示すること。
1. 現在のプロジェクトで確認できたタスク管理・記録の仕組み（調査範囲を明記）
2. 推奨ファイル構成と CORE-001、プロジェクトの `CLAUDE.md` との関係
3. タスク記載例、ステータス遷移、実行順序
4. 自動継続、一時停止、ブロック、再開の具体的なルール
5. 作成・変更予定のファイル一覧とその理由
6. 私の確認が必要な最小限の重要事項

**今回の禁止事項**：ファイルの作成・上書き・削除、業務コードの変更、タスクキューの実行開始。設計案と権限範囲について、私の確認を待つこと。
