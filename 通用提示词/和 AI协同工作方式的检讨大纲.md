# 和 AI协同工作方式的检讨大纲

- 版本：讨论稿 v0.2
- 日期：2026-11-21
- 状态：讨论大纲（尚未定稿，未自动部署为 Claude/Harness 执行规则）
- 主题：遇到复杂问题时，人和 AI 如何有效合作，把目标转化为可靠成果。

## 一、核心思想

人与 AI 共同解决复杂问题的关键，不只是提出好问题，而是：

> 在正确目标的引导下，把复杂问题逐渐拆解成清楚、可执行、可验证的小问题，持续消除未知，最终实现目标。

三个关键词：

1. **想清楚**：到底要解决什么问题？最终想得到什么？
2. **做明白**：依据什么资料，按照什么逻辑，一步步解决？
3. **验清楚**：如何证明方案正确、完整、没有遗漏？

## 二、协同解决复杂问题的五阶段流程

| 阶段 | 目的 | 人与 AI 要做的事 | 阶段成果／检查点 |
| --- | --- | --- | --- |
| ① 明确目标 | 定义真正要解决的问题与成功标准 | 确认问题、范围、约束、优先级和完成条件 | 目标说明、完成标准 |
| ② 拆解问题 | 降低复杂度，找出依赖关系 | 将任务拆成若干可处理、可验证的小问题，排好先后顺序 | 问题树、执行路线图 |
| ③ 调查与推理 | 用事实替代猜测 | 收集原始资料及证据，区分已知／未知／推断，提出并比较方案 | 调查结论、可选方案、风险 |
| ④ 执行与验证 | 形成可以核验的实际结果 | 逐项实施，对照完成标准检查，发现问题及时修正并再验证 | 实际成果、检查与修正记录 |
| ⑤ 成果与经验 | 实现目标，并可追溯、可复用 | 交付最终成果，保留依据、决策、遗留问题和经验 | 成果清单、证据索引、经验总结 |

**闭环要求**：验证不通过时，返回对应的调查、拆解或执行步骤修正，而不是只说「已完成」。

~~~mermaid

    A["① 明确目标\n问题・范围・约束・完成标准"] --> B["② 拆解问题\n小问题・依赖关系・优先级"]
    B --> C["③ 调查与推理\n事实・证据・未知・解决方案"]
    C --> D["④ 执行与验证\n实施・检查・修正"]
    D --> E{"是否达到完成标准？"}
    E -- "否" --> F["定位原因与问题所属步骤"]
    F --> B
    E -- "是" --> G["⑤ 形成成果与经验\n交付・留档・复用"]
~~~

注：这是通用协作方式的概念流程图，不代表某个 Agent 工程已经按该流程实现。

## 三、人与 AI 如何分工

| 人负责 | AI 负责 |
| --- | --- |
| 决定最终目标及价值判断 | 帮助澄清目标、发现问题定义中的模糊之处 |
| 判断优先级、约束与可接受的取舍 | 拆解问题、分析依赖关系、整理路线图 |
| 授权关键操作与高风险变更 | 在授权范围内调查资料、列出证据、比较方案 |
| 对关键方案作决定 | 执行可授权的任务，并报告实际过程与结果 |
| 判断成果是否真正满足需求 | 自检、测试、解释差异、按反馈修正 |

原则：**人掌握方向与最终判断；AI 负责大量调查、逻辑分析、执行和检查；双方通过持续反馈校正结果。**

## 四、第一步重点检讨：如何把目标定义清楚

复杂任务的常见失败原因之一，是开始执行前没有定义「什么叫成功」。

- 模糊目标：「帮我完善项目追加 Agent。」
- 更清晰的目标：「以对应一览为根本依据，确保改修要求不遗漏，生成正确的基本设计、详细设计及程序；每条要求均能追溯处理方法和验证结果。」

在开始拆解之前，先共同确认：

1. **Why**：为什么做，最终要解决什么问题？
2. **What**：要交付什么具体成果？
3. **Scope**：哪些属于本次范围，哪些不属于？
4. **Constraint**：资料、权限、时间、工程规则等限制是什么？
5. **Done**：用哪些可检查的条件判定完成？

## 五、协同交流的基本节奏

1. 首先由 AI 用两三句话复述目标、关键约束和预期成果，让人快速判断方向是否正确。
2. AI 给出**整体路线图**，指出当前最重要的问题和步骤。
3. 讨论阶段**一次只聚焦一个关键问题**：讲清目的、依据、具体 How、结果与未确认点。
4. 人确认后继续讨论下一项；不要求人在每个已授权的机械执行步骤中反复确认。
5. 已授权的完整执行任务由 AI 持续推进并自检；关键判断、风险变更和缺少必要依据时再征求人的决定。
6. 结果必须有可复核证据；不能把「生成文件」「写入规则」「执行测试」直接视为「结果正确」「规则已生效」「测试通过」。

## 七、目标驱动与主要矛盾：为什么 AI 容易陷入细节（讨论中）

> 状态：2026-11-21 初步讨论记录，**尚未作为正式执行规则定稿**。本节用于持续完善人与 AI 的工作方式。

### 7.1 观察到的现象

在长流程工程中，AI 往往按照「发现问题 → 立即分析修复 → 又发现新问题 → 继续修复」的顺序行动。即使每个局部问题处理得认真，仍可能没有推进最终交付目标。

**核心问题**：AI 往往先回答「怎样解决眼前问题」，却未先判断「这个问题是不是当前阻碍目标实现的主要矛盾」。

### 7.2 初步原因分析（需在实际工程中验证）

1. **最近的问题最显眼**：当前消息、工具错误、子 Agent 的报告往往比长期目标更具体、更容易直接执行。
2. **目标没有贯穿各层**：最终目标、阶段验收标准、当前关键路径与眼前子任务之间缺少显式联系，局部 Agent 容易只完成自己的小任务。
3. **缺少“是否值得现在修”的决策关口**：发现问题后直接进入解决，而不是先判断阻塞性、影响与依赖关系。
4. **局部成功替代全局进展**：把「问题关闭、文件生成、任务完成」视为进步，却没有检查整个工程是否更接近阶段验收和最终交付。

以上是工作机制层面的假设，不能仅据此断言所有 AI 或所有项目都如此。

### 7.3 候选原则：先保目标，再解决问题

建议形成四层视野：

**最终目标 → 当前阶段必须通过的验收关口 → 当前最关键的阻碍 → 本次最小必要行动。**

AI 发现问题时，先做一个「目标影响判断」：

- **A｜主线阻塞问题**：不解决就不能满足当前阶段的关键验收条件，或无法安全继续工程。优先查根因，解决足以解除阻塞的最小必要部分，然后立即回到主线。
- **B｜高价值但不阻塞**：可能影响后续质量、成本或效率，记录影响和建议时机，按依赖关系安排，不自动抢占主线。
- **C｜当前不相关或可延后**：写入待办/改善清单，不在当前执行阶段展开。

注意：安全、合规、机密保护、数据破坏风险或明确的强制约束不能仅因不在当下主线上就推迟。主要矛盾会随着阶段完成而改变，需要定期重新判断。

### 7.4 判断流程（候选）

~~~mermaid
flowchart TD
  A["回顾最终目标及当前阶段验收标准"] --> B["发现新问题"]
  B --> C{"不立即处理，是否阻碍关键目标或存在不可接受风险？"}
  C -- "是" --> D["确认根因、证据与最小必要修复"]
  D --> E["实施、验证是否解除阻碍"]
  E --> F["回到主线：检查阶段目标进展"]
  C -- "否" --> G["记录影响、优先级和后续处理时机"]
  G --> F
~~~

### 7.5 结合 Agent 项目理解（用于讨论的例子）

- **对应一览中的改修要求在 Step3 改修一览里遗漏**：若会导致后续设计漏改，属于当前交付链路的主线阻塞问题，应优先修正并核对全量映射。
- **说明资料中的非关键排版样式不够美观**：如果不影响当前阶段规定的验收或使用，通常先记入后续改善项；如果当前验收明确要求某种可读性，则应重新评估优先级。
- **某个 Action 参数的来源和实际生效机制不明**：不能只因看不懂就无限深入；应先判断它是否是确保本次实现正确、安全的必要条件，再决定调查深度。

### 7.6 待继续讨论和确认的问题

1. 怎样让 AI 在每次子任务开始时，自动把任务与**最终目标和当前阶段完成标准**关联？
2. AI 发现问题后，用什么最简单的判断，区分「必须现在解决」和「可以暂缓」？
3. 谁来确认问题优先级；什么时候 AI 可以自行判断，什么时候需要用户决策？
4. 怎样衡量「工程推进」而不只统计「处理了多少问题」？

**本轮的首要讨论点**：是否应把「新问题先判断是否阻碍主线，否则进入待办，不立即展开」作为协作方式的基本决策关口？
