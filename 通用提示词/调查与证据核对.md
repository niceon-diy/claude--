## 中文

<a id="scope-and-evidence"></a>

### 1. 范围、依据与过程记录

适用于程序、Shell、COBOL、SQL、批处理及调用链，业务逻辑，程序与设计的关系，文件／DB／IF 影响，重运行判断及测试观点的调查。各专题可以增加检查项，仍需覆盖下述范围、证据、验证和交接要求。

1. **先确定范围。** 写明目标、正式输入、当前版本、历史参考、对象和判定标准。建立对象及关系清单，分别记录“已识别”“已调查且验证”“已调查待验证”“未调查”“无法读取／无法确认”，不把未检测、未读取或不可访问解释为不存在。
2. **沿实际关系追踪。** 从入口继续确认直接、间接及动态依赖、业务条件、参数传递、数据来源、文件／DB／IF 副作用。不能只看入口、部分文件或关键词命中就宣布调用链和影响完整；无法展开的关系保留原因、受影响结论及补充资料位置。
3. **区分结论状态。** 每项记录为已确认事实、推断、未确认或证据冲突。推断写明前提、已知依据和适用限制。文件名、惯例、相似代码、旧报告、搜索结果和表面合理性不能独立充当证明。
4. **保留可复查证据。** 重要结论至少关联：结论 ID、原始资料／Source、可确认版本、具体行／函数／段落／章节／表格位置、相关原文或代码、支持结论的简要理由、交叉核对依据（适用时）及验证状态。使用已核实的位置；不能只给文件名、概括或未经验证的链接。
5. **双向核对代码与设计。** 从每条相关设计要求查实际实现，再从实际处理、条件、参数和数据操作反查设计。记录一对多、多对一、缺失、冲突、过时设计及无法对应；不强行归类。设计里写了不等于已实现，代码存在也不等于满足本次要求。
6. **使用可重复过程。** 按“明确范围 → 建立对象清单 → 追踪关系 → 收集原始证据 → 分析与判定 → 验证／评审 → 保存过程成果 → 汇总与验收”执行。记录实际使用的工具、脚本、输入和检查方法，使他人能复查；专题检查不能替代必要的范围核对。
7. **保存过程成果。** 沿用工程既有成果位置和格式，保存对象覆盖、进度、调用／对应关系、证据索引、关键判定依据、复查结果、未确认项及下一步。过程记录与原文、版本和最终报告相互关联，不能只保留最终报告或依靠聊天上下文。已有成果复用前确认版本及适用范围。
8. **来源变化后复核。** 原资料或版本变化时，确定受影响的证据和结论，重新验证后更新状态。AI 摘要不能代替原资料，未验证的中间结论不能自动变为事实；记录或机制尚不存在时如实写明，不把计划当作已经运行。
9. **静态结论写清边界。** 读取代码、设计和配置只能支持已验证范围内的静态判断；不代表业务程序已经运行、数据库已经实测、动态依赖已经解决或重运行已经证明安全。

<a id="evidence-review"></a>

### 2. 证据与结论复查

在重要阶段和交接前，回到原始依据检查：

- 事实、推断、未确认和冲突是否分别标明，推断的条件是否仍然成立。
- 证据是否真的支持本条结论，是否遗漏执行条件、数据来源、参数、调用路径、其他可能行为或反例。
- 前一步结论在用于后一步前是否已经核实；不能把未经复查的旧结论作为新事实继续传播。
- 设计与代码是否双向覆盖，未调查、无法解析和范围外对象是否都有记录；范围外必须有理由。
- 原文、实际代码、调查说明和判定理由是否分开，证据版本与定位能否实际打开核对。
- 是否存在无依据推断、逻辑跳跃、漏查或用“没发现风险／反例”代替正面证明。

完成反馈列出目标与范围、实际检查的对象及覆盖情况、已确认结论、代码与设计差异、问题及影响、未确认／限制、复查结果和剩余工作。明细可放在结构化台账中，由报告给出明确索引；简短反馈不省略必要证据，冗长报告也不能弥补未验证。

“格式完整”“内容很多”“结论看起来正确”“AI 说已理解／已确认”以及脚本通过，都不能单独证明调查完整、过程正确或已经独立验证。独立复查应实际返回资料，验证来源、范围和结论。

### 3. 工程调查规则的只读检查

本节用于检查现有规则是否支持调查，关联 [LATER-004：只读评估调查基础](https://github.com/niceon-diy/claude--/issues/20)。评估与改修分开；不能把完成本节作为其他已准备好任务的前置门槛。

**检查范围：** 当前工程实际使用的 `CLAUDE.md`、`.claude/` 下相关配置、可访问且适用的用户共通规则。先列出实际读取文件的绝对路径，区分“实际加载并生效”“参考资料”“尚不能确认是否加载”；没有验证加载情况就保持未确认。

| 检查项 | 核对内容 |
| --- | --- |
| Box 与设计资料访问 | 是否明确搜索、读取方法、可访问范围，以及读取失败／权限不足时如何记录和继续处理 |
| 设计书版本 | 是否区分过去类似 テーマ 的参考设计与本次实际改修的当前设计，能否确认来源和版本 |
| 本地程序调查 | 是否明确 Shell、COBOL、DB、IF、直接／间接／动态调用、参数与数据处理的调查方法 |
| 证据验证 | 是否要求文件、版本、章节／行号等可复查依据，区分事实、推断、未确认和矛盾，并复核结论 |
| 操作约束 | 是否明确未获当前任务授权不得修改业务程序、设计、配置或执行有副作用的操作，限制是否与实际生效规则一致 |

每项判为“已对应／部分对应／未对应／无法确认”，填写证据文件与具体位置、已满足点、缺口、对当前调查的影响和最小改善候选。规则冲突要同时列出各处依据及影响，不自行改写被检查配置以消除矛盾。

只读评价限于与目标相关的目录和资料；可以使用必要的只读 Git 查询核对版本，但不改写提交、索引或工作区。不无范围全盘扫描、不运行业务程序、不连接数据库执行操作，也不创建、修改、移动或删除被评估文件。报告沿用当前任务约定的成果位置；没有保存要求时在回复中说明。发现缺口不自动安装 Hooks、改配置或重建整体框架；其他有资料支持的独立工作继续按原任务执行。

报告区分“规则文字存在”“实际加载”“机制已实现”“已有运行证据”，不可相互替代。仅有静态规则或示例报告时，不能声称工程机制已经实际运行。

## 日本語

<a id="scope-and-evidence-ja"></a>

### 1. 範囲・根拠・過程の記録

プログラム、Shell、COBOL、SQL、バッチと呼出しチェーン、業務ロジック、コードと設計の関係、ファイル／DB／IF の影響、リラン判断、試験観点の調査に適用します。専門項目を追加しても、以下の範囲・根拠・検証・引継ぎを省略しません。

1. **最初に範囲を定める。** 目的、正式入力、現行版、過去参考、対象、判定基準を明記します。対象・関係の一覧を作り、「特定済み」「調査・検証済み」「調査済み・要検証」「未調査」「読取り不能／確認不能」を区別します。未検出、未読、アクセス不能を不存在とみなしません。
2. **実際の関係を追う。** 入口から直接・間接・動的依存、業務条件、引数の受渡し、データの出所、ファイル／DB／IF への副作用を確認します。入口、一部ファイル、検索命中だけで呼出しや影響が完全としません。展開できない関係には理由、影響する結論、必要資料の場所を残します。
3. **結論の状態を分ける。** 確認済み事実、推論、未確認、証拠の不整合を記録します。推論には前提、現時点の根拠、適用制限を付けます。ファイル名、慣例、類似コード、旧報告、検索結果、もっともらしさだけでは証明になりません。
4. **再検証できる根拠を残す。** 重要結論には、結論 ID、原資料／Source、確認できた版、行／関数／段落／章節／表の位置、関連原文・コード、結論を支える短い理由、必要な相互照合根拠、検証状態を関連付けます。定位は確認済みのものを使い、ファイル名、要約、未検証リンクだけで済ませません。
5. **コードと設計を双方向に照合する。** 関連する各設計要求から実装を探し、実処理、条件、引数、データ操作から設計を逆に確認します。一対多、多対一、欠落、矛盾、古い設計、対応不能を記録し、無理に対応付けません。設計への記載は実装済みを、コードの存在は今回要件への適合を意味しません。
6. **再実施できる手順にする。** 「範囲の明確化 → 対象一覧 → 関係追跡 → 一次証拠収集 → 分析・判定 → 検証／レビュー → 過程成果保存 → 統合・受入確認」の順で進めます。使用したツール、スクリプト、入力、確認方法を残し、第三者が追跡できるようにします。専門チェックは必要な範囲照合の代わりになりません。
7. **途中の成果も保存する。** 工程の既存の保存場所・形式を使い、対象の網羅状況、進捗、呼出し／対応関係、根拠索引、重要判断の根拠、再検証結果、未確認、次の作業を残します。原文・版・最終報告と関連付け、最終報告やチャットの文脈だけに依存しません。既存成果の再利用前に版と適用範囲を確認します。
8. **出所が変われば再確認する。** 原資料や版の変更が影響する根拠・結論を特定し、再検証後に状態を更新します。AI 要約を原資料の代わりにせず、未検証の中間結論を自動的に事実へ変えません。記録や仕組みが未整備なら、その旨を明記し、計画を稼働済みとしません。
9. **静的判断の境界を示す。** コード・設計・設定の読取りで裏付けられるのは検証済み範囲の静的判断です。業務プログラムの実行、DB 実測、動的依存の解決、リラン安全性の実証を意味しません。

### 2. 根拠と結論の再点検

重要な段階と引継ぎ前に原資料へ戻り、次を確認します。

- 事実、推論、未確認、不整合が区別され、推論の前提が現在も成立するか。
- 根拠がその結論を支持するか。実行条件、データの出所、引数、呼出し経路、別の動作や反例を見落としていないか。
- 前の結論を次の判断に使う前に確認したか。未検証の旧結論を新たな事実として伝播していないか。
- 設計とコードを双方向に確認し、未調査、解析不能、範囲外にも記録があるか。範囲外の理由があるか。
- 原文、実コード、調査説明、判定理由が分かれ、根拠の版と位置を実際に開いて確認できるか。
- 根拠のない推測、論理の飛躍、確認漏れ、「リスク／反例が見つからない」ことによる証明の代用がないか。

報告には目的・範囲、実際の確認対象と網羅状況、確認済み結論、コードと設計の差異、問題と影響、未確認・制限、再検証結果、残作業を示します。明細は構造化台帳へ保存し、報告から明確に参照できます。短さのために必要な根拠を省かず、長さで検証不足を補いません。

書式の充足、情報量、もっともらしい結論、AI の「理解した／確認した」という申告、スクリプトの成功だけでは、調査の完全性、過程の正しさ、独立検証を証明できません。独立した点検では実際に原資料へ戻り、出所・範囲・結論を確認します。

### 3. 工程の調査ルールを読み取り評価する

既存ルールが調査を支えられるかを確認する節です。[LATER-004：調査基盤の読取り評価](https://github.com/niceon-diy/claude--/issues/20)に対応します。評価と改修を分け、他の準備済みタスクをこの評価の完了待ちにしません。

**確認範囲：** 現工程で実際に使う `CLAUDE.md`、`.claude/` 配下の関連設定、アクセス可能で適用対象となるユーザー共通ルールです。読んだファイルの絶対パスを最初に示し、「実際に読込み・適用済み」「参考資料」「読込み状態が未確認」を分けます。読込みを検証していなければ未確認のままにします。

| 評価項目 | 確認する内容 |
| --- | --- |
| Box・設計資料へのアクセス | 検索・読取り方法、アクセス範囲、読取り失敗／権限不足の記録と継続方法が定められているか |
| 設計書の版 | 類似する過去 テーマ の参考設計と今回改修する現行設計を分け、出所・版を確認できるか |
| ローカルプログラムの調査 | Shell、COBOL、DB、IF、直接・間接・動的呼出し、引数とデータ処理の調査方法が定められているか |
| 根拠の検証 | ファイル・版・章節／行等の追跡可能な根拠、事実・推論・未確認・矛盾の区分、結論の再検証を求めているか |
| 操作上の制約 | 現タスクで許可されていない業務プログラム・設計・設定の変更や副作用のある操作を禁止し、実際に有効なルールと整合するか |

各項目を「対応済み／一部対応／未対応／確認不可」と判定し、根拠ファイル・位置、満たす点、不足、現調査への影響、最小の改善候補を記録します。矛盾は双方の根拠と影響を示し、確認対象の設定を勝手に直して消しません。

読取り評価は対象に関係するディレクトリと資料に限定します。版確認に必要な読取り専用 Git 照会は利用できますが、コミット・インデックス・作業ツリーは変更しません。範囲を定めない全ディスク走査、業務プログラム実行、DB 接続・操作、評価対象ファイルの作成・変更・移動・削除は行いません。報告は現タスクで定めた成果場所へ保存し、保存要求がない場合は回答で説明します。不足発見を理由に Hooks 導入、設定変更、全体基盤再構築を自動開始しません。根拠の揃う別の作業は元の依頼に従って継続します。

「規則の記載」「実際の読込み」「仕組みの実装」「運用証拠」を区別します。静的なルールや報告例だけで、工程の仕組みが稼働しているとは報告しません。
