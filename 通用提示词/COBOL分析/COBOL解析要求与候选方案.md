## 中文

<a id="requirements"></a>

### 1. 解析目标、输入和边界

目标是让初级程序员能够理解约 3 万行、100 多个 SECTION 的实际 COBOL 程序，准确说明指定位置的处理、变量及取值、条件分支、循环，以及从入口到该位置的调用路径。规模是原讨论场景，不是对实际输入的限制。

先确认目标 Source 的真实路径与有效版本、编码、编译器／方言、固定或自由格式、相关 COPYBOOK／被调用程序及可读取范围、业务设计、输出目录。实际用户指定的目标和工程证据优先，不能把行数最多的文件直接认定为真正主程序。

每个实体保留代码中的实际名称，同时提供读者可理解的中文说明名。说明名不是实际符号的改名；无法确认业务含义时，标明暂定解释和依据。只读原 Source，分析成果写入工程既有的调查成果位置；缺资料与未读范围逐项记录。

本文补充 COBOL 特有的解析细节。[P001 程序与设计书对应调查](../程序与设计书对应调查/P001_程序与设计书对应调查及报告生成提示词.md)继续负责代码与设计依据的对应报告。14 项目 P002 负责漏项与参考 Diff；AI／Manual P002 与 LATER-001 负责调查既有智能体，均不能单凭文档存在推断本候选构成已实施。

<a id="section-map"></a>

### 2. 第一阶段：SECTION 地图与变量索引

若本轮只指定第一阶段，就只生成索引与待确认事项，不提前声称业务逻辑分析完成。

1. 在实际工程范围内搜索 .cob、.cbl、.COB、.CBL 等已知 COBOL 文件，列出候选。未指定目标时，结合 PROGRAM-ID、PROCEDURE DIVISION、调用与工程资料定位目标；行数与大小只作候选信息。多个实际主程序分别建图。
2. 记录文件路径、总行数、PROCEDURE DIVISION 的真实行号。只在该部之后识别过程 SECTION，排除 WORKING-STORAGE SECTION、FILE SECTION、LINKAGE SECTION 等数据部定义。
3. 按实际方言和源格式识别 SECTION。固定格式中第 7 列为 * 的注释、以 *> 标识的注释须过滤；其他注释、续行和调试行按实际编译规则判断。形如 “名称 SECTION.” 的检索结果只是候选，不以一次正则命中替代源格式核查。
4. 每个 SECTION 记录实际名称、开始行、结束行、行数、名称推测职责和备注。通常结束行是下一 SECTION 开始行减 1，最后一项到真实 PROCEDURE DIVISION 结束位置或文件末尾；核实边界后再填写。没有 SECTION 的段落或未归属区段单独登记，不制造 SECTION 补齐数量。
5. 仅凭名称推测职责时，写明“推测、待确认”。索引阶段不据名称作业务实现结论。
6. 同时建立变量索引：实际名称、定义位置、初始化位置、赋值位置、参照／利用位置及所属 SECTION。COPYBOOK 缺失、同名变量、限定名、REDEFINES 或别名导致的不明确关系单列。
7. 使用确定性检索和分段读取逐步处理大文件，保留实际行号；避免一次把全部代码放入单个模型上下文。核对分段覆盖区间、衔接和重复，不能因分批漏掉区段。

SECTION 表至少包含：编号、实际名称、开始行、结束行、行数、名称推测职责、备注、来源版本／位置。索引阶段的简短反馈包含目标路径、总行数、PROCEDURE DIVISION 行号、SECTION 总数、成果路径、前 10 项及未确认内容；完整索引保存在成果文件。

### 3. 分析、验证、流程图与逐行说明

| 阶段 | 必须整理的内容 | 交付与完成依据 |
| --- | --- | --- |
| 索引 | SECTION、变量及其定义／初始化／赋值／参照位置 | 完整索引、文件版本、覆盖区间与未解析项 |
| SECTION／变量分析 | 每个 SECTION 的实际名与说明名、行号、长度、处理概要、功能分类、关键变量及用法、分支与循环；每个变量的实际名与说明名、行号、类型、定义及使用位置与所属 SECTION | 分 SECTION／变量的记录，结论能回到 Source |
| 验证 | 逐项回读 SECTION 从开始到结束的代码；核对正向与反向调用、遗漏节点、外部 CALL、条件、循环及变量使用。复核不能只重述上一阶段文字 | 每项覆盖状态、发现的差异、修正及剩余未确认内容 |
| 流程图 | 入口至目标位置的路径、调用关系、触发条件、分支及循环；外部／动态／未解析节点保留状态 | 图中节点与实际 Source、行号、分析记录一一对应 |
| 全代码逐行说明 | 左侧完整代码，右侧同位置的逻辑说明；解释变量用途及关键取值，支持 SECTION／行号导航 | 代码不截断，说明与行号对齐，图和索引能跳回相应位置；实际打开核对长代码、换行与导航 |

变量值域要分别记录：代码明示的常量／区分值及含义、可由定义和条件推导的约束、来自外部输入或依赖而尚不能确定的范围。附证据与未知条件，不能为了满足“所有可能值”而编造值，也不能把任意输入范围假写成有限枚举。对原文未能证明的含义保留待确认。

调用与资源的具体检查使用[单程序静态调查清单](单程序静态调查清单.md#static-checklist)。图解版可由 LATER-003 交付；完整逐行对照是本解析要求中的独立范围，不能把少量教学片段当成全代码逐行说明完成。

优先使用实际工程约定的成果目录。以下是可采用的相对文件结构，不是已存在的工程文件，也不要求为了统一名字搬动公司既有成果。

### 5. Agent＋Command＋Skill 候选构成

这是可选设计，需先按 LATER-001 确认公司已有机制，再由 LATER-002 比较必要性和最小采用范围。没有实际定义文件、有效配置与验证证据时，只能称为候选方案。

| 组件 | 候选职责 | 核对重点 |
| --- | --- | --- |
| Command | 接收实际目标与范围，作为用户入口 | 参数、范围和输出位置能明确传给执行流程 |
| Agent／子任务 | 分批执行索引、分析、复核及生成文档；主流程只汇总必要结果 | 实际工具是否提供独立上下文；失败、重试和汇总如何处理，不能假定自动隔离或自动续跑 |
| Skill／共通知识 | 索引、SECTION／变量分析、验证、输出格式规范 | 载入时机、适用范围、版本和与已有规则的冲突 |
| 确定性工具 | 文件盘点、候选检索、区间／引用检查、产物生成 | 工具输出仍需按方言、范围和原文复核 |

原讨论示例有 cobol-indexing、cobol-section-analysis、cobol-verification、cobol-output-format 等规范，以及命令、Agent 定义的目录和 frontmatter。模型名、工具权限、skills 字段、user-invocable 等均须按公司实际 Claude 版本与环境核实，不将历史示例复制成已生效配置。

先形成角色输入输出 Schema、证据格式、资料加载、失败返工、状态保存和完成条件，再用许可的小型真实 Source 比较既有方式与候选方案。实现、接入和验收分别列为实际采用范围内的后续任务，不因整理讨论而改造整个工程。

## 日本語

<a id="requirements-ja"></a>

### 1. 解析の目的・入力・境界

初級プログラマーが、約3万行・100超のSECTIONからなる実際のCOBOLを理解し、指定位置の処理、変数と値、条件分岐、ループ、入口からそこへ至る呼出し経路を正確に説明できることが目的です。この規模は元の相談の想定で、実際の入力を制限する条件ではありません。

対象Sourceの実パスと有効版、文字コード、コンパイラー・方言、固定／自由形式、関連COPYBOOK・呼出し先と読取り範囲、業務設計、成果の保存先を確認します。ユーザーが指定した実対象と工程の根拠を優先し、最大行数のファイルを本当の主プログラムと即断しません。

各エンティティは実コード名と、読者が理解できる日本語説明名を併記します。説明名で実際の識別子を改名せず、業務上の意味が不明なら暫定解釈と根拠を示します。元Sourceは読取り専用とし、成果は工程の既存保存先へ記録します。不足資料・未読範囲を個別に残します。

本書はCOBOL固有の解析詳細を補います。[P001 プログラムと設計書の対応調査](../程序与设计书对应调查/P001_程序与设计书对应调查及报告生成提示词.md)はコードと設計根拠の対応報告、14案件P002は漏れと参考Diff、AI／ManualのP002とLATER-001は既存エージェントの調査を担当します。資料の存在だけで本候補構成が実装済みとは判断できません。

<a id="section-map-ja"></a>

### 2. 第1段階：SECTIONマップと変数索引

今回が第1段階だけの依頼なら、索引と未確認事項だけを作成し、業務ロジックの解析完了とは報告しません。

1. 実工程の範囲内で.cob、.cbl、.COB、.CBLなどの既知形式を探し、候補一覧を作ります。未指定時はPROGRAM-ID、PROCEDURE DIVISION、呼出しと工程資料から対象を確認し、行数・サイズは候補情報とします。複数の実主プログラムは別々に整理します。
2. パス、総行数、PROCEDURE DIVISIONの実際の行番号を記録します。その後だけで手続きSECTIONを識別し、WORKING-STORAGE SECTION、FILE SECTION、LINKAGE SECTIONなどのデータ部を除外します。
3. 実際の方言・ソース形式でSECTIONを識別します。固定形式の第7列が*のコメント、*>によるコメントを除外し、その他のコメント・継続行・デバッグ行は実コンパイル規則で判定します。「名称 SECTION.」の検索結果は候補で、正規表現一回だけで確定しません。
4. 各SECTIONの実名、開始行、終了行、行数、名前からの推測責務、備考を記録します。通常は次SECTIONの開始行−1を終了行とし、最後は実際のPROCEDURE DIVISION終端またはファイル末尾までです。境界を確認してから記入します。SECTIONのない段落や未所属区間は別記し、数合わせのSECTIONを作りません。
5. 名前だけからの責務は「推測・要確認」とします。索引段階で名称から業務実装を断定しません。
6. 変数索引も作ります。実名、定義・初期化・代入・参照利用の位置と所属SECTIONを記録し、COPYBOOK欠落、同名・修飾名、REDEFINESや別名による不明関係は別記します。
7. 決定的な検索と分割読取りで大きなファイルを扱い、実際の行番号を保持します。全コードを一つのモデル文脈へ一度に投入せず、区間の網羅・接続・重複を照合し、分割による欠落を防ぎます。

SECTION表は番号、実名、開始行、終了行、行数、推測責務、備考、出所版・位置を含みます。索引完了時の短い報告は対象パス、総行数、PROCEDURE DIVISION行、SECTION数、成果パス、先頭10件と未確認事項です。完全な索引は成果ファイルへ保存します。

### 3. 分析・検証・フロー図・全行説明

| 段階 | 必須内容 | 成果と完了根拠 |
| --- | --- | --- |
| 索引 | SECTION、変数、定義・初期化・代入・参照位置 | 全索引、ファイル版、網羅区間、未解析項目 |
| SECTION・変数分析 | SECTIONの実名と説明名、行・長さ、概要、機能分類、主要変数と使い方、分岐・ループ。変数の実名と説明名、行、型、定義・使用位置と所属SECTION | SECTION・変数別の記録とSourceへ戻れる結論 |
| 検証 | 各SECTIONの開始から終了まで独立して再読し、順方向・逆方向の呼出し、欠落ノード、外部CALL、条件、ループ、変数利用を確認。前段説明の繰返しだけにしない | 対象別の網羅状態、差異、修正、残る未確認 |
| フロー図 | 入口から対象への経路、呼出し、条件、分岐、ループ。外部・動的・未解析ノードの状態を保持 | 図のノードがSource・行・分析記録と対応 |
| 全コード行単位説明 | 左側に全コード、右側の対応位置に論理説明。変数の用途と主要値を説明し、SECTION・行で移動可能にする | コードの欠落がなく説明と行が揃い、図・索引から該当位置へ戻れる。長いコード・折返し・移動を実際に開いて確認 |

変数の値域は、コードに明示された定数・区分値と意味、定義や条件から導ける制約、外部入力・依存により未確定な範囲を区別します。根拠と不明条件を付け、「全ての可能値」を満たすために値を捏造したり、任意入力の範囲を有限列挙と偽ったりしません。原文で証明できない意味は要確認とします。

呼出し・リソースの詳細は[単本静的調査チェックリスト](单程序静态调查清单.md#static-checklist-ja)を使います。図解版はLATER-003で納品できますが、全コードの左右行対照は本要件の独立した範囲です。少数の説明用コード片を全行説明の完了と扱いません。

### 4. 段階成果の契約と会話をまたぐ継続

実工程の既存保存先を優先します。以下は採用できる相対構造の例で、既に存在するファイルを示さず、会社成果を名前の統一だけのために移動させる要求でもありません。

| 段階・ファイル | 最小データ契約 |
| --- | --- |
| manifest.json | 対象と版・ハッシュ、コンパイル・文字コード条件、実入力範囲、実行・バッチID、段階状態、網羅区間、成果入口、要確認、次の一手 |
| index/sections.json、index/variables.json | 安定エンティティID、実名、説明名、ファイル・行範囲、定義・使用位置、読取り・解析状態 |
| analysis/sections/、analysis/variables/ | エンティティID、処理・値の説明、呼出し・リソース関係、根拠、推測・制約。各バッチを別保存 |
| verification/report.json | 照合対象、独立再読範囲、差異と処理結果、未解析ノード、網羅不足 |
| diagrams/flow.json | 安定ノード・辺ID、対応エンティティと位置、条件、ループ、解析状態。同じデータから図を生成 |
| documentation/ | 全コードと行単位説明、図・索引の入口、出所版、未確認範囲。実際に必要なMD・HTMLを利用 |

後続段階は保存成果とmanifestから続け、会話の記憶に依存しません。主工程が各バッチを統合し、IDの一意性、参照の有効性、区間の接続を確認し、重複・未解析を記録します。Sourceや依存の版が変わったら、影響する索引・分析・図を要再確認にして更新します。形式の再出力を再解析と扱いません。

### 5. Agent・Command・Skillの候補構成

任意の設計案です。LATER-001で会社の既存機構を確認し、LATER-002で必要性と最小採用範囲を比較します。実定義、有効設定、検証証拠がなければ候補案とのみ呼びます。

| 要素 | 候補の役割 | 確認点 |
| --- | --- | --- |
| Command | 実対象・範囲を受け取るユーザー入口 | 引数、範囲、出力先が実行工程へ明確に渡る |
| Agent・子タスク | 索引・分析・再確認・文書生成を分割実行し、主工程は必要結果を集約 | 独立文脈の実機能、失敗・再試行・統合。自動分離・自動継続を仮定しない |
| Skill・共通知識 | 索引、SECTION・変数分析、検証、出力形式の規範 | 読込み時点、適用範囲、版、既存ルールとの衝突 |
| 決定的ツール | 棚卸し、候補検索、区間・参照点検、成果生成 | 出力も方言・範囲・原文で検証する |

元の案にはcobol-indexing、cobol-section-analysis、cobol-verification、cobol-output-formatなどの規範と、Command・Agentの定義ディレクトリやfrontmatterがあります。モデル名、ツール権限、skills欄、user-invocableなどは会社の実Claude版・環境で確認し、履歴例を有効設定とみなしません。

役割の入出力Schema、根拠形式、資料読込み、失敗・手戻り、状態保存、完了条件を設計し、許可された小さな実Sourceで既存方式と比較します。実装・導入・検証は実際の採用範囲で別の後続タスクとし、相談整理だけで工程全体を改造しません。
