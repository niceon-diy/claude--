## 中文版｜直接发给 Claude 的提示词

### 一、目标与范围
请把**你在本会话中刚刚向我解释过的那段内容**完整保留下来，并以该解释为起点，结合本次任务的实际资料与实现证据，制作一套**带 Flow 图、能够独立阅读、能追溯来源的说明资料**。

这是今后所有解释型资料的统一生成方法，不限于当前 Agent、当前 Step 或当前项目。**既有资料不得被静默覆盖或抹去原始解释**。对不相关的简短问答，不强制每次生成文件或 Flow 图。

### 二、先保存已有解释，不允许丢失
1. 找到当前会话中你刚给我的解释，确定其具体消息/段落范围。首先把**完整原文逐字保留**到说明资料的「原解释（原文保留）」章节或独立附录，包含原有标题、编号、说明、限制、QA 和已知未确认事项。不得把摘要、重写或流程图当作原文替代品。
2. 对该原文单独附上来源识别信息（会话、消息或时间等可核实信息）。若无法读取该解释，明确标注「原解释未取得」，**不得假装已经保留或自行重建原文**；先完成可做的模板和已取得内容，再说明缺失项。
3. 后续如果发现解释有错：**原文不改**，另设「订正与补充／変更履歴」写明原文位置、纠正后的内容、依据及理由。以前解释过的内容和后来的订正都要能够查阅。

### 三、生成适合阅读的说明书
请在符合现有工程目录规则的地方生成以下成果；不得未经确认假定公司环境路径存在。
- **MD 正本**：说明内容的唯一维护源；至少包括「0.整体结构 → 1.目的与范围 → 2.原解释（全文）→ 3.输入／处理／输出总览 → 4.Flow 图 → 5.节点逐项详解 → 6.实际文件与证据对照 → 7.QA／例外／未确认事项 → 8.验证结论 → 9.订正记录」。
- **HTML 阅读版**：由同一份 MD 内容生成，含**左侧目录导航**、章节跳转、返回总览、图文同屏或相邻可查的结构；**可离线打开**，不依赖外网 CDN、远端 JavaScript 或必须在公司电脑另行安装的软件。完整原文及证据详情仍需可在同一份报告内阅读。
- **Flow 图**：MD 中保留可维护的 Mermaid 源码；HTML 中提供能离线查看的实际图形（如已验证可生成的静态 SVG，或等效的自包含图形）。若环境不能生成/渲染离线图形，诚实报告「图形尚未生成」，保留 Mermaid 源，不得把代码块冒充已完成的可视化图。
- 文件名和路径按实际项目既有约定确定，**不覆盖旧版**，先检查已有同名文件；新建或更新时保存变更记录。

### 四、Flow 图必须解释实际 How，而非装饰
图必须来自**真实可核查的处理流程**，至少呈现：
1. **输入**：哪个项目、哪份对应一览／改修一览／设计书／Source 或实际记录，具体读取哪些字段、章节或资料。
2. **处理主体**：哪个 Agent、脚本、程序、人或工程阶段负责该节点；实际执行主体和调用关系。
3. **How（最重要）**：怎样识别要求、怎样确定适用对象和写入位置、依据什么规则比较/拆分/转换/生成/调用/写入；每项操作的成立条件和具体判断方法。
4. **分支及例外**：什么条件走哪条路径，出现未确认、冲突、缺少资料、QA 或失败时怎样处理；**先查过去类似案件的实际改修**，找不到可用依据时再提出需要用户判断的问题。
5. **输出及传递**：每个节点生成哪些实体或文件（用真实名称/ID/路径），哪个下游节点读取，用来做什么。
6. **核对与闭环**：如何按原要求逐条对照产出、检测遗漏或无依据扩写，如何修正、复核并留下证据。

图中的每一个节点采用稳定 ID（如 F01、F02），箭头标明实际数据或控制流方向，判断分支写出条件；不能将未实现的「预期流程」画成「已实施事实」。如有必要，**已实施流程**与**目标/建议流程**分开成图并明确标记。

示例结构仅展示表达方式，**不是对当前项目实际行为的断言**：

~~~mermaid
flowchart TD
  A["F01 获取原解释与实际依据"] --> B["F02 完整保存原解释"]
  B --> C["F03 解析输入／处理／输出"]
  C --> D{"F04 有无未确认信息？"}
  D -- "有" --> E["F05 核查过去案件与当前证据"]
  E --> F["F06 说明真实处理及剩余QA"]
  D -- "无" --> F
  F --> G["F07 生成说明与Flow图"]
  G --> H["F08 逐条检查原文／图／证据一致"]
  H --> I["F09 生成离线阅读版"]
~~~

### 五、每个节点的解释模板（不得只给节点名字）
对于 F01、F02……每个节点，依次写清：
- **目的／Why**：本节点要解决的具体问题及其在整体流程中的作用。
- **来源／Where**：项目、输入文件的完整实际路径、章节/行号/字段、版本与证据位置。
- **执行者与时机／Who・When**：具体 Agent／程序／脚本及触发阶段。
- **输入／What**：实际输入内容、条件、前置成果。
- **处理／How**：处理规则、操作顺序、判断标准、具体实现方式；必要时列示关键代码、调用、参数、转换例；说明为何采取该处理。
- **输出／Result**：真实生成内容、文件完整路径、接收者及下游使用用途。
- **边界与验证**：异常、例外、未确认事项、核对方法与结果。
- **流程关联**：该说明对应哪个 Flow 节点，下一节点为什么能接收其输出。

特别针对 Agent/设计生成的说明，还必须说明：①如何识别改修内容；②如何决定归属和写入位置；③如何生成具体设计内容；④如何拆分跨文件和复杂条件；⑤谁实际写文件且怎样保护原有格式；⑥如何确保改修一览逐条反映而不遗漏。对于不适用项注明原因，未知项标注未验证，不能编造机制。

### 六、保证「原解释－Flow－实际资料」三方一致
建立对照表，至少包含：
「Flow节点ID｜原解释对应段落｜真实输入及依据位置｜执行主体与How｜生成结果及路径｜检查状态｜未确认问题」。

逐条验证：
- 原解释中的重要处理步骤、条件、例外、输出与注意点，在文字和 Flow 图中均可找到。
- 图上每个节点都有解释和依据；解释没有图未反映的关键逻辑；不凭想象增加流程。
- 每条原要求或改修项都能追踪到对应处理与结果；原文和改修一覧映射关系不被简化抹去。
- 明确区分「原文说法」「设计应如此」「代码现状」「执行日志证实」「推断／尚未确认」。
- 输入/生成/校验全程留实际路径、行号/章节、版本和可用时的哈希或时间戳；不存在的信息不能捏造。
- 改动仅限本次授权的说明资料与相关规则，不修改业务 Source、设计正本、既有总则或既有历史档案。

### 七、交付与后续统一规则
1. **先用两三句话**讲清本次资料的目标、核心 How 和生成结果，再给出整个资料的结构。用户需要分段讲解时，一次只讲一个节点/章节，解释后等待明确「继续」再讲下一段；**这不应阻止已授权的资料生成任务一次做完**。
2. 完成 MD、Flow 图和 HTML 后，报告每个文件的**完整实际路径、创建/修改状态、图的节点数与对应关系检查结果**；不能只发「完成了」或文件名。
3. 从本次以后，凡是生成或更新 **Agent 实现说明、调查报告、基本/详细设计的解释资料、工程执行手顺、处理流程说明、改修影响说明、实施结果说明**，均默认遵循本 P004，不必每次重新问是否要保留原解释及生成 Flow 图。**已有资料不自动批量改写**；之后被指定更新时按同样格式改造，并保留旧版与变更记录。
4. 如需真正让公司 Claude 后续会话长期自动执行，先读取当前有效的 CLAUDE.md / Harness 规则和优先级，检查冲突后把 P004 作为**专项规则引用**接入既有入口；**保留唯一核心总则**，不要另建冲突的总则或未经检查直接覆盖。报告「Git 已保存／公司规则已接入／新会话已加载／执行已验证」各自的真实状态。

**立即执行：先原样保留你刚刚的解释，再完成本次资料的 MD、Flow 图、离线 HTML 和三方对应检查。不要中途只解释计划而不生成成果。**

## 日本語版｜Claude にそのまま渡すプロンプト

### 1. 目的と適用範囲
**この会話であなた（Claude）が直前に説明した内容を全文そのまま保存**し、その説明と実際の資料・実装根拠に基づいて、**フロー図を備えた、単独で理解でき、根拠を追跡可能な説明資料**を作成してください。

本方式は今後のすべての**説明系成果物**（Agent実装説明、調査結果、設計内容の説明、作業手順、処理フロー、改修影響、実行結果など）に共通して適用します。無関係な短い質疑応答にまで資料・図の作成を強制するものではありません。既存の説明文や旧版を無断で消去・上書きしないでください。

### 2. 既存の説明を最優先で保持する
1. この会話で直前に回答した説明の対象メッセージと段落を特定し、見出し・番号・説明・制約・QA・未確認事項を含む**原文全文を一字一句変更せず**、資料内の「元の説明（原文保持）」または独立した付録に保存してください。要約、言い換え、フロー図で代替してはいけません。
2. 原文の出所（確認可能な会話・メッセージ・日時など）を記録してください。取得できなければ「元の説明は未取得」と明示し、**想像で再現したり、保持済みと報告したりしないこと**。作成可能な構成・入手済み内容は作成して、不足事項を報告してください。
3. 原説明の誤りが判明した場合でも原文を変更せず、別の「訂正・補足／変更履歴」に対象箇所、修正内容、根拠、理由を記載してください。

### 3. 説明資料の成果物
既存のプロジェクト規約と実際の保存先を調べ、次の資料を作成してください。未確認の社内パスを仮定しないでください。
- **MD正本**：説明内容の唯一の保守元。「0.全体構成 → 1.目的と対象範囲 → 2.元の説明全文 → 3.入力／処理／出力の全体像 → 4.フロー図 → 5.各ノードの詳細 → 6.実ファイルと根拠の対応 → 7.QA・例外・未確認事項 → 8.検証結果 → 9.訂正履歴」を含めてください。
- **HTML閲覧版**：同じMDを元に生成し、**左側の目次ナビゲーション**、章へのジャンプ、全体像へ戻る導線、フローと説明を照合できる構成にしてください。**オフラインで閲覧可能**とし、外部CDN・外部JavaScriptや社内PCへの新規ソフト導入を必須にしないでください。元の説明・根拠詳細も資料内で閲覧可能にしてください。
- **フロー図**：MDに保守可能なMermaidコードを残し、HTMLには実際にオフライン閲覧できる図（実環境で生成・検証済みの静的SVG、または同等の自己完結形式）を配置してください。生成できなければ「図は未生成」と明示し、Mermaidコードを残してください。コードだけを描画済みの図と報告してはいけません。
- 既存ファイル、命名規約、保存先を調べ、旧版を無断で上書きせず、変更履歴を残してください。

### 4. フロー図は実際の How を示す
図は確認可能な**実際の処理**を表し、次の要素を含めてください。
1. **入力**：対象プロジェクト、対応一覧／改修一覧／設計書／Source／実行記録、参照する項目・章・フィールド。
2. **実行主体**：各ノードを実行するAgent、スクリプト、プログラム、担当者または工程。
3. **How（最重要）**：改修内容の識別、反映対象と記載箇所の決定、比較・分割・変換・生成・呼出し・書込みの**具体的な判断規則と処理順序**。
4. **分岐・例外**：判定条件、資料不足、矛盾、QA、失敗時の対応。**まず過去の類似案件で実際に行われた改修を調査**し、適切な根拠が見つからない場合に利用者の判断を求めてください。
5. **出力と引継ぎ**：生成物の実際の名称・ID・完全パス、後続工程と利用目的。
6. **検証と是正**：原要求との全件突合、漏れ・根拠のない追加の確認、修正・再検証・証拠の記録。

各ノードには固定ID（F01、F02等）を付け、矢印の方向と判断条件を明示してください。**未実装の想定フローを実装済みの事実として描かないこと**。必要なら「実装済みのフロー」と「目標／提案フロー」を分けてください。

### 5. ノード単位で具体的に説明する
各F番号について、次を明記してください。
- **Why**：そのノードの目的と全体での役割。
- **Where／根拠**：対象プロジェクト、原資料の実際の完全パス、章・行・フィールド、版、証拠の所在。
- **Who／When**：実行するAgent・処理・担当者、実行段階・起動条件。
- **What／入力**：実際の入力、前提条件、前工程の成果物。
- **How**：具体的な処理規則、順序、判定条件、実装方法、必要なコード・呼出し・パラメータ・変換例、採用理由。
- **Result／出力**：実際の成果と完全パス、受渡し先・後続用途。
- **例外・検証**：例外、未確認事項、確認方法と実施結果。
- **関連**：フロー図のノードIDと前後ノードの入出力関係。

Agent／設計生成では、特に①改修の識別方法、②対象と書込み先の決定方法、③具体的な設計内容の生成規則、④複数ファイル・複雑条件の分割、⑤書込み主体と原形式の保全、⑥改修一覧の全項目を反映したことの検証方法を説明してください。該当しない項目は理由を書き、未確認の仕組みは作り上げないでください。

### 6. 「原説明・図・実資料」の三者を照合する
「フローノードID｜元説明の対応段落｜実際の入力・根拠位置｜実行主体とHow｜成果物・完全パス｜検証状態｜未確認事項」の対応表を作成してください。

原説明にある重要な処理、条件、例外、出力、注意事項が図と説明に揃っていること、すべての図のノードに説明と根拠があること、図だけの想像上の手順がないこと、原要件または改修項目から成果まで追跡できることを確認してください。「元の説明」「仕様上の期待」「実際のコード」「実行ログにより検証済み」「推論／未確認」を明確に区別してください。

実在するパス、章・行、版、取得可能なハッシュ・タイムスタンプを記録してください。未確認データを捏造しないこと。今回認められた説明資料と関連ルール以外の業務Source、原設計書、既存の基本原則、過去の記録は変更しないでください。

### 7. 納品と今後の共通適用
1. 最初に**2～3文で目的、中心となるHow、成果・現状**を簡潔に説明し、その後、資料全体の構成を提示してください。対話式に説明する場合は一度に一つの章／ノードだけ説明し、「続けて」と明示されてから次に進んでください。ただし、**承認済みの資料生成処理は最後まで連続実行**してください。
2. MD、フロー図、HTMLを作成した後、各成果物の**実際の完全パス、作成・更新区分、図のノード数、三者照合の結果**を示してください。実行していない作業を完了済みと報告しないでください。
3. 今後作成・更新する**Agent実装説明、調査報告、基本／詳細設計の解説、作業手順、処理フロー、改修影響、実行結果説明**にはP004を標準適用してください。**既存資料を一括して勝手に書き換えないこと**。更新指定を受けた資料は本方式で改訂し、旧版と変更履歴を残してください。
4. 社内Claudeの次回以降の会話で確実に参照できるようにする場合、まず有効なCLAUDE.md／Harnessルールと優先順位を確認し、競合しない**専門ルールへの参照**として組み込んでください。唯一の基本原則を増設したり無断で上書きしたりしないこと。「Git保存済み」「社内ルールへの組込み済み」「新規会話で読込み済み」「挙動検証済み」は別々に報告してください。
