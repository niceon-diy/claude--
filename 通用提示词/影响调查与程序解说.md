# 影响调查与程序解说／影響調査とプログラム解説

<a id="impact-and-explanation"></a>

[中文](#zh-cn) · [日本語](#ja)

两种语言是同一任务的完整等价说明，按需要选择一种执行；影响调查和程序解说可分别使用。相关证据标准见[调查与证据核对](调查与证据核对.md)，表达与交付方式见 [B001](B001_把话说清楚与输出格式.md)。  
両言語は同じ作業の完全な説明です。一方を選び、影響調査・プログラム解説を必要な範囲で使用してください。根拠の基準は[調査と根拠の照合](调查与证据核对.md)、説明・納品方法は [B001](B001_把话说清楚与输出格式.md)を参照します。

## 中文

### 1. 目标、输入与边界

依据本次功能追加／规格变更，查清真实影响、原因、调用及数据关系、改修对象、具体方案和测试观点；需要时输出新人可读、图与代码可相互定位的程序解说。

输入至少包括本次要求 ID／名称及具体要求、目标 Source 与可确认版本、现行设计及相关 DB／文件／IF／配置。先确认资料路径和实际适用范围；未知内容登记待确认，不把示例中的 `REQ-XXX`、类名、程序名或路径当作真实项目。

调查默认读取资料、保存调查成果，不改业务 Source、设计或配置。静态解析不等于已经运行业务程序或实测数据库；运行、DB 操作及实际改修按当前任务另行明确的范围执行。

### 2. 影响调查顺序与检查项

按“要求 → 数据／DB → IF → 画面 → OL 在线处理 → BT 批处理 → Source 参照与更新位置 → 调用方／被调用方 → 数据流 → 共通部件 → 测试 → 改修判定”逐项调查。检查范围依据实际工程；确实无关的项目保留不适用理由，不能漏掉后直接宣布无影响。

| 类别 | 应确认的具体内容 |
| --- | --- |
| DB | 表、列、PK／FK、索引、View、存储过程、DB 定义和 Entity／DTO／Model；SELECT／INSERT／UPDATE／DELETE 的对象、条件及数据影响；字段／表的参照与更新位置，JOIN／WHERE／ORDER BY／GROUP BY 的关系 |
| IF／外部系统 | 实际存在的 API、REST／SOAP、消息（如 Kafka）、文件连携、JSON／XML／CSV、Request／Response、Input／Output；字段名、类型、位数、必填、默认值、发送方与接收方、映射、校验、错误处理及数据经过的路径 |
| 画面 | 实际技术栈下的 HTML／JSP／Thymeleaf／JavaScript／TypeScript、Controller／Form／Validation；显示项、输入项、按钮、错误消息；字段增改、校验、显示条件、Submit 和后端 Request 的影响 |
| OL 在线功能 | 功能 ID／名称、Controller、Service、业务逻辑、DAO／Repository、SQL 和共通处理；从画面到后端、DB 的实际调用边、参数及返回结果，不只列文件名 |
| BT 批处理 | Job、Scheduler、Shell、Java Batch 或实际语言、SQL、Job 定义、输入输出文件、DB 与外部 IF；使用／更新／作成目标数据的批处理、依赖、执行顺序和异常处理 |
| 共通部件 | Utility、Common Service／DAO、共通 Validation／Mapper／Exception／Message／配置；通过父类、继承、Interface、共通 SQL／DTO／Mapper／配置传递的间接影响及对其他功能的二次影响 |
| 测试与运用 | 受影响的既有测试、数据格式、错误与日志、兼容性、迁移需要及回归范围；重运行适用时关联[重运行调查清单](../追加开发/重运行调查清单.md) |

图中的框架名称只是说明方式；工程没有相应组件时不虚构。实际数据流应能从“输入 → 校验 → 业务处理 → DB／IF → 输出”定位到代码、设计或配置。

### 3. 调用追踪、判定与改修方案

- 从目标处理向上找调用方，向下找被调用方，记录入口、条件、重要实参、返回值、数据生成／变化／传递／输出及副作用；动态或间接关系不能解析时写明缺口。
- 每个候选对象分别判为“有影响”“无影响”“待确认”。有影响写明改修内容及原因；无影响仍说明为何虽有关联却无需改修；待确认写明缺失信息、影响的判断和确认对象。不得用关键词命中代替实际关系。
- 发现设计与 Source 不一致时分别列出现行要求、设计、实际实现和依据，按本次指定基准判定；不自行选择看起来合理的一侧。
- 改修方案必须说明：文件与函数／SECTION／段落位置、现状、问题、本次要求、修改后的行为、为什么需要改、调用及数据／其他功能影响、异常处理与测试方法。不能只有“修改某程序”。
- 沿用现有规格与架构，在本次要求范围内提出必要改修；额外改善另列，避免把教学建议或历史差分直接当成正式规格。
- 测试观点覆盖成立／不成立条件、空值、边界、异常、既有功能回归，以及实际相关的 DB／IF／批处理影响；预期结果需要来源依据。

### 4. 影响报告与改修方案结构

沿用现有成果目录和稳定 ID。可维护一个主 Markdown，也可按工程惯例拆成 `impact_analysis.md`、`modification_plan.md`，必要时附 `call_graph.md`、`data_flow.md`；各文件的编号、版本、关系和结论保持一致。

报告至少包含：

| 部分 | 需要保存的内容 |
| --- | --- |
| 要求概要 | 要求 ID／名称、具体内容、正式输入和版本、目标及范围 |
| 影响范围汇总 | DB／IF／画面／OL／BT／共通部件的状态、对象数、概要；分开统计待确认，不能算作无影响 |
| 影响对象明细 | 记录 ID、类别、功能 ID、名称、完整路径及具体位置、处理内容、影响与理由、是否改修、证据及状态 |
| 调用与数据流 | 实际调用边、条件和重要参数，以及数据的生成、校验、处理、存取和输出；未解析关系单列 |
| 改修对象及方案 | 改修 ID、文件／处理位置、现状与问题、改修后行为、理由、优先级、调用、数据及其他功能影响、异常与测试 |
| 无影响对象 | 与本次有关但不需改修的对象、判定条件与依据 |
| 待确认事项 | 问题 ID、缺口、原因、受影响结论、确认人或资料位置 |
| 风险与复查 | 共通处理、DB 对既有批处理、IF 对外部系统、数据迁移、向后兼容及回归风险；实际复查和剩余工作 |

报告要解释“为什么影响、怎样改”，不是搜索结果的罗列。相关原文、代码与解释分开显示；详细依据可以展开或放在有明确索引的明细中，但不能以文件路径代替实际内容。

### 5. COBOL 新人解说：必须保留的内容

先从真实 Source 确认语言、方言、固定／自由格式和版本；不能因无法判定就声称标准 COBOL，也不能在未核实源码格式时套固定列号规则。目标较大时可分批解析并保存索引，最终界面和说明仍明确实际覆盖范围、版本与未解析部分。

1. **业务与结构。** 先说明程序做什么、何时启动、输入输出和业务目的，再说明四个 DIVISION、WORKING-STORAGE、段落／SECTION、PIC、层级号、MOVE／COMPUTE／ADD／IF／EVALUATE。首次出现的术语加简短说明；保留变量、段落和 SECTION 的实际名称。
2. **流程与数据。** 按实际执行顺序解释 PERFORM、PERFORM UNTIL／VARYING、CALL、GO TO、分支与循环。主要数据按“生成 → 修改 → 传递 → 输出”解释类型／位数和关键条件，说明异常与边界。
3. **控制标志表。** 列出重要标志实际名、用途、初值／VALUE、赋值位置、引用位置、各状态值如何改变处理。使用 88 级条件名时明确条件名与父变量、取值的关系。代码中必须突出重要控制标志与88级条件名，图中必须特别标记由标志控制的分支；不能仅凭名称猜其用途。
4. **调用与跳转。** 显示调用方／被调用方及返回或后续路径；PERFORM THRU 明确覆盖范围，CALL 区分外部程序，GO TO 按控制转移说明，不能画成普通调用返回。未提供的外部 Source 保持未解析，不声称已完整分析。
5. **说明顺序。** 功能概要 → 全体结构 → 执行流程 → 数据流 → 控制标志表 → 调用链图 → 注意点／异常／可读性风险 → 按优先级列出的改善建议。改善建议分别覆盖可读性、维护性、性能和安全性。建议与本次必要改修分开，不自动把 GO TO 改写等建议当作已验证可行的变更。

### 6. 自包含交互 HTML 与验证

需要新人阅读版时，生成一个无需构建、离线可打开的 HTML，CSS／JavaScript 内嵌，不依赖 CDN、外部 CSS／JS 或 Mermaid。解释、标签和注释采用本次选择的中文或日文，实际代码与名称保持原样。

- 在同一 HTML 中保存解说正文、实际目标 Source 全文、图、控制标志表和调用链图；长代码可折叠／导航，不能截断或只给外部 Source 链接。非目标或未取得的 Source 另外标明边界。
- Source 显示行号、语法高亮，每行有唯一 ID（如 `L42`），各段落／SECTION 有锚点。图节点关联真实行范围；同一报告包含多文件时 ID 加文件前缀避免重复。
- 主流程图以段落／SECTION 为单元，必要时在块内或展开图显示开始／结束、通常处理、IF／EVALUATE、循环、PERFORM、CALL、GO TO、输入输出和错误处理。控制流与数据流使用不同线型／颜色，图中使用实际名称。
- 点击图节点可平滑滚动到相应代码并暂时高亮，点击代码行可反向突出对应节点；调用链节点也可定位。图与代码可同时看见或方便切换，提供目录、返回总览和悬停时明确的可点击提示；确保暗色模式下可读，或提供明暗切换。
- 从真实 Source 抽查并核对所有生成的 ID 关联、行范围、节点与边、标志赋值／引用、THRU 范围和说明。实际打开 HTML 检查双向跳转、折叠／长文本、字符与代码显示，无法验证的功能注明。
- 静态 HTML 或图表生成成功不证明业务逻辑正确、动态路径全部覆盖或实际数据库行为已验证；交付时写明实际检查和剩余缺口。

### 7. 完成与交接

只有实际范围内的 DB／IF／画面／OL／BT／共通影响、调用两侧、数据流、影响判定及理由、改修方案、测试观点和证据都已核对，或有明确不适用理由，才按相应任务标准报告完成。待确认或未验证的结论保留状态，不能为凑齐章节虚构信息。

交付实际文件完整路径、版本、对象及记录数、已做检查、未解析／待确认内容和下一步。解说任务另报图与代码关联、导航及离线打开的验证结果。

## 日本語

### 1. 目的・入力・境界

今回の機能追加・仕様変更を基準に、実際の影響、理由、呼出しとデータの関係、改修対象、具体的な方針、試験観点を明らかにします。必要なら、初心者が読み、図とコードを相互に定位できるプログラム解説を作ります。

入力は少なくとも、今回の要求 ID・名称と具体的要求、対象 Source と確認できた版、現行設計、関連 DB／ファイル／IF／設定です。最初に資料の場所と実際の適用範囲を確認し、不明は要確認にします。例の `REQ-XXX`、クラス名、プログラム名、パスを実案件とみなしません。

標準の調査は資料を読み成果を保存する作業であり、業務 Source・設計・設定を変更しません。静的解析は業務プログラム実行や DB 実測ではありません。実行、DB 操作、実改修は現タスクで別途明示された範囲に従います。

### 2. 影響調査の順序と項目

「要求 → データ／DB → IF → 画面 → OL オンライン処理 → BT バッチ → Source の参照・更新位置 → 呼出し元／先 → データフロー → 共通部品 → 試験 → 改修判定」の順で調べます。範囲は実工程に合わせ、無関係な項目には不適用理由を残します。未確認のまま省略して影響なしとしません。

| 区分 | 具体的な確認内容 |
| --- | --- |
| DB | テーブル、カラム、PK／FK、INDEX、View、ストアド、DB 定義、Entity／DTO／Model。SELECT／INSERT／UPDATE／DELETE の対象・条件・データ影響。項目・表の参照／更新位置、JOIN／WHERE／ORDER BY／GROUP BY の関係 |
| IF／外部システム | 実在する API、REST／SOAP、メッセージ（Kafka 等）、ファイル連携、JSON／XML／CSV、Request／Response、Input／Output。項目名、型、桁、必須、既定値、送受信元、Mapping、Validation、エラー処理、データが通る経路 |
| 画面 | 実際の技術構成の HTML／JSP／Thymeleaf／JavaScript／TypeScript、Controller／Form／Validation。表示・入力項目、ボタン、エラー表示。項目の追加変更、検証、表示条件、Submit、Backend Request への影響 |
| OL オンライン機能 | 機能 ID・名称、Controller、Service、業務ロジック、DAO／Repository、SQL、共通処理。画面から Backend・DB までの実呼出し辺、引数、戻り値。ファイルの列挙だけで済ませない |
| BT バッチ | Job、Scheduler、Shell、Java Batch または実言語、SQL、Job 定義、入出力ファイル、DB、外部 IF。対象データを使用・更新・作成するバッチ、依存、実行順、異常処理 |
| 共通部品 | Utility、Common Service／DAO、共通 Validation／Mapper／Exception／Message／設定。親クラス、継承、Interface、共通 SQL／DTO／Mapper／設定を通る間接影響と他機能への二次影響 |
| 試験・運用 | 既存試験、データ形式、異常・ログ、互換性、移行の必要性、回帰範囲。リランに関係する場合は[リラン調査チェックリスト](../追加开发/重运行调查清单.md)と関連付ける |

図のフレームワーク名は説明例です。存在しない部品を作りません。実データフローは「入力 → 検証 → 業務処理 → DB／IF → 出力」をコード・設計・設定へ定位できるようにします。

### 3. 呼出し追跡・判定・改修方針

- 対象処理から呼出し元・先を追い、入口、条件、重要引数、戻り値、データの生成・変更・受渡し・出力、副作用を記録します。動的・間接関係を解決できなければ不足を明示します。
- 各候補を「影響あり」「影響なし」「要確認」に分けます。影響ありには改修内容・理由、影響なしには関連があるのに変更不要な理由、要確認には不足情報・影響する判断・確認先を示します。検索命中を実際の関係の代わりにしません。
- 設計と Source が違う場合、今回の要求、設計、実装、各根拠を示して指定基準で判断します。もっともらしい側を勝手に採用しません。
- 改修方針はファイル・関数／SECTION／段落位置、現状、問題、今回要求、変更後動作、理由、呼出し・データ・他機能影響、異常処理、試験方法を説明します。「あるプログラムを変更する」だけでは不十分です。
- 既存仕様・構成を尊重し、今回必要な変更を示します。追加改善は別にし、教材的な提案や過去 Diff を正式仕様にしません。
- 試験は条件成立／不成立、空値、境界、異常、既存機能の回帰、関連する DB／IF／バッチ影響を含め、期待結果の根拠も示します。

### 4. 影響報告と改修方針の構成

既存成果場所と安定 ID を使います。主 Markdown を一つにまとめても、工程の方式で `impact_analysis.md` と `modification_plan.md` に分けても構いません。必要なら `call_graph.md`、`data_flow.md` を付けます。番号・版・関係・結論を全ファイルで一致させます。

最低限、次を含めます。

| 部分 | 保存する内容 |
| --- | --- |
| 要求概要 | 要求 ID・名称、具体的内容、正式入力・版、目的・範囲 |
| 影響範囲の集計 | DB／IF／画面／OL／BT／共通部品の状態、対象数、概要。要確認を別集計し、影響なしへ含めない |
| 影響対象明細 | 記録 ID、区分、機能 ID、名称、絶対パス・具体位置、処理内容、影響・理由、改修要否、根拠・状態 |
| 呼出しとデータフロー | 実際の辺、条件、重要引数、データの生成・検証・処理・参照更新・出力。未解決関係は別記 |
| 改修対象と方針 | 改修 ID、ファイル・処理位置、現状・問題、変更後動作、理由、優先度、呼出し・データ・他機能影響、異常・試験 |
| 影響なしの対象 | 関連するが変更不要と判断した対象、成立条件・根拠 |
| 要確認事項 | 問題 ID、不足、理由、影響する結論、確認先または資料場所 |
| リスクと再点検 | 共通処理、DB と既存バッチ、IF と外部システム、データ移行、後方互換・回帰リスク。実際の再点検と残件 |

「なぜ影響し、どう変えるか」を説明し、検索結果の羅列にしません。原文・コード・解説を分けて示します。詳細を展開表示や索引付き明細に置けますが、実内容をパスだけで置き換えません。

### 5. COBOL 初心者向け解説で残す内容

実 Source で言語、方言、固定／自由形式、版を確認します。不明だから標準 COBOL とせず、形式未確認のまま固定の列規則を適用しません。大きい対象は分割解析して索引を残せますが、最終画面・説明には実際の範囲、版、未解析部分を明示します。

1. **業務と構造。** 何をするか、起動時機、入出力、業務目的を先に説明し、四つの DIVISION、WORKING-STORAGE、段落／SECTION、PIC、レベル番号、MOVE／COMPUTE／ADD／IF／EVALUATE を説明します。初出用語を短く補足し、変数・段落・SECTION の実名を保持します。
2. **制御とデータ。** 実行順に PERFORM、PERFORM UNTIL／VARYING、CALL、GO TO、分岐・ループを説明します。主要データを「生成 → 変更 → 受渡し → 出力」で追い、型・桁・重要条件、異常・境界も説明します。
3. **制御フラグ表。** 重要フラグの実名、役割、初期値／VALUE、代入位置、参照位置、状態値ごとの動作変化を示します。88 レベル条件名があれば、条件名・親変数・値の関係を明示します。コード内の重要フラグ・88レベル条件名を必ず強調し、フラグで制御する分岐も図で特別に表示します。名称だけで役割を推測しません。
4. **呼出しと分岐転移。** 呼出し元・先と復帰または後続経路を示します。PERFORM THRU は範囲、CALL は外部プログラムを区別し、GO TO は制御転移として説明し通常の呼出し復帰にしません。未提供の外部 Source を解析済みとしません。
5. **解説の順序。** 機能概要 → 全体構造 → 実行フロー → データフロー → フラグ表 → 呼出しチェーン図 → 注意点・異常・可読性リスク → 優先度付き改善提案とします。改善提案は可読性・保守性・性能・安全性の四つの観点を扱います。改善は今回の必須改修と分け、GO TO 置換等を検証済みの変更とみなしません。

### 6. 自己完結する対話 HTML と検証

初心者向け閲覧版が必要なら、ビルド不要でオフライン表示できる単一 HTML を作ります。CSS／JavaScript を内包し、CDN、外部 CSS／JS、Mermaid に依存しません。説明・ラベル・コメントは今回選択した中国語または日本語を使い、コードと実名は保持します。

- 同じ HTML に解説、実対象 Source の全文、図、フラグ表、呼出しチェーンを保存します。長いコードは折畳み・ナビゲーションを使えますが、省略・切断したり外部 Source リンクだけにしません。対象外・未取得 Source の境界は別記します。
- Source に行番号・構文強調を付け、各行に一意 ID（例 `L42`）、段落／SECTION にアンカーを付けます。図ノードを実際の行範囲へ対応付け、複数ファイルはファイル接頭辞で ID 重複を避けます。
- 主図を段落／SECTION 単位にし、必要ならブロック内や展開図で開始終了、通常処理、IF／EVALUATE、ループ、PERFORM、CALL、GO TO、入出力、エラー処理を示します。制御流とデータ流を線種・色で区別し、実名を使います。
- 図ノードから該当コードへ滑らかにスクロールして一時強調し、コード行から図ノードを逆強調します。呼出しチェーンも定位できます。図・コードを同時表示または容易に切替え、目次・総覧への復帰、ホバー時の明確なクリック可能表示を用意します。暗色モードでの可読性を確保するか、明暗切替えを提供します。
- 実 Source と照合し、生成した ID 対応、行範囲、ノード・辺、フラグ代入／参照、THRU 範囲、説明を点検します。実際に HTML を開き、双方向移動、折畳み・長文、文字・コード表示を確認し、未検証機能を示します。
- 静的 HTML・図の生成成功は、業務ロジックの正しさ、全動的経路、DB 動作の実証を意味しません。納品で実施した検証と不足を示します。
