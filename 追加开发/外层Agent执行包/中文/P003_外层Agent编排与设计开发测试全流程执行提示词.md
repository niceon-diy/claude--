请以资深系统架构师、AI 开发工程师和测试负责人标准，读取我的实际公司工程，**实现并接通一套由我自己的外层 Agent 管理的设计、开发、测试流程，并在具备资料和环境条件的真实范围内执行、检查和修正。**

这是执行任务。请完成必要的调查、方案、代码／配置、接口接入、测试及成果保存，不要只交分析报告、架构建议、提示词草稿或下一步计划。先查清当前步骤必要的接口，随即实现和验证；无需先完成整个 Framework 的全量研究才动手。

## 02｜持续执行规则：减少等待，保留真实边界

1. **检查 → 实施 → 验证 → 修正 → 下一项**连续推进。阶段完成后，满足前置条件便进入下一阶段，不以“请确认后继续”作为例行结尾。
2. 能从工程、代码、Manual、有效设计或已有记录查到的问题，先自行查证。目录命名“最新”、文件时间或 Agent 自述不足以认定版本、能力和完成状态。
3. 常规技术选择采用与工程一致、改动最小、可维护的方案，记录理由并执行；业务规则、想定、正式范围的关键缺口不得凭猜测补成事实。
4. 以案件／机能／设计项／Case／对象判断阻塞。单条 Case 缺想定，只暂缓该 Case 的判定；单个环境不可用，继续适配实现、离线验证、其他环境或明确对象。只有同一前置确实影响全部剩余任务，才停止依赖它的执行。
5. 每个可修复缺陷按证据定向修复，默认最多 3 轮；瞬时连接错误默认最多重试 2 次。项目有有效限制则沿用。超过上限记录原因、证据和恢复点，继续其他就绪任务，不无限调用和重复生成。次数上限不能作为跳过首次实际实现或验证的理由。
6. 断连、超时或退出码缺失时，先检查远端实际状态。结果不明的部署、DDL、数据导入和程序运行，不盲目重试。
7. 可并行调查、设计、生成数据和检查；写同一文件、改同一 DB 对象或使用互相影响的测试数据时串行。子任务使用独立输出位置，由外层合并并复核。
8. 每完成实质步骤或准备交接，保存状态、输入输出版本、证据、已采取的修正、未完成项和下一恢复点。上下文不足时写接续记录；新会话先核对真实文件和环境后继续，避免整套重跑。
9. 问题写文件之后，继续全部不依赖回答的就绪工作。用户未回答不构成批准，也不能自动关闭问票或将业务假设升级为确认规则。
10. 当所有就绪工作已经完成、仅剩实际阻塞，或遇到平台硬限制时，保存完整交接再汇报；不用空转等待来伪装持续工作。不要承诺脱离当前工具／会话仍会自动后台运行。

## 03｜先接上真实 Framework，不做无关重建

读取当前适用规则、Manual 和既有工作状态，确认 Framework 版本、实际语言、SDK、角色配置、运行器、工具及文件结构。沿一条有代表性的真实机能追踪：

`用户入口 → 参数／上下文 → Agent 选择 → 工具调用 → 实际产物 → 检查／失败处理 → 下一步`

将当前工作需要的组件逐项登记：

| 字段 | 必须查清 |
| --- | --- |
| 能力与类型 | 设计／开发／Case／数据／连接／部署／DB／执行／采集／比较；Agent、角色、脚本还是编排器 |
| 实际接口 | 入口文件、函数／命令／配置、版本、参数、返回对象及工作目录 |
| 输入输出 | 输入格式、实际读取的文件、产物位置、完成信号、错误和超时 |
| 复用结论 | 直接复用／调整配置／薄适配／确实缺失／尚未确认 |
| 证据 | 实际路径、符号／配置键、可定位原文、已有日志；静态可确认与真实运行分别标记 |
| 接入与验证 | 外层将怎样调用、补哪一小段、用什么样例核验 |

组件名没有 agent 也要按实际职责识别；存在配置不等于真实可达，存在日志文件不等于本轮执行成功。不要凭名字编造现有能力。

优先复用原入口、角色、模型调用、连接、数据、runner、采集、比较器及报告格式。保持既有 Framework 可继续独立运行，不为增加外层去整体改写或移动底层代码。若现有编排能加前后处理，直接扩展；若接口不兼容，写最小适配器。只有确实缺失或无法满足本次要求的能力才补实现。

不要先建设新向量库、长期记忆平台、复杂多 Agent 自由讨论或全量全局规则。历史知识使用工程现有文件／检索入口，并核对范围、版本、适用条件和本次差异。

## 04｜实际实现三类外层 Agent 和共同闭环

至少形成可调用的外层设计、外层开发、外层测试三个角色／模块，并提供统一运行及按阶段运行入口。共享一个简洁核心即可；角色数量、文件名、语言和目录沿用工程习惯。

每个外层必须真正完成：

1. **接收和预处理**：解析本次用户输入，核对完整性、版本及正式／参考用途，解析真实文件，准备底层 Agent 所需消息、结构化字段和附件。
2. **调用**：通过已经查实的接口调用既有 Agent，传入适配后的实参，保留调用编号、配置／版本、可复核的输入引用和输出位置。
3. **收集**：核对真实返回对象和落盘文件，保留底层原始成果，区分执行失败、输出缺失、格式错误及内容不足。
4. **检查**：先做可确定的格式、文件、ID、范围、引用、构建／测试检查，再做有正式依据的语义和覆盖检查。另起一个审查角色也不能代替独立依据。
5. **纠正**：将具体缺陷、依据、目标位置、期待修正及验收条件交回原 Agent；外层能据已确认资料直接补充的也可补充，但保留补充来源、前后差异及再次检查结果。
6. **交接**：只有有效且检查合格的产物版本交给下阶段；未确认项随产物明确传递。部分对象可交接时注明边界，不把整包失败当成所有对象不可推进。

实现形式可以是现有宿主支持的自定义 Agent 配置加可执行编排／检查代码，也可以是工程原有调用接口的封装。必须有真实入口、调用链及可运行实现；仅写三段角色提示词、仅改名转发或只交接口空壳不满足要求。

为每个外层建立简洁的输入输出约定，并实际校验关键字段：

- 输入：`task_id`、真实案件／机能、阶段、输入资料及版本／哈希、正式范围、参考依据、环境引用、上阶段有效产物、适用检查规则。
- 输出：实际状态、产物路径与版本／哈希、底层调用记录、检查项及证据、修正与重试记录、未确认问题 QID、下阶段可消费的有效产物。
- 状态至少能区分：待处理、运行中、已生成待检查、返工中、检查合格、部分完成、局部阻塞、失败及不适用。不适用必须有依据。
- 运行状态与业务结论分开。例如“工具退出 0”“已生成 Case”“程序已部署”“已执行”“比较通过”分别记录，不以一个布尔值概括。

所有外层检查均应可从保存的原始依据和实际成果复核，不要求或保存模型隐藏思维链。

## 05｜资料基准、追踪和版本管理

建立任务输入清单，区分本次正式要求、有效现行设计、当前 Source、用户 Matrix／固定想定、历史参考、调查推断及待确认资料。保留原件，不因转换、提取或补充覆盖原文。

关键定位使用真实文件、版本、章节／页码／工作表／单元格／行或代码符号。资料只有路径、尚未读取、无法访问和已经读取分别记录；不能把“文件存在”写成“本轮已传给 Agent”。按工程可用机制保存输入引用／哈希和实际传入记录，敏感正文留在公司允许位置。

贯穿以下关联，并支持从实际变更反查依据：

`正式要求 → 设计项 → 程序／DB Object与环境 → 实际变更 → Matrix行／Case → 执行批次 → 原始证据 → 比较结论`

沿用已有稳定 ID；没有时在本次范围分配，保留原用户编号，避免重命名导致对应关系丢失。不要用只有名称相似的记录自动合并对象。

采用已有版本管理和保存机制。修改前核对工作区已有差异；保存 Source 前后版、实际 Diff、构建标识、产物哈希、DDL／数据脚本和运行配置引用。程序经本轮改动后，必须重新构建或取得与改动匹配的有效编译产物，再更新测试批次；不得继续拿旧产物证明新 Source 正确。

公司已有管理台账时在其上更新并建立引用，避免另建互相矛盾的业务事实源。公开 Git 中只维护通用代码、模板和经过审核的脱敏内容；业务正文、真实路径、源码、Diff、DB 内容、测试数据、环境配置和问答原件按公司规则保存在内部。

## 06｜外层设计 Agent：把本次要求变成可实施设计

### 输入处理和底层调用

整理本次追加对应一览、有效现行设计、Source、外部设计、Object×环境、参考 Thema／Diff。确认历史资料的适用性，将本次真实值和规则与历史示例分开。调用既有基本设计／详细设计 Agent，并传入有效资料版本及本次重点。

参考 Thema 的发布模块一览用于反查候选漏项；候选是否属于本次应改范围，仍根据本次正式要求及实际用途判定。核实源码与发布生成物的映射，不能仅凭短名相同认定一致。

### 输出必须检查

- 业务目的、机能、正式要求、实际入口和改修范围是否完整；范围外和待确认项是否有依据。
- 按项目正式分类表达机能；若适用原“前台 PL → 前台 BL → batch”，沿用其含义及排序，不凭名称猜类别。
- 输入 → 关键处理／调用 → SQL／DB → 输出及上下游的数据流、字段来源和去向是否说清。
- 字段类型／长度、字节或字符语义、空值／默认值、有效值、条件、转换和派生是否有依据。
- 改哪些程序、具体处理位置、接口／文件、DB Object×环境，是否与追加一览及现行实现对应。
- 基本设计到详细处理、分支／异常、事务、日志及必要兼容性的关系是否可实施。
- 正常、边界、异常和回归要求，以及受入条件、独立想定来源和测试关联是否明确。
- 关键结论是否能回到正式输入；是否混入历史 Thema 的名称、值、条件或错误环境。

按缺陷定向补充或返工。已有正式规格足够的设计项继续开发；必须由用户决定的规格缺口保留 QID，仅阻塞相关设计项，不把未确定内容当正式规格推广。

交付有效基本／详细设计、改修对象和位置清单、字段流转、环境影响、受入条件与测试依据、设计检查和修正记录。

## 07｜外层开发 Agent：用既有开发能力实现并核对

将有效详细设计、追加范围、源码基准、参考 Diff、编码规范及构建方式适配后交给既有开发 Agent。逐项检查并执行：

1. 修改是否限定在本次已确认对象；既有用户工作和未归入任务的变更是否保留。
2. 实际 Source／Diff 是否实现设计中的字段、条件、异常及接口；保留项目实际语言的编码、换行、固定列等约束。
3. 双向核对：应改设计项是否落实；每个实际新增、删除和修改是否有本次依据，识别漏改、多改和错改。
4. 按工程真实命令构建／编译和必要静态检查，保存命令、配置引用、退出码、日志及产物；未运行明确标记。
5. 构建产物与本次 Source、依赖、参数及目标运行环境是否对应。已有编译产物可复用，但必须能证实对应关系；时间较新不足以证明。
6. 失败根据具体原因交回底层开发 Agent，或由外层据确认设计补充；复验原问题及直接关联影响。

交给测试的包至少包含实际 Source 版本、Diff、设计对应、编译产物、部署清单、DB／接口变化、构建证据及已知未确认项。编译通过与业务测试通过分别报告。

## 08｜外层测试 Agent：Matrix、固定 Case 与想定先形成有效基准

### 保留用户输入并适配现有生成器

读取我的原始 Matrix、固定 Case、想定、初期表和数据说明，保留版本、原行号／单元格及固定编号。先判断输入是测试观点 Matrix、已固定的执行 Case，还是二者混合。

- 已有固定 Case 直接纳入，不无故重新生成、重命名、删减条件或改写想定。
- 需要生成的部分交给既有测试／Case Agent；通过输入映射、上下文、模板及工具参数让其消费原输入，不要求用户为适配 Framework 重写整张 Matrix。
- 每个生成 Case 保留对应 Matrix 行／条件组合及正式依据。一行可对应多个 Case，按 Matrix 明确的组合／覆盖规则展开；不要擅自生成无边界的笛卡尔积。
- 额外发现的边界、异常和回归用例，另标“补充用例”并记录依据，与用户固定基准区分；不得借补充数量掩盖原 Matrix 漏项。
- 缺少的期待规则只能从有效正式要求／设计中有依据地补充；无法判断则登记 QID，相关项保留未确认，其他明确 Case 继续。

### 外层检查 Case

每条至少能确定：Case ID、Matrix 定位、要求／设计项、目标程序与步骤、前置条件、输入及数据准备、运行参数、想定值／判定规则及来源、应采集的证据、清理／恢复方法。

核对全部 Matrix 条件及固定 Case 的处理去向：已有有效 Case、已生成待检查、存在缺口、待确认、或有依据不适用。保留分母和明细，不悄悄删除难例或将未执行计为通过。

在实际运行前固定 Case、想定及比较规则版本。若原 Case 只是固定的输入，还须找到独立的想定依据；程序实际输出不能自动变成正确答案。开发者或比较器都不得通过修改想定、扩大忽略范围或放宽容差来掩盖失败。

## 09｜测试执行批次与环境准备顺序

先生成离线 Case、数据文件／SQL 和比较定义；实际数据导入在目标结构就绪后执行。测试流程为：

```text
用户 Matrix／固定 Case／想定
→ 外层解析、适配并调用既有 Case／数据能力
→ 外层检查覆盖及想定，固定有效版本
→ 复用既有连接，读取个人开发环境现状
→ 按依赖计划同步编译产物、Oracle 结构及必要依赖
→ 核验实际装载程序、实际 DB 结构
→ 装载初期表和本批 Case 数据，检查前置状态
→ 环境与数据 READY
→ 既有 runner 实际跑程序
→ 既有能力采集、比较和报告
→ 外层复核、分类修复、关联复测
→ 清理／保留现场并交接
```

为每次真实执行生成唯一 `run_id`，保存批次清单。内容至少包括：

| 类别 | 必须绑定的内容 |
| --- | --- |
| 范围 | 案件、机能、Case ID、Matrix版本及定位、目标环境 |
| 程序 | Source版本／哈希、构建标识、编译产物与哈希、依赖和运行入口 |
| 数据库 | Oracle服务及个人用户／schema引用、Object范围、目标定义版本、迁移脚本ID／哈希 |
| 数据 | 初期表基准、数据文件／SQL版本、装载顺序、数据批次和清理范围 |
| 判定 | Case版本、想定原件／规则版本、采集范围、比较规范 |
| 环境与调用 | 目录／配置引用、既有Agent／工具版本、部署／执行参数、状态和证据索引 |

没有 Source commit 时可以记录真实文件哈希及构建出处；对应关系无法证明的保留未确认。不要在普通清单中保存口令。测试过程期间版本变化应建立新批次并判断受影响范围，不能混用不同程序／DB／想定版本的证据。

## 10｜Oracle 表结构更新：从实际结构迁移到目标定义

优先复用既有 DB 连接、元数据读取、DDL 执行和迁移记录能力。缺口补为可被外层调用的普通模块，不另造一个自由生成并直接执行任意 SQL 的流程。

1. **确认对象身份。** 核对实际 Oracle 版本、连接服务、用户、目标 schema、对象 owner、同义词及程序真实连接配置。个人开发用户隔离不自动证明所有表都属于个人范围；识别共享对象并限定操作。
2. **取得实际状态。** 读取本次涉及的列、类型、长度与字节／字符语义、精度、空值、默认值、约束、索引及相关依赖，保存结构快照和已应用迁移记录。可用数据字典、`DBMS_METADATA` 或工程现有方式；不要只读历史版本号推定实际一致。
3. **确定目标。** 从正式最新版定义及本次设计取得目标结构；定义是 Excel／文档时保留准确定位和解析缺口。定义中的示例、物理存储差异及环境值如何处理必须有项目依据。
4. **生成差分迁移。** 形成 actual → target 的明确增量脚本及对象清单，核对已有数据、NULL／必填、类型转换、字段缩短、默认值、必要回填、约束及依赖影响。完整建表 SQL 是目标定义时，不直接把它当已有库升级脚本运行。
5. **建立实施计划。** 程序、DDL、数据回填、依赖重建／编译和装载的先后顺序由兼容性与工程实际依赖决定，不统一假设 DB 永远先于程序或相反。保存前置条件、脚本哈希、备份／恢复条件及后置检查。
6. **按已确认范围执行。** 对确认的个人开发对象及已有依据、不会造成不可恢复损失的必要迁移，完成前置检查后直接推进。删表／删列、数据丢失、归属不明或超出授权的修改记录 QID；其余可执行步骤继续。
7. **核验实际结果。** 每步记录命令、结果和已应用状态，再查询真实结构、必要数据及受影响依赖。脚本退出成功不代替 actual 与 target 的核验。

已应用且核验一致的迁移不重复执行；同一迁移 ID 对应不同脚本哈希时记录冲突，查清原因和实际结构后处理，不能覆盖历史记录、直接视为已应用或盲目重放。

Oracle 常规结构 DDL 会隐式提交。DDL 与测试数据 DML 分开处理；不要依赖最后一次 `ROLLBACK` 恢复整批结构，也不要让 DDL 意外提交尚未核对的测试数据事务。保留所需的程序前版、结构及必要数据恢复条件；按平台特性使用明确的恢复或前滚修复方案。失败后先识别已生效部分，再决定续跑。

无实际 DB 访问时完成元数据适配、差分计划、脚本和离线校验，远端应用标“未执行／待验证”，不以示例库结果冒充个人开发库已更新。

## 11｜FTP 放置编译产物：核对实际生效版本

先调查现有 FW 是否已经有传送、部署和装载步骤；有则由外层调用并补检查。没有才补 FTP 适配。协议、主机、用户、路径及配置来自公司已有有效设置，不凭“FTP”一词推断具体服务器或环境。

- 确认本次产物、Source／构建对应、目标平台、依赖、目录及实际装载路径。测试新改修前须取得对应的新编译产物。
- 保存现有程序版本及需要的恢复资料；按平台支持的机制临时上传、核验、切换。编译二进制使用二进制传输，避免文本模式改写字节。
- 上传后用远端校验值或回读比较确认内容一致，记录部署清单。只有文件大小或时间一致时，不能据此声称内容完全一致。
- 核对权限、相关配置／依赖，以及是否需要重新启动、重新装载、链接或其他平台步骤；按现有工程方法执行。
- 从真实运行入口／装载路径和平台可提供的版本或构建标识验证实际使用的程序。上传成功、部署完成和运行生效分别记录。
- FTP 负责传输；实际跑程序、等待结束及取退出码，需要查清并使用既有 FW 的运行通道。不要假定 FTP 本身能够执行远端程序。
- 断连后先查看远端临时文件、目标文件、校验及切换状态，再续跑。恢复状态不明时不要反复覆盖并继续测试。

## 12｜初期表、测试数据和 READY 检查

将用户提供的初期表内容、共通基准数据、Case 专用数据和部分测试数据想定分开登记，保留来源、版本、键范围和适用 Case。初期表的项目含义从说明和现有流程确认，不擅自理解成整个 schema 全量重置。

尽量使用既有数据 Agent／生成器、导入和清理机制，并由外层检查：

- 初期值、代码值、主外键、关联表、触发条件及装载顺序是否满足本次 Case。
- 有预先指定数据时保留原值；需生成的字段按有效规则生成，记录必要的时间、序列、随机种子或冻结方法，保证结果可解释和可复现。
- 共通初始化与每条 Case 的准备／清理分开。互相依赖的 Case 明确顺序；不独立的数据不并发执行。
- 实际导入前确认目标结构已就绪；导入后检查行数、键值及关键前置值，事务按既有方法明确提交／回滚。
- 数据清理限定为本次允许的数据键／批次和对象，不默认全表 DELETE、TRUNCATE 或重建。保留测试前现场和恢复／保留说明。
- 数据脚本已生成、数据已导入和数据满足前提分别记录。期待的初期内容与实际装载结果不一致时先修准备步骤。

下列项均有证据才将对应测试批次标为 `READY`：目标环境身份正确；实际程序符合批次；相关 Oracle 结构符合目标；依赖和运行通道可用；初期表与 Case 数据符合前提；想定及比较规则有效；无影响本批运行的未解决环境差异。

`READY` 是正式执行前的程序化检查点，不是新的人工逐阶段批准点。失败则修复或登记局部阻塞，并继续其他可做的工作。

每条 Case 或有顺序依赖的 Case 组运行前，都重新核对其前置数据及当前程序／结构状态；前一 Case 已产生的变化按有效定义重置或保留。批次开始时检查一次不能代替逐 Case 的前置核验。

正式比较批次只纳入想定和其他前提均有效的 Case。缺想定的 Case 单独保留；只有运行范围、数据影响、其他前提和仅采集目的都明确时，才可单独执行采集，并标“仅采集、未判定”，不计通过，也不阻塞其余就绪 Case。

## 13｜运行、采集、比较与外层复核

### 实际运行和取结果

由外层传入已经确认的 Case、程序入口、参数、目录、个人环境及数据批次，调用既有 runner。保存开始／结束、作业或进程标识、命令／参数引用、退出码、超时、原始日志和最终状态。

按 Case 要求采集必要的返回值、日志、文件、DB 行及前后状态，保持 Case 与证据一一可追踪。保存原始证据，解析／规范化结果另外存放。采集失败、程序执行失败和比较不一致分开记录。涉及触发器、异步作业或后台处理时按工程条件判断完成，不只凭提交成功就判整个程序完成。

每条 Case 的原始证据应在下一条 Case 的初始化、清理或输出覆盖之前完成采集并保存到独立位置。需要保留连续场景状态时也先保存当前检查点，防止批量运行后只剩最后一条 Case 的状态。

### 复用既有比较能力

将独立想定与实际结果适配给既有比较器，沿用项目有效的排序、NULL／空值、编码、日期／时区、数值精度、容差、动态字段及忽略项规则。Oracle／项目对空串等实际语义按正式要求处理，不自行泛化；比较规则缺失且影响结论时列 QID。

保存想定、实际、差异位置和判定依据。不得为了通过而自动改想定、忽略新增差异、放宽容差、跳过 Case 或只比较容易通过的字段。

### 外层最终检查

核对 Matrix 覆盖、固定 Case 保留、输入数据、实际程序／DB版本、执行完成状态、采集完整性及比较逻辑。必要时对代表性的结果直接复核原文件／查询，避免只相信原 Agent 的总结。

每条 Case 区分：待确认、已生成待检查、就绪、未运行、运行中、执行失败、中断／结果不明、比较不一致、比较通过及有依据不适用。报告中分别列分母及各类数量，未执行和未确认不算通过。

## 14｜返工、外层补充和恢复

每个缺陷记录：发现阶段、对象／Case、实际表现、想定或规则、原始证据、原因类别、修正责任模块、修正差异及复验结果。

| 原因 | 处理方式 |
| --- | --- |
| 设计或业务规格缺口／冲突 | 依据可确认部分修正；必须业务决定的写 QID，仅阻塞相关项 |
| Source 实现错误 | 反馈具体缺陷给外层开发及既有开发 Agent，修复、重构建、更新批次并复测 |
| Case 或测试数据错误 | 按独立正式依据修正，记录版本和影响；保留原固定输入及更改原因 |
| 程序部署／DB结构／依赖不一致 | 修环境准备和核验，重新达到 READY，再执行受影响 Case |
| 运行通道／环境故障 | 按有限重试与恢复规则处理，未执行不算业务通过或业务实现失败 |
| 采集／解析／比较错误 | 保留原证据，修工具和规则，重新采集或比较；判断是否确实需要重跑 |

有依据的外层补充可以提高完整性，但不能凭空补业务规格、修改用户固定想定或隐藏原始缺陷。所有补充保留来源、作者／执行模块、版本和重新检查结果。

再次执行前核对已发生的数据变化、重复处理、已生成文件和已应用 DDL，明确最小重跑单元及恢复方法。程序修改后重新部署对应产物；仅比较器修正且原始证据充分时可复用有效证据，不机械全量重跑。所有复用必须确认版本和状态仍有效。

每轮修复需改善明确的未通过项；重复失败按第02节保存局部阻塞，不把修复循环变成改变期待值的循环。

## 15｜集中问答文件：只问真正缺的，回答后自动闭环

在公司允许的成果目录维护**一份权威问答文件**，优先沿用工程已有问答格式，没有时用 `待回答问题.md`。不要将同一问题散落聊天、多个草稿或公共 GitHub Issue。其他成果通过稳定 QID 引用。已有权威文件时，将本包预核实清单去重合并，保留 QID 映射；不要另开第二份文件，也不要把8项预核实问题一律标为待用户回答。

每项问题至少包含以下字段，可直接采用此模板：

```text
QID：
状态：待调查／已查明无需回答／待用户回答／已回答待核验／已采纳待更新／已更新待验证／已验证关闭
问题：一句话说明需要提供或决定什么
已查内容：实际资料、版本、定位、查找范围、结论
影响对象：案件／机能／设计项／程序／DB Object／Case
是否阻塞：只写实际受影响的步骤；可继续部分另列
候选方案与建议：依据、影响和推荐；可自决问题直接记录决定而不索要批准
暂行处理：继续哪些工作；哪些内容保持未确认
用户回答：留空，保留之后填写的原文
回答者与时间／适用范围：未知不填造
采纳结果：核验后的解释、关联变更、冲突或需追问之处
验证与关闭：受影响版本、真实复验结果和证据
```

沿用权威问答文件已有的等价状态并记录映射，不并行维护两套状态。先去重和查证，再写确实需要用户回答的缺口。能凭有效工程事实解决的，记录依据标“已查明无需回答”，不要求用户重复确认。不得将“所有可能风险”堆成问卷，问题必须对应具体缺口和实际影响。

用户之后在文件里批量回答时：读取并保留原回答，核对与当前资料、业务权限及适用范围是否一致，更新关联设计、Source、数据、Case、环境计划或比较规则，执行必要复验，再记录关闭。发生冲突时留证据并提出针对性追问；回答不能直接等同所有操作已获授权或所有验证已通过。

将一条可直接发送的续接指令保存在交接文件：

“读取本工程本次外层 Agent 的运行记录和权威问答文件，核验我的新增回答，更新受影响成果并复验，从最小恢复点继续所有就绪任务；剩余问题仍集中写文件，不逐阶段等待。”

## 16｜交付结构、验证和完成标准

沿用工程既有目录，以下只是没有现成约定时的建议，实际采用后给出真实入口；不要为满足目录示意创建没有内容的空成果。

```text
外层Agent/                        # 实际实现，或工程原生Agent／workflow目录
  统一入口、三个角色、适配层、检查与状态管理
本次运行/<run_id>/
  输入索引与版本记录
  Framework复用与接入清单
  设计与开发成果及检查／实际Diff
  测试基准、Case、初期表／数据计划
  环境前态、部署／迁移／导入记录
  原始执行与采集证据、想定与差异、结果汇总
  进度与接续说明
权威问答文件                      # 在工程既有位置维护一份，运行记录引用它
```

### 验证实施本身

先运行工程规定的必要检查。对新增外层和适配逻辑，验证真正可能出错的分支：输入缺失／版本冲突、原 Agent 产物不完整、返工成功与超限、工具失败、结果不明后的恢复，以及想定未被实际输出覆盖。优先复用既有测试；新增检查应检验行为，不只镜像实现或确认文件存在。

离线／虚构夹具可用来验证接口和控制逻辑，但必须与真实公司 Case 隔离标注。它们不能证明远端已部署、Oracle已更新或业务测试通过。

### 跑通真实链路后扩展

从已有输入自动选择一个资料明确、有代表性的真实机能／Case，完成外层输入 → 既有 Agent → 外层检查 → 部署及Oracle／数据准备 → 实际运行 → 采集与比较。确认链路有效后，**自动继续处理其余已确认、可复用且条件就绪的范围**，无需为“试点已跑通”再次等待我允许扩展。仍不明确的业务规则只在明确范围内暂缓。

### 按层次验收

| 层次 | 合格时必须看到的真实成果 |
| --- | --- |
| 外层实现 | 三类外层有实际入口、输入处理、既有Agent调用、输出检查、补充／返工及状态恢复 |
| Framework复用 | 清单中每个结论有实际接口和证据；可以复用的沿用，新增部分有缺口依据 |
| 设计／开发 | 有效输入、真实设计、实际改修、构建／检查及双向追踪；未实施项单列 |
| 测试基准 | 原Matrix和固定Case完整保留，有覆盖明细、独立想定及明确比较规则 |
| 环境整备 | 指定个人环境的程序实际生效，Oracle目标结构、初期表和测试数据均经核验 |
| 测试执行 | 每条已执行Case可追至批次、运行、原始结果、想定和比较证据 |
| 闭环 | 缺陷修正并复验；问题集中、可批量回答；交接可从真实状态继续 |

所有层次分别列“实现完成／离线已验证／远端已应用／实际已运行／比较通过／未执行／部分完成／阻塞”。未取得公司访问、资料或环境条件时，完成全部仍可做的实现、适配、脚本及离线检查，剩余明确标未验证；不要宣称端到端完成，也不要因此退回只交建议。
