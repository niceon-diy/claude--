## 00｜プロンプト開始：今回、実際に完了させる作業

経験豊富なシステムアーキテクト、AI開発エンジニア、テスト責任者として、私の社内の実際のプロジェクトを読み取り、**私自身の外側Agentが管理する設計・開発・テストの一連の流れを実装・接続し、資料と環境の条件が整っている実際の範囲で、実行・検査・修正してください。**

これは実行タスクです。必要な調査、方針策定、コード／設定、インターフェース接続、テスト、成果物の保存を完了してください。分析報告、構成案、プロンプト草案、次の作業計画の提出だけで終えないでください。現在のステップに必要なインターフェースを確認したら、実装と検証へ進んでください。着手前にFramework全体の調査を完了させる必要はありません。

私の中心的な要求は次のとおりです。

1. **ユーザーの入力は、最初に私の外側Agentが受け取ります。** 外側Agentは根拠のあるコンテキストを整理・補足し、既存Agentに適した入力を作成して呼び出します。出力を受け取った後は実際の成果物を検査し、不足があれば対象を絞って修正を依頼するか、正式資料に基づいて補足し、再検査します。
2. 設計と開発の両方でこの方式を採用します。基本設計と詳細設計は、一つの外側設計Agent内の異なるステップとしても構いません。実際のFrameworkのインターフェースに合わせて接続してください。
3. テストでは、既存FrameworkのAgent、環境接続、データ準備、実行、結果収集、比較、レポート機能を優先して再利用します。既存の制御フローで要求を満たせる場合は、それも再利用します。実際の不足箇所だけに、外側のルール、インターフェース適合処理、必要なステップを追加してください。
4. テストの重要な入力は、私が提供する**Matrix、既存の固定Case、期待結果／判定ルール（想定）**です。Caseの生成と検査、初期テーブル（初期表）とテストデータの準備、プログラム配置、Oracleテーブル構造の更新、実際の実行、結果取得、期待結果との比較を含めてください。
5. 通常の実装上の選択や各工程の終了ごとに、私の確認を繰り返し待たないでください。自分で資料を調べ、実行・検査・修正してください。私の業務判断、追加資料、権限が本当に必要な事項は、一つの質問・回答ファイルに集約し、その事項に依存するステップだけを保留して、他の作業を続けてください。
6. 最終的に、繰り返し利用できる実際の入口、実装、実成果を受け取りたいと考えています。完了した内容、実行証拠のある内容、未実行の内容、そして私がまとめて回答した後にどう再開するかを明確にしてください。

### 今回、継続して実施してよい作業

本指示は、確認できた社内プロジェクトおよび個人用開発／テスト範囲において、本タスクに必要な外側Agent、アダプター、設定、実行記録、成果物を作成・変更すること、有効な要求に従って設計とSource改修を行うこと、既存Agentとツールを呼び出すこと、ビルド・配置・テストを実行することを許可します。また、今回の個人開発範囲に属すると確認したOracleオブジェクトについて、必要かつ根拠のある増分更新と、範囲を限定したデータ準備を実施してよいものとします。許可済みで範囲が明確、かつ前提条件を満たす通常のステップは、そのまま進めてください。

変更前に現状と差分を保存し、他の既存作業を保護してください。有効なプロジェクト制約、実際の権限、プラットフォームの必須承認は引き続き適用されます。本番環境、他ユーザー／共有オブジェクト、アクセス権の拡大、認証情報の変更、範囲不明の操作、データを復元不能に失う操作は、本指示によって許可されたと推定しないでください。実際に該当する場合は、具体的な操作、根拠、局所的な停止範囲を質問・回答ファイルに記録し、対応する計画、スクリプト、検査、および影響を受けない作業を先に完了してください。

本タスクは、権限検査の無効化、プラットフォーム承認の回避、他者アカウントの使用、グローバルルールの変更、社内情報の公開リポジトリへの送信を要求しません。認証には会社が許可した既存の設定／認証情報の仕組みを使用し、通常のログや質問・回答にはパスワードやトークンを記録しないでください。

**本実行指示は、過去のタスク段階だけに属する「読み取り専用調査、分析のみで実装しない、サンプル提出後に待機、回答後に再確認、通常の各工程ごとの承認待ち」などの要求を置き換えます。** 過去の段階の制限を、本タスク全体の停止条件として扱わないでください。会社の組織ルール、現在有効なプロジェクト制約、実際のアクセス権、プラットフォームの必須承認、本指示で許可していない操作の制限は引き続き守ってください。これを理由に回避してはいけません。実際の衝突は、具体的な出典と影響する操作を記録し、他の実行可能な作業は続けてください。

## 02｜継続実行のルール：待機を減らし、実際の境界を守る

1. **検査 → 実施 → 検証 → 修正 → 次の項目**を連続して進めてください。工程が完了し、次の前提条件を満たしたら進み、通常の締めくくりとして「確認後に続けます」としないでください。
2. プロジェクト、コード、Manual、有効な設計、既存記録から分かることは先に自分で確認してください。「最新」というディレクトリ名、ファイル時刻、Agentの自己申告だけで、バージョン、機能、完了を認定しないでください。
3. 通常の技術判断は、プロジェクトに沿った変更量の少ない保守可能な方式を選び、理由を記録して実施してください。業務ルール、期待結果、正式範囲に関する重要な不足を、推測で事実として補ってはいけません。
4. 案件／機能／設計項目／Case／オブジェクト単位で停止を判断してください。一つのCaseに期待結果がなければ、そのCaseの判定だけを保留します。一つの環境が利用できなければ、適合処理の実装、オフライン検証、他環境や明確な対象を進めてください。同じ前提の不足が本当に残り全体に影響する場合だけ、それに依存する実行を止めてください。
5. 修正可能な欠陥は根拠に基づいて対象を絞り、既定では最大3回の修正反復とします。一時的な接続エラーの再試行は、既定で最大2回です。有効なプロジェクト制限があればそれに従ってください。上限後は原因、証拠、再開点を保存し、他の準備済みタスクを続けてください。無制限の呼び出しや再生成を行わず、回数上限を初回の実装・検証を省く理由にもしないでください。
6. 切断、タイムアウト、終了コード不明の場合は、先にリモートの実際の状態を確認してください。結果不明の配置、DDL、データ投入、プログラム実行を、状態未確認のまま再試行しないでください。
7. 調査、設計、データ生成、検査は並行化できます。同じファイルへの書き込み、同じDBオブジェクトの変更、互いに影響するテストデータの利用は直列化してください。サブタスクは別の出力先を使い、外側Agentが統合して再検査してください。
8. 実質的なステップが終わった時と引き継ぎ前に、状態、入出力バージョン、証拠、修正内容、未完了項目、次の再開点を保存してください。コンテキストが不足する場合は、引き継ぎ・再開用の記録を残し、新しいセッションでは実ファイルと環境を確認してから再開してください。一式の無条件な再実行を避けてください。
9. 質問をファイルに書いた後は、回答に依存しない実行可能な作業をすべて続けてください。未回答を承認と扱ったり、質問を自動で閉じたり、業務上の仮定を確認済みルールに変更したりしてはいけません。
10. 実行可能な作業がすべて完了し、実際の阻害要因だけが残った場合、またはプラットフォームの上限に達した場合は、完全な引き継ぎを保存して報告してください。空の待機で継続作業を装わず、現在のツール／セッションの外でも自動でバックグラウンド実行が続くと約束しないでください。

`ユーザー入口 → 引数／コンテキスト → Agent選択 → ツール呼び出し → 実成果物 → 検査／失敗処理 → 次のステップ`

現在の作業に必要な構成要素を項目ごとに登録してください。

| フィールド | 必ず確認する内容 |
| --- | --- |
| 機能と種類 | 設計／開発／Case／データ／接続／配置／DB／実行／収集／比較。Agent、役割、スクリプト、制御処理のいずれか |

構成要素名にagentがなくても実際の責務で識別してください。設定の存在は実際に到達可能なことと同じではなく、ログファイルの存在も今回の実行成功を意味しません。名前から既存機能を創作しないでください。

元の入口、役割、モデル呼び出し、接続、データ、runner、収集、比較器、レポート形式を優先して再利用してください。既存Frameworkが引き続き単独でも動く状態を保ち、外側を追加するために下位コード全体を書き直したり移動したりしないでください。既存制御に前処理・後処理を追加できれば拡張し、インターフェースが合わなければ最小アダプターを書いてください。実際に欠けている、または今回の要求を満たせない機能だけを補ってください。

新しいベクトルDB、長期記憶基盤、複雑な複数Agentの自由討論、全体のグローバルルールを先に作らないでください。過去知識にはプロジェクトの既存ファイル／検索入口を使い、範囲、版、適用条件、今回との差異を確認してください。

## 04｜三種類の外側Agentと共通の改善ループを実装する

少なくとも、呼び出し可能な外側設計Agent、外側開発Agent、外側テストAgentの三つの役割／モジュールを作り、統一実行と工程別実行の入口を提供してください。簡潔な共通コアを共有して構いません。役割数、ファイル名、言語、ディレクトリはプロジェクトの慣行に合わせてください。

各外側Agentは、次を実際に行う必要があります。

1. **受付と前処理**：今回の入力を解析し、完全性、バージョン、正式資料／参考資料としての用途を確認します。実ファイルを読み取り、下位Agentに必要なメッセージ、構造化フィールド、添付を準備します。
2. **呼び出し**：確認済みインターフェースで既存Agentを呼び出し、適合済みの実引数を渡します。呼び出し番号、設定／版、検証可能な入力参照、出力先を記録します。
3. **収集**：実際の戻り値と保存済みファイルを確認し、下位の原成果を保持します。実行失敗、出力欠落、形式不正、内容不足を区別します。
4. **検査**：まず確定的に検査できる形式、ファイル、ID、範囲、参照、ビルド／テストを確認し、次に正式な根拠に基づく意味と網羅性を検査します。別のレビュー役を起動することは、独立した根拠の代わりにはなりません。
5. **是正**：具体的な欠陥、根拠、対象位置、必要な修正、受入条件を元のAgentへ返します。外側が確認済み資料から直接補足できる場合は補足して構いませんが、出典、前後差分、再検査結果を保存します。
6. **引き渡し**：有効かつ検査合格の成果物バージョンだけを次工程へ渡し、未確認事項は明示して添付します。一部対象だけ引き渡せる場合は境界を示し、一式の失敗をすべての対象が進められない理由にしないでください。

実装は、既存実行基盤が対応するカスタムAgent設定と実行可能な制御／検査コードでも、プロジェクトの既存呼び出しインターフェースのラッパーでも構いません。実際の入口、呼び出し経路、動く実装が必要です。役割プロンプトを三つ書くだけ、名前を変えて転送するだけ、空のインターフェースを提出するだけでは要件を満たしません。

各外側Agentに簡潔な入出力契約を定義し、主要フィールドを実際に検証してください。

- 入力：`task_id`、実案件／機能、工程、入力資料と版／ハッシュ、正式範囲、参考根拠、環境参照、前工程の有効成果、適用する検査ルール。
- 出力：実際の状態、成果物パスと版／ハッシュ、下位呼び出し記録、検査項目と証拠、修正・再試行記録、未確認事項のQID、次工程が利用できる有効成果。
- 状態は少なくとも、未処理、実行中、生成済み検査待ち、修正中、検査合格、一部完了、局所的保留、失敗、適用対象外を区別します。適用対象外には根拠が必要です。
- 実行状態と業務上の結論を分けます。例えば「ツール終了コード0」「Case生成済み」「プログラム配置済み」「実行済み」「比較合格」を別々に記録し、一つの真偽値でまとめないでください。

すべての外側検査は、保存した原根拠と実成果から再確認できるようにしてください。モデルの隠れた思考過程を要求したり保存したりしないでください。

## 05｜資料の基準、追跡、バージョン管理

タスク入力一覧を作り、今回の正式要求、有効な現行設計、現行Source、ユーザーのMatrix／固定期待結果、過去参考、調査上の推論、未確認資料を区別してください。原本を保持し、変換、抽出、補足で上書きしないでください。

重要な根拠は、実ファイル、版、章／ページ／ワークシート／セル／行、またはコードのシンボルで特定してください。パスのみ確認、未読、アクセス不可、読取済みを区別し、「ファイルが存在する」を「今回Agentへ渡した」と書き換えないでください。利用可能な仕組みで入力参照／ハッシュと実際の引き渡し記録を保存し、機密本文は会社が許可した場所に保持してください。

以下の関連を通して保持し、実変更から根拠への逆引きも可能にしてください。

`正式要求 → 設計項目 → プログラム／DB Objectと環境 → 実変更 → Matrix行／Case → 実行バッチ → 原証拠 → 比較結果`

既存の安定したIDを継続使用してください。なければ今回の範囲で採番し、ユーザーの元番号を保持して、改名による対応関係の消失を防いでください。名前が似ているだけの対象を自動統合しないでください。

既存のバージョン管理と保存方式を使用してください。変更前にワークスペースの既存差分を確認し、Source変更前後版、実際のDiff、ビルド識別子、成果物ハッシュ、DDL／データスクリプト、実行設定の参照を保存します。今回プログラムを変更した後は、必ず再ビルドするか、変更に一致する有効なコンパイル済み成果物を取得して、テストバッチを更新してください。旧成果物を使って新Sourceの正しさを証明してはいけません。

社内に既存管理台帳がある場合は、それを更新して参照を関連付け、矛盾する業務上の事実の管理元を別に作らないでください。公開Gitには汎用コード、テンプレート、確認済みの匿名化内容だけを保存し、業務本文、実パス、Source、Diff、DB内容、テストデータ、環境設定、質問・回答の原本は会社規則に従って社内に保持してください。

## 06｜外側設計Agent：今回の要求を実施可能な設計にする

### 入力処理と下位Agentの呼び出し

今回の追加対応一覧、有効な現行設計、Source、外部設計、Object×環境、参照Thema／Diffを整理する。過去資料の適用可否を確認し、今回の実際の値とルールを過去の例から区別する。既存の基本設計／詳細設計Agentを呼び出し、有効な資料の版と今回の重点事項を渡す。

参照Themaのリリースモジュール一覧は、漏れの候補を逆方向から確認するために使う。候補が今回の改修対象に含まれるかどうかは、今回の正式要求と実際の用途に基づいて判定する。ソースコードとリリース生成物の対応を確認し、短い名前が同じという理由だけで同一と判断しない。

### 出力で必ず確認する事項

- 業務目的、機能、正式要求、実際の入口、改修範囲が揃っているか。範囲外と未確認事項に根拠があるか。
- プロジェクトの正式な分類で機能を表現しているか。従来の「前台 PL → 前台 BL → batch」が適用される場合は、プロジェクト上の正式な意味と順序を引き継ぎ、名前から分類を推測しない。
- 入力 → 主要な処理／呼び出し → SQL／DB → 出力、および上流・下流のデータフロー、フィールドの出所と行き先が明確か。
- フィールドの型／長さ、バイト単位か文字単位かの意味、NULL／デフォルト値、有効値、条件、変換、派生に根拠があるか。
- 改修するプログラム、具体的な処理箇所、インターフェース／ファイル、DB Object×環境が、追加対応一覧と現行実装に対応しているか。
- 基本設計から詳細処理、分岐／例外、トランザクション、ログ、必要な互換性へのつながりが、実施可能な内容になっているか。
- 正常、境界、異常、回帰の要求、受入条件、独立した期待結果の出所、テストとの対応が明確か。
- 重要な結論を正式入力までたどれるか。過去Themaの名称、値、条件、誤った環境が混入していないか。

不備に応じて対象を絞り、補足または手戻り対応を行う。正式仕様が十分に揃っている設計項目は開発を続ける。ユーザーの決定が必要な仕様不足はQIDを残し、関連する設計項目だけを保留する。未確定の内容を正式仕様として他の対象に展開しない。

有効な基本／詳細設計、改修対象と箇所の一覧、フィールドの流れ、環境への影響、受入条件とテスト根拠、設計確認と修正の記録を引き渡す。

## 07｜外側開発Agent：既存の開発能力で実装し、照合する

有効な詳細設計、追加範囲、ソースコードの基準版、参照Diff、コーディング規約、ビルド方法を適合させたうえで、既存の開発Agentに渡す。次を項目ごとに確認し、実行する。

1. 変更が今回確認済みの対象に限定されているか。ユーザーの既存作業と、本タスクに含まれない変更が保護されているか。
2. 実際のSource／Diffが、設計のフィールド、条件、例外、インターフェースを実装しているか。プロジェクトで実際に使用する言語の文字コード、改行、固定桁などの制約を維持する。
3. 双方向で照合する。改修すべき設計項目が実装されているか。実際の追加、削除、変更のそれぞれに今回の根拠があるか。改修漏れ、余分な改修、誤改修を特定する。
4. 工程の実際のコマンドでビルド／コンパイルと必要な静的チェックを実行し、コマンド、設定の参照先、終了コード、ログ、生成物を保存する。未実行は明示する。
5. ビルド生成物が、今回のSource、依存関係、パラメーター、対象実行環境に対応しているか。既存のコンパイル済み生成物は再利用できるが、対応関係を証明できなければならない。更新日時が新しいだけでは証明にならない。
6. 失敗は具体的な原因に基づいて下位の開発Agentへ差し戻すか、外側が確認済み設計に基づいて補足する。元の問題と直接関連する影響を再検証する。

テストに渡すパッケージには、少なくとも実際のSourceの版、Diff、設計との対応、コンパイル済み生成物、デプロイ一覧、DB／インターフェースの変更、ビルドの証拠、既知の未確認事項を含める。コンパイル成功と業務テスト合格は分けて報告する。

## 08｜外側テストAgent：Matrix、固定Case、期待結果（想定）を先に有効な基準にする

### ユーザー入力を保持し、既存の生成器に適合させる

私の元のMatrix、固定Case、期待結果、初期テーブル、データ説明を読み、版、元の行番号／セル、固定IDを保持する。まず、入力がテスト観点のMatrix、固定済みの実行Case、または両者の混在のどれに当たるかを判定する。

- 既存の固定Caseはそのまま取り込み、理由なく再生成、改名、条件の削減、期待結果の書き換えを行わない。
- 生成が必要な部分は既存のテスト／CaseAgentに渡す。入力マッピング、コンテキスト、テンプレート、ツールのパラメーターを使って元の入力を利用させ、Frameworkに合わせるためにユーザーへMatrix全体の書き直しを求めない。
- 生成した各Caseに、対応するMatrixの行／条件の組み合わせと正式な根拠を残す。1行に複数のCaseが対応してよい。Matrixで明示された組み合わせ／カバレッジのルールに従って展開し、独断で際限のない直積を生成しない。
- 追加で見つかった境界、異常、回帰のCaseは「補足Case」と別に表示し、根拠を記録して、ユーザーの固定基準から区別する。補足件数の多さで元のMatrixの漏れを隠さない。
- 不足する期待結果のルールは、有効な正式要求／設計に基づく根拠がある場合にだけ補足する。判断できなければQIDを登録し、関連項目は未確認のまま残して、他の明確なCaseを進める。

### 外側によるCaseの確認

各Caseについて、少なくともCase ID、Matrix内の位置、要求／設計項目、対象プログラムと手順、前提条件、入力とデータ準備、実行パラメーター、期待値／判定ルールとその出所、収集すべき証拠、クリーンアップ／復旧方法を特定できるようにする。

すべてのMatrix条件と固定Caseの扱いを照合し、既存の有効なCase、生成済み・確認待ち、不足あり、未確認、根拠付きの対象外のいずれかを記録する。分母と明細を保持し、難しいCaseを黙って削除したり、未実行を合格に数えたりしない。

実際の実行前に、Case、期待結果、比較ルールの版を固定する。元のCaseが固定入力だけの場合は、独立した期待結果の根拠も探す。プログラムの実際の出力を自動的に正解にしてはならない。開発者も比較器も、期待結果の変更、無視する範囲の拡大、許容差の緩和によって失敗を隠してはならない。

## 09｜テスト実行バッチと環境準備の順序

最初にオフラインでCase、データファイル／SQL、比較定義を生成する。実際のデータ投入は、対象の構造が整ってから実施する。テストフローは次のとおり。

```text
ユーザーのMatrix／固定Case／期待結果
→ 外側が解析・適合処理を行い、既存のCase／データの能力を呼び出す
→ 外側がカバレッジと期待結果を確認し、有効な版を固定する
→ 既存の接続を再利用し、個人開発環境の現状を読み取る
→ 依存関係に基づく計画に従い、コンパイル済み生成物、Oracleの構造、必要な依存物を同期する
→ 実際にロードされるプログラムと実際のDB構造を照合する
→ 初期テーブルと今回のバッチのCaseデータを投入し、前提状態を確認する
→ 環境とデータがREADYになる
→ 既存のrunnerで実際にプログラムを実行する
→ 既存の能力で収集、比較、報告を行う
→ 外側が再確認し、原因別に修正して関連テストを再実行する
→ クリーンアップ／実行時の状態を保存し、引き継ぐ
```

実際の実行ごとに一意の`run_id`を生成し、バッチ一覧を保存する。少なくとも次の内容を含める。

| 分類 | 必ずひも付ける内容 |
| --- | --- |
| 範囲 | 案件、機能、Case ID、Matrixの版と位置、対象環境 |
| プログラム | Sourceの版／ハッシュ、ビルド識別子、コンパイル済み生成物とハッシュ、依存関係、実行入口 |
| データベース | Oracleサービスと個人ユーザー／schemaの参照先、Objectの範囲、対象定義の版、移行スクリプトのID／ハッシュ |
| データ | 初期テーブルの基準、データファイル／SQLの版、投入順序、データバッチ、クリーンアップ範囲 |
| 判定 | Caseの版、期待結果の原本／ルールの版、収集範囲、比較規約 |
| 環境と呼び出し | ディレクトリ／設定の参照先、既存Agent／ツールの版、デプロイ／実行パラメーター、状態、証拠索引 |

Source commitがない場合は、実際のファイルのハッシュとビルドの出所を記録してよい。対応関係を証明できないものは未確認のまま残す。通常の一覧にパスワードを保存しない。テスト中に版が変わった場合は新しいバッチを作成して影響範囲を判断し、異なるプログラム／DB／期待結果の版の証拠を混在させない。

## 10｜Oracleのテーブル構造更新：実際の構造から対象定義へ移行する

既存のDB接続、メタデータ取得、DDL実行、移行記録の能力を優先して再利用する。不足は外側から呼び出せる通常のモジュールとして補い、任意のSQLを自由に生成して直接実行する別のフローを新設しない。

1. **対象の識別情報を確認する。** 実際のOracleの版、接続サービス、ユーザー、対象schema、オブジェクトのowner、シノニム、プログラムの実際の接続設定を照合する。個人開発ユーザーが分離されているだけでは、すべてのテーブルが個人の範囲に属する証明にはならない。共有オブジェクトを識別し、操作を限定する。
2. **実際の状態を取得する。** 今回関係する列、型、長さとバイト／文字の意味、精度、NULL、デフォルト値、制約、索引、関連する依存関係を読み取り、構造スナップショットと適用済み移行の記録を保存する。データディクショナリ、`DBMS_METADATA`、工程の既存方式を使用してよい。過去の版番号だけを読んで、実際にも一致していると推定しない。
3. **目標を確定する。** 正式な最新版の定義と今回の設計から対象構造を取得する。定義がExcel／文書の場合は、正確な位置と解析できなかった部分を残す。定義内の例、物理格納の差異、環境固有値をどう扱うかは、プロジェクトの根拠が必要である。
4. **差分移行を生成する。** actual → targetの明確な増分スクリプトと対象一覧を作成し、既存データ、NULL／必須、型変換、フィールド長の短縮、デフォルト値、必要なデータ補完、制約、依存関係への影響を確認する。完全なテーブル作成SQLが目標定義であっても、それをそのまま既存DBの更新スクリプトとして実行しない。
5. **実施計画を作成する。** プログラム、DDL、データ補完、依存オブジェクトの再作成／コンパイル、ロードの順序は、互換性と工程の実際の依存関係に基づいて決める。DBを常にプログラムより先にする、またはその逆と一律に仮定しない。前提条件、スクリプトのハッシュ、バックアップ／復旧条件、実施後の確認事項を保存する。
6. **確認済みの範囲で実行する。** 個人開発対象であることが確認でき、根拠があり、回復不能な損失を生じさせない必要な移行は、事前確認後にそのまま進める。テーブル／列の削除、データ損失、帰属不明、許可範囲を超える変更はQIDを記録し、それ以外の実行可能な手順を続ける。
7. **実際の結果を照合する。** 各手順のコマンド、結果、適用済み状態を記録し、実際の構造、必要なデータ、影響を受ける依存関係を再照会する。スクリプトの正常終了だけでactualとtargetの照合に代えない。

適用済みで照合結果も一致している移行は再実行しない。同じ移行IDに異なるスクリプトハッシュが対応する場合は競合を記録し、原因と実際の構造を確認してから対応する。履歴を上書きしたり、そのまま適用済みとみなしたり、確認せずに再実行したりしない。

Oracleの通常の構造DDLは暗黙的にコミットされる。DDLとテストデータのDMLは分けて扱う。最後の`ROLLBACK`でバッチ全体の構造を復旧できると考えず、DDLによって未確認のテストデータトランザクションが意図せずコミットされないようにする。必要なプログラムの旧版、構造、必要なデータの復旧条件を保持し、プラットフォームの特性に応じて明示的な復旧または前進修正の計画を使う。失敗後は先に適用済みの部分を特定し、その後で継続実行を判断する。

実際のDBにアクセスできない場合は、メタデータの適合処理、差分計画、スクリプト、オフライン検証を完成させる。リモートへの適用は「未実行／検証待ち」と記録し、サンプルDBでの結果を個人開発DBの更新済み結果として扱わない。

## 11｜FTPによるコンパイル済み生成物の配置：実際に有効な版を照合する

まず既存FWに転送、デプロイ、ロードの手順があるかを調査する。存在する場合は外側から呼び出し、確認を補う。存在しない場合にだけFTPの適合処理を追加する。プロトコル、ホスト、ユーザー、パス、設定は会社の既存の有効な設定に基づき、「FTP」という語だけから具体的なサーバーや環境を推測しない。

- 今回の生成物、Source／ビルドとの対応、対象プラットフォーム、依存関係、ディレクトリ、実際のロードパスを確認する。新しい改修をテストする前に、対応する新しいコンパイル済み生成物を取得する。
- 既存のプログラムの版と必要な復旧資料を保存する。プラットフォームが対応する方式で、一時アップロード、照合、切り替えを行う。コンパイル済みバイナリはバイナリ転送を使い、テキストモードでバイト列が変更されるのを防ぐ。
- アップロード後は、リモートのチェックサムまたは読み戻しによる比較で内容の一致を確認し、デプロイ一覧を記録する。ファイルサイズや時刻が一致するだけでは、内容が完全に一致すると主張しない。
- 権限、関連設定／依存関係、再起動、再ロード、リンク、その他のプラットフォーム固有手順が必要かを確認し、工程の既存方法に従って実行する。
- 実際の実行入口／ロードパスと、プラットフォームが提供できる版またはビルド識別子により、実際に使われるプログラムを検証する。アップロード成功、デプロイ完了、実行時の有効化を分けて記録する。
- FTPの役割は転送である。実際のプログラム実行、終了待ち、終了コードの取得には、既存FWの実行経路を調べて使用する。FTP自体でリモートプログラムを実行できると仮定しない。
- 接続が切れた後は、リモートの一時ファイル、対象ファイル、照合結果、切り替え状態を先に確認してから継続する。復旧状態が不明なまま、繰り返し上書きしてテストを続けない。

## 12｜初期テーブル、テストデータと READY チェック

ユーザーが提供した初期テーブルの内容、共通の基準データ、Case 専用データ、一部テストデータの期待結果（想定）を分けて登録し、出典、版、キーの範囲、適用する Case を保持する。本プロジェクトにおける初期テーブルの意味は説明資料と既存の手順から確認し、schema 全体の初期化を意味すると独断で解釈しない。

既存のデータAgent／生成器、投入・クリーンアップ機構をできるだけ使用し、外側Agent が以下を確認する。

- 初期値、コード値、主キー・外部キー、関連テーブル、処理の発動条件、投入順序が今回の Case の条件を満たしているか。
- 指定済みデータがある場合は元の値を保持する。生成が必要な項目は有効な規則に従って生成し、結果を説明・再現できるよう、必要な時刻、シーケンス、乱数シード、または値の固定方法を記録する。
- 共通の初期化と各 Case の準備／クリーンアップを分ける。相互依存する Case は順序を明示し、データが独立していない処理は並列実行しない。
- 実際の投入前に目標の構造が準備済みであることを確認する。投入後は行数、キー値、重要な前提値を確認し、既存の方法に従ってトランザクションのコミット／ロールバックを明示する。
- データのクリーンアップは今回許可されたデータのキー／バッチとオブジェクトに限定し、全件 DELETE、TRUNCATE、再作成を既定の処理にしない。テスト前の状態と、復旧／保持方法の説明を保存する。
- データスクリプト生成済み、データ投入済み、データが前提条件を満たす、を別々に記録する。期待する初期状態と実際の投入結果が一致しない場合は、まず準備処理を修正する。

次の全項目に証拠がある場合に限り、該当テストバッチを `READY` とする。対象環境の識別が正しいこと、実際のプログラムがバッチで指定したものと一致すること、関連する Oracle の構造が目標と一致すること、依存要素と実行経路が利用可能なこと、初期テーブルと Case データが前提条件を満たすこと、期待結果と比較規則が有効なこと、本バッチの実行に影響する未解決の環境差異がないこと。

`READY` は本実行前のプログラムによるチェックポイントであり、新たに人手で各段階を承認するための手順ではない。失敗した場合は修正するか、該当部分のブロック事項を登録し、ほかの実行可能な作業を続ける。

各 Case または順序依存のある Case グループの実行前に、その前提データと現在のプログラム／構造の状態を再確認する。前の Case によって生じた変更は、有効な定義に従ってリセットまたは保持する。バッチ開始時の一度だけの確認で、各 Case の前提確認を代替してはならない。

正式な比較バッチには、期待結果とその他の前提がすべて有効な Case のみを含める。期待結果のない Case は別に保持する。実行範囲、データへの影響、その他の前提、結果採取のみを目的とすることがすべて明確な場合に限り、個別に採取を実行し、「採取のみ・未判定」と表示する。合格には数えず、ほかの準備済み Case の実行も妨げない。

## 13｜実行、採取、比較と外側Agent による再確認

### 実際の実行と結果取得

外側Agent から確認済みの Case、プログラム入口、パラメータ、ディレクトリ、個人環境、データバッチを渡し、既存の runner を呼び出す。開始／終了、ジョブまたはプロセスの識別子、コマンド／パラメータの参照先、終了コード、タイムアウト、生ログ、最終状態を保存する。

Case の要求に従って、必要な戻り値、ログ、ファイル、DB の行、および前後の状態を採取し、Case と証拠を個別に追跡できるようにする。元の証拠を保存し、解析／正規化後の結果は別に保存する。採取失敗、プログラム実行失敗、比較不一致を分けて記録する。トリガー、非同期ジョブ、バックグラウンド処理が関係する場合は、工程の条件に従って完了を判断し、実行要求の送信に成功しただけでプログラム全体の完了としない。

各 Case の元の証拠は、次の Case の初期化、クリーンアップ、出力の上書きが行われる前に採取を完了し、独立した場所へ保存する。連続シナリオの状態を保持する必要がある場合も、まず現在のチェックポイントを保存し、バッチ実行後に最後の Case の状態だけが残ることを防ぐ。

### 既存の比較機能の再利用

独立した期待結果と実際の結果を既存の比較器に合わせて渡し、プロジェクトで有効な並び順、NULL／空値、文字コード、日付／タイムゾーン、数値精度、許容差、動的項目、無視項目の規則を使用する。Oracle／本プロジェクトにおける空文字列などの実際の意味は正式な要求に従って扱い、独断で一般化しない。比較規則が欠けており結論に影響する場合は QID を登録する。

期待結果、実際の結果、差異の位置、判定根拠を保存する。合格させるために期待結果を自動変更したり、新たな差異を無視したり、許容差を広げたり、Case を飛ばしたり、合格しやすい項目だけを比較したりしてはならない。

### 外側Agent による最終確認

Matrix のカバー状況、固定 Case の保持、入力データ、実際のプログラム／DB の版、実行完了状態、採取の完全性、比較ロジックを確認する。必要に応じて代表的な結果の元ファイル／クエリ結果を直接再確認し、既存Agent の要約だけを信用しない。

各 Case の状態を、確認待ち、生成済み・チェック待ち、準備完了、未実行、実行中、実行失敗、中断／結果不明、比較不一致、比較合格、根拠のある適用対象外に分ける。報告では分母と各分類の件数を個別に示し、未実行と未確認を合格に数えない。

## 14｜手戻り、外側Agent による補足と復旧

各不備について、発見段階、対象／Case、実際の事象、期待結果または規則、元の証拠、原因分類、修正担当モジュール、修正差分、再検証結果を記録する。

| 原因 | 対応方法 |
| --- | --- |
| 設計または業務仕様の不足／矛盾 | 確認可能な内容に基づいて修正する。業務判断が必要な事項は QID に記録し、関連項目だけをブロックする |
| Source の実装誤り | 具体的な不備を外側開発Agent と既存開発Agent に返し、修正、再ビルド、バッチ更新、再テストを行う |
| Case またはテストデータの誤り | 独立した正式な根拠に従って修正し、版と影響を記録する。元の固定入力と変更理由を保持する |
| プログラム配備／DB 構造／依存要素の不一致 | 環境準備と検証を修正し、再度 READY を満たしてから影響する Case を実行する |
| 実行経路／環境の障害 | 回数制限のある再試行・復旧規則に従う。未実行を業務上の合格や業務実装の失敗として扱わない |
| 採取／解析／比較の誤り | 元の証拠を保持してツールと規則を修正し、再採取または再比較する。本当に再実行が必要かを判断する |

根拠のある外側Agent の補足によって完全性を高めてもよいが、業務仕様を根拠なく補ったり、ユーザーの固定された期待結果を変更したり、元の不備を隠したりしてはならない。すべての補足に出典、作成者／実行モジュール、版、再チェック結果を残す。

再実行前に、発生済みのデータ変更、重複処理、生成済みファイル、適用済み DDL を確認し、最小の再実行単位と復旧方法を明示する。プログラム修正後は対応する成果物を再配備する。比較器のみの修正で元の証拠が十分な場合は、有効な証拠を再利用し、機械的に全件を再実行しない。すべての再利用について、版と状態が引き続き有効であることを確認する。

各修正サイクルで、明確な未合格項目を改善する。失敗が繰り返される場合は第02節に従って該当部分のブロック事項を保存し、修正ループを期待結果の変更ループにしない。

## 15｜質問・回答の一元管理：本当に不足している事項だけを質問し、回答後に自動で対応を完結する

会社が許可する成果ディレクトリに、**正本の質問・回答ファイルを一つ**維持する。工程に既存の形式がある場合は優先して使用し、ない場合は `回答待ち事項.md` を用いる。同じ問題をチャット、複数の草稿、公開 GitHub Issue に分散させない。ほかの成果からは固定した QID で参照する。すでに正本がある場合は、本パッケージの事前確認リストを重複排除して統合し、QID の対応を保持する。二つ目のファイルを作らず、事前確認の8項目を一律にユーザー回答待ちにしない。

各質問には少なくとも以下の項目を含める。このテンプレートをそのまま使用してよい。

```text
QID：
状態：未調査／調査で解決・回答不要／ユーザー回答待ち／回答済み・確認待ち／採用済み・更新待ち／更新済み・検証待ち／検証済み・完了
質問：何を提供または決定する必要があるかを一文で記す
調査済みの内容：実際の資料、版、位置、調査範囲、結論
影響対象：案件／機能／設計項目／プログラム／DB Object／Case
ブロックの有無：実際に影響する手順のみを記し、継続可能な部分は別に示す
選択肢と提案：根拠、影響、推奨案。自分で決められる事項は承認を求めず決定を記録する
暫定対応：継続する作業と、未確認のまま保持する内容
ユーザー回答：空欄とし、後で記入された原文を保存する
回答者・日時／適用範囲：不明な情報を作って記入しない
採用結果：確認後の解釈、関連変更、矛盾または追加確認が必要な点
検証と完了：影響を受ける版、実際の再検証結果と証拠
```

正本の質問・回答ファイルにすでにある同等の状態を使用し、対応関係を記録する。二組の状態を並行管理しない。まず重複排除と事実確認を行い、本当にユーザーの回答が必要な不足事項だけを書く。有効な工程上の事実で解決できるものは根拠を記録し、「調査で解決・回答不要」とし、ユーザーに再確認を求めない。「考えられるすべてのリスク」を質問票に並べてはならず、各質問は具体的な不足と実際の影響に対応させる。

ユーザーが後からファイルにまとめて回答した場合は、原回答を読み取って保存し、現在の資料、業務上の権限、適用範囲と一致するか確認する。関連する設計、Source、データ、Case、環境計画、比較規則を更新し、必要な再検証を実施してから完了を記録する。矛盾がある場合は証拠を残し、対象を絞って追加質問する。回答があったことを、そのまますべての操作が承認済み、またはすべての検証が合格済みであることと同一視しない。

そのまま送信できる再開指示を一つ、引継ぎファイルに保存する。

「本工程の今回の外側Agent の実行記録と正本の質問・回答ファイルを読み、私の追加回答を確認し、影響する成果を更新して再検証してください。最小の復旧地点から準備の整ったすべての作業を続け、残る質問は引き続きファイルに集約し、段階ごとに回答を待たないでください。」

## 16｜成果の構成、検証と完了条件

工程の既存ディレクトリを使用する。以下は既存の規約がない場合の提案にすぎず、実際に採用した後で本当の入口を示す。ディレクトリ例を満たすためだけに、内容のない空の成果を作らない。

```text
外側Agent/                        # 実際の実装、または工程の既存Agent／workflowディレクトリ
  統一入口、三つの役割、アダプター層、チェックと状態管理
今回の実行/<run_id>/
  入力索引と版の記録
  Framework再利用・接続一覧
  設計・開発成果とチェック／実際のDiff
  テスト基準、Case、初期テーブル／データ計画
  環境の変更前状態、配備／移行／投入記録
  元の実行・採取証拠、期待結果と差異、結果集計
  進捗と再開の説明
正本の質問・回答ファイル          # 工程の既存の場所に一つ維持し、実行記録から参照する
```

### 実装そのものの検証

まず工程で定められた必要なチェックを実行する。追加した外側Agent とアダプターのロジックについて、本当に誤りが生じ得る分岐を検証する。入力不足／版の矛盾、既存Agent の成果不足、手戻り成功と上限到達、ツール失敗、結果不明後の復旧、期待結果が実際の出力で上書きされていないことを含める。既存テストを優先して再利用する。追加チェックは振る舞いを検証し、実装をそのまま写しただけのチェックやファイル存在確認だけにしない。

オフライン／架空のフィクスチャはインターフェースと制御ロジックの検証に使用してよいが、実際の会社 Case と分離し、明示する。それらによってリモートへの配備済み、Oracle 更新済み、業務テスト合格を証明することはできない。

### 実際の一連の処理を通した後の展開

既存の入力から、資料が明確で代表性のある実際の機能／Case を自動選択し、外側Agent への入力 → 既存Agent → 外側Agent のチェック → 配備と Oracle／データ準備 → 実際の実行 → 採取と比較を完了する。一連の処理が有効であると確認できた後は、**残りの確認済みで再利用可能、かつ条件の整った範囲を自動で続けて処理する**。「パイロットの処理が通った」ことを理由に、展開の許可を私に再度求めて待たない。まだ明確でない業務規則は、影響範囲を明示して該当部分だけを保留する。

### 層別の受入確認

| 層 | 合格時に確認できなければならない実際の成果 |
| --- | --- |
| 外側Agent の実装 | 三種類の外側Agent に実際の入口、入力処理、既存Agent 呼び出し、出力チェック、補足／手戻り、状態復旧がある |
| Framework の再利用 | 一覧内の各結論に実際のインターフェースと証拠がある。再利用可能なものは継続使用し、追加部分には不足の根拠がある |
| 設計／開発 | 有効な入力、実際の設計、実際の改修、ビルド／チェック、双方向の追跡がある。未実施項目は別に示す |
| テスト基準 | 元の Matrix と固定 Case が完全に保持され、カバー明細、独立した期待結果、明確な比較規則がある |
| 環境整備 | 指定した個人環境で対象プログラムが実際に有効となり、Oracle の目標構造、初期テーブル、テストデータがすべて確認されている |
| テスト実行 | 実行済みの各 Case をバッチ、実行、元の結果、期待結果、比較証拠まで追跡できる |
| 対応の完結 | 不備が修正・再検証されている。質問が集約され、まとめて回答できる。実際の状態から再開できる引継ぎがある |

すべての層について「実装完了／オフライン検証済み／リモート適用済み／実際に実行済み／比較合格／未実行／一部完了／ブロック」を分けて示す。会社へのアクセス、資料、環境条件を取得できない場合も、引き続き可能な実装、アダプター、スクリプト、オフラインチェックをすべて完了し、残りは未検証と明示する。エンドツーエンドで完了したと宣言してはならず、その事情を理由に提案だけを提出する状態へ戻ってもならない。
