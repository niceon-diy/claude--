01 · 建议先确认的结论

建议采用“保留对应一览业务结构 + 增加追踪索引 + 加固 Step3 生成流程”，不建议因 Step5 出现 QA 就大改全部分类或把大量技术字段塞进主表。

① 对应一览确定改哪些对象、概略怎么改；缺项才修
② Step3将每个对应项展开成有证据、可执行的改修项
③ QA 门禁先回查上游并自解决，真正需判断才形成 QA
④ Step5只接受版本一致、覆盖完整、阻塞透明的交付

核心验收：Step5 的“零残留 QA”应理解为零未调查／零未归属／零被静默遗漏。真正需业务决策的事项保留为 BLOCKED，不能用删除或自动猜测使报告好看。

02 · 必须先核对的真实基准

项目目前掌握执行时必须核实
工程编号当前要求：Step3 制作改修一览，Step5 存在 QA确认实际 Step3／Step5 任务名称与 Agent 调用链；历史流程的编号可能不同
正式范围输入対応一覧优先；数据库主表项目追加为起点文件／Sheet／版本／对应ID／审批状态

03 · 对应一览（対応一覧）准备怎么改？

3.1 分类：尽量保持现有结构，补漏不重造

顺序建议分类检查要点处理原则
01DB 関連主要表最前，之后相关表、VIEW、设定数据；DB 项目追加是否完整明确主表字段和关联条件，链接下游引用对象
02外部 APIAPI 项目追加／入出力／处理／错误分支单列，避免混同内部 IF
03IF外部／系统 IF layout、数据项、调用条件与 API 顺序一致；不重复计入
04画面输入、表示、校验、迁移、画面间连接若属于正式范围，逐项关联
05画面关联 CSV画面连接或下载／上传相关 CSV 的定义、字段、映射独立可追踪，但避免与画面重复描述同一需求
06OL 機能在线程序、业务处理、DB 访问、调用关系以机能为主，Source 做关联索引
07BT 機能批处理、调度／文件与 SQL 影响、错误恢复以机能为主，Source 做关联索引
附属索引Source／模块关联程序、类、方法、SQL、文件路径与对应ID链接不是新的业务分类，也不增加“帳票”分类

如果公司现行对应一览已有上述内容，不做无意义改版；先找 Step5 的 QA 是否由遗漏、粒度不当或映射缺失造成，再决定需调整的具体位置。

3.2 主表怎么调整

建议保留既有四列：ID｜名称｜概要説明｜改修内容。正文写给业务／设计复核人员看，尽量短；技术追踪信息移到同一工作簿的辅助 Sheet 或附属文件。不要让一张表兼任需求、程序清单、QA 台账、证据库四种角色。

主表字段拟修订规则例（仅格式示意）
ID保持稳定、跨版本不重用；唯一定位对象及子项DB-001
名称明确业务对象和本次变化对象主要表：项目追加
概要説明说明当前→目标的业务变化，避免直接贴代码新增管理项目并在关联功能中使用
改修内容说明需改什么及关联处理；不写无证据实现细节表定义更新；同步核查引用／更新对象

3.3 建议新建／补齐「追踪・证据索引」

字段作用为何必要
対応ID／行定位主表的精确定位符（Sheet、行号、节）防止 Step3 漏读或误认行
区分／对象键分类及唯一对象键跨 Sheet／跨对象去重
清单版本／Source 基准对应一览版本、设计书／代码基准发现使用旧版本
来源证据Box 章节、Source 路径和行号、设计依据让 Step5 QA 可反查
确定状态確定／要確認／対象外（附理由）不把推测当既定范围
改修ID 链接一个対応ID可映射多个改修ID可验证拆分完整性
关联QA-IDStep5 问题的逆向索引同类 QA 再现时可追根因
复核／批准状态提出者、复核时间、审批状态区分草案和正式范围

变更审批：若对应一览缺少真实业务对象，应先生成修订差分并申请批准；不允许 Step3 依据参考 Source 自动追加正式改修范围。

04 · Step3：改修一览的生成流程准备怎么改？

建议先把 Step3 现有执行链列为「入口 → 信息抽取 → 对象影响 → 改修项生成 → 检查 → QA → 出口／交接」。下面 S3-01～08 是待核查的控制点，并非已经确认公司代码缺少它们。

ID检查当前是否做到拟修改措施（若缺失）检查通过标准
S3-01入口是否锁定有效对应一览、设计书、稳定 Source 及版本创建输入基准清单，记录路径／版／时间戳／hash；缺版本或不一致则阻断每次生成可复现并指向相同输入基准
S3-02是否读取全部 Sheet／分类／有效行，包括主表、API、IF、画面、CSV、OL、BT建立全量清点表，记录应读取数／实读数／异常行及遗漏原因每个有效対応ID都被读取并有处理结果
S3-03是否完成 DB→程序／SQL→API／IF→画面／CSV→测试影响追踪增加影响展开与证据约束；影响なし必须记录理由影响有／无／待确认都有可定位依据
S3-04是否将一个需求拆为可执行、可追溯的改修单位给每项稳定改修ID、对象、现行→改修后、理由、来源、依赖、证据和状态每个改修ID能明确说明谁改什么、为什么
S3-05是否利用既存类似项目的改修前后 Diff 检查具体改法记录参考文件 before／after、差异、适用条件与采用理由；不扩大范围无证据时状态为未确认，而非臆测已确定
S3-06是否进行对应ID ↔ 改修ID 双向验证增加缺项、重复、孤儿项、冲突、错版、范围外改修检查器无未解释漏项，例外有理由／审批
S3-07是否在 QA 发给用户前完成根因调查按输入缺失、生成缺陷、传递、资料冲突、工具和业务判断分类，自解决并记录证据无笼统 QA；每个待决事项有调查清单和明确问题
S3-08是否把完整改修一览、版本、覆盖矩阵与未决项交给 Step5制定交接契约：改修ID 集合、版本、证据索引、状态必须被后续读取确认Step5 接收数据与 Step3 输出一致；失败即阻断

4.1 推荐改修一览（Step3 Output）字段

必需字段含义／要求
改修ID｜对应ID｜区分｜对象明确由哪个对应一览项目展开成哪个具体改修对象；一对多允许
現行仕様｜改修後仕様｜改修理由明确差异、边界和原因，不用“按需求修改”等空话
处理位置｜影响关联程序／类／方法／SQL／API／IF／画面／CSV，能定位就标路径和行号
证据位置｜Source 基准设计书版次／章节、代码基准、类似项目 Diff
状态｜QA-ID｜前置依赖確定／要確認／対象外；不明点不能混入已确定执行内容
生成版｜复核结果标识哪一轮生成、使用什么基准、是否通过双向覆盖

主张：**对应一览仍负责“改什么”；Step3 才负责展开“具体谁改、在哪里改、怎样验证”**，避免两个文件职责混乱。

05 · Step5 QA 发现后，应该回写哪里？

QA 主因对应一览准备怎么改Step3 准备怎么改是否可直接定案
A 业务范围遗漏／矛盾列候选改修条目或说明修订差分批准后重新展开该对应ID的改修项否，需业务审批
B Step3 漏抽取／误生成原清单正确则不改修补抽取、原子化或覆盖校验并重生成授权范围内可修
C 版本／交接错误原清单正确则不改修复版本检查、传递及接收验证授权范围内可修
D Step5 独立问题不改通常不改，记录不上游的理由在本阶段有证据地处理
E 设计／Source 冲突仅业务范围不清才提出澄清保留争议证据，不凭空决定视审批权限
F 工具／权限故障不改修复受权工具流程；权限问题请求授权超权限必须阻塞
G 必须业务决策提出明确待决差异保持候选／BLOCKED，不生成假定确定项否

一项 QA 即使关联多个文件也只有一个主根因，可以记录多个次因；必须保留 QA-ID、对应ID、改修ID、处理前后、证据和状态的完整链。

Test ID测试情形期望结果

Step5 出口判定：
PASS＝全 QA 已调查归属、上游修改获授权并落实、双向覆盖与复测通过、无关键阻塞；
BLOCKED＝仍需业务决定、权限、缺少必要输入或存在未解决关键差异；
NOT_VERIFIED＝未取得完整环境、无法完成必要检查或复测。

08 · 推荐落地顺序、审批与风险控制

  1. 只读调查：确认真实 Step3／Step5 和输入文件、现行对应一览格式、QA 原文及权限。
  2. QA 全量建账：去重、查因、对应ID／改修ID映射、证据采集；不能绕过需用户提供的真正业务判断。
  3. 先交评审版：展示对应一览每条候选修订差分和 Step3 每个节点改修设计；标“已确认事实／推断／建议／待审批”。
  4. 审批后再修改：范围类先更新对应一览，再改 Step3 规则和生成逻辑；仅交接缺陷不动业务清单；保护原始资料。
  5. 复验：重新生成改修一览，检查上下游 ID／版本，重新运行 Step5，核对 QA 台账与复现结果。
  6. 归档：在项目内 document／output 保存报告、差分、证据索引、版本、审批记录和审计日志。
主要风险：① 未经审批改变业务范围；② Step 编号与实际工程不一致；③ 以缺少 QA 数量冒充零 QA；④ “已生成文件”被误认为已正确传递；⑤ 公司资料复制到公开 GitHub。缓解：所有公司机密原文与 Source 保持在获授权的公司环境；GitHub 中只存本通用方案与不含机密的提示词。

10 · 日本語版｜レビュー用方針書

件名：Step5 不明点の全件調査および対応一覧・Step3 改修一覧生成処理の改善案。

注意：本書は現行ソース・実際の QA 原文・正式な設計書を未確認の提案版です。正式な対応一覧や Agent を改修済みという意味ではありません。最初は読み取り専用で調査し、改修案の承認後に実施してください。

10.1 改善の基本方針

対応一覧は「何を改修するか」の上位基準です。主表示列（ID／名称／概要説明／改修内容）をなるべく維持し、対応 ID・証跡・変更 ID・QA-ID・版数等は追跡用の Sheet または付属索引で管理します。Step3 は対応一覧の全件を読み取り、改修対象を実行可能な単位へ展開し、後続工程へ漏れなく引き継ぎます。

10.2 対応一覧の見直し

対象変更案判定基準
分類DB（主要テーブル優先）→ 外部 API → IF → 画面 → 画面関連 CSV → OL → BT正式な現行構成との差分がある場合のみ提案。帳票の無断追加禁止
主表ID／名称／概要説明／改修内容を可能な限り維持業務担当者が理解できること
追跡索引対応ID、対象、版、証跡、確定状態、改修ID、QA-ID、承認情報上流・下流を双方向に追跡可能
範囲変更変更前後、理由、証跡、影響を候補差分として提出承認前に正式改修範囲を変更しない

10.3 Step3 に追加・強化すべき検証点

管理 ID改善内容

S3-02DB・API・IF・画面・CSV・OL・BT の全件読込と件数突合
S3-03DB 項目から SQL、Source、API／IF、画面／CSV、試験まで影響調査
S3-04安定した改修 ID、変更前後、出典対応ID、証跡、確定状態をもつ改修項目の作成

S3-06対応 ID ↔ 改修 ID の双方向網羅性、重複、漏れ、矛盾、対象外を検査
S3-07QA 発行前に原因調査と自己解決を実施。要判断事項だけ正式 QA
S3-08改修一覧・版・未決事項・証跡索引を後続へ引継ぎ、受領／版一致を検証

10.4 QA の反映先と出口判定

対応一覧自体が不足する場合は候補差分を作成して承認を取得し、その後に改修一覧へ反映します。Step3 の抽出ミスなら生成処理を修正します。版や引継ぎの不備なら連携を修正します。Step5 固有の課題は当該工程で対処し、上流を無用に変更しません。業務判断を要する事項は明確な選択肢と根拠を提示し、BLOCKED とします。

Step5 の QA 残留ゼロとは、未調査／未分類／未処理の QA をなくすことです。未承認の業務上の重要事項を勝手に解決済みにしてはいけません。再生成と再実行による実証ができなければ PASS と判断できません。

10.5 承認前に必要な具体的成果

実 QA ごとの QA-ID、対応 ID、改修 ID、証跡、原因、対応一覧の変更前／変更後、Step3 の対象 Agent／スクリプトと変更前／変更後、承認要否、正常・異常系テスト、実施状況を記載した差分表。実際のファイルや行番号が未取得なら「未取得／未検証」と明記してください。
