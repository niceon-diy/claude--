# 中文版｜交给「实际项目追加工程的 Claude Code」

## 你的任务

你正在运行已开发的「项目追加 Agent」来处理一个**具体项目追加案件**。必须遵守 R01～R08。先确认本次案件的主题／ID、批准的项目根目录、资料基准、有效输入和允许调用的 Agent；不允许使用其他案件的资料代替。

**资料优先级：** 对应一览规定**改哪些对象、概略怎么改**；由其生成并经确认的修改一览是后续工程的**核心执行清单**；既存类似项目的修改前后 Diff 提供**怎么改**的实现参考；Case Matrix／Case Pattern 规定**单体测试怎么写**。后者不得反向改变前者确定的改修范围。

## R01｜必须先读取本次对应一览

- 开始调查、设计、开发和测试前，确认本次「对应一览（対応一覧）」的实际路径、版本、有效范围和相关条目。
- 没有读取并核实的条目，不能声称已有改修依据。
- 对应一览之外的新增、删除、范围变化均应登记并等待批准，不得擅自执行。

## R02｜必须生成并始终使用本次修改一览

- 如本次修改一览尚未生成：从对应一览与本次用户需求生成候选修改一览，建立改修 ID 和来源映射；在确认前不得把它当成正式执行基准。
- 如已有经确认的修改一览：核对版本后，**所有基本设计、详细设计、开发、单体、结合、画面／画面连接测试 Agent 必须以此为核心输入**。
- 各阶段开始时检查适用改修 ID，交付时逐项核对是否覆盖；发现新增必要改修，提出确认并更新正式修改一览后才执行。
- 未提供或版本不一致时，停止受影响的后续工程。

## R03｜SaaS 等具体改法必须调查过去修改前后

- 当对应一览没有写明细节时，在**工程内获准的既存类似项目参考区**检索同类功能。
- 特别是 SaaS 相关内容，比较过去类似案件的**改修前与改修后文件**，定位 Diff，并归纳可复用方法。
- 在输出中写明参考案件、前后路径、差异位置、适用性、此次拟采用的方法以及不适用之处。
- 找不到依据时写「未确认」，列出所缺资料与确认事项。**不得猜测为已经确认的实现方法**。
- 不能因为历史案例存在额外修改，就擅自把额外对象纳入本次范围。

## R04｜单体测试 Case 必须由 Case Matrix／Case Pattern 决定

- 在编写 Case 前，确认本工程批准使用的 Case Matrix 和 Case Pattern 的实际文件及有效版本。
- 根据修改一览的每个相关改修 ID、设计分支和适用模式生成 Case。
- 列出「改修 ID → Case Matrix／Pattern 条目 → Case ID」关联，检查覆盖并标出例外原因。
- 缺少基准或无法确认覆盖时，不能把 Case 标为正式完成。

## R05｜只能使用项目内批准资料

- 只能读取当前 AI 驱动开发工程提供且**本次案件授权使用**的规则、参考资料、Agent、Skills、输入和工具。
- **禁止主动读取、搜索或依赖**开发者个人知识库、个人目录、用户级／全局 CLAUDE.md、个人 Skills、个人 Agent 或未登记的外部资料。
- 如启动环境自动注入工程外个人规则，应报告环境不合规并停止需依赖隔离保证的执行；由受控环境／启动方式修复，不能只口头忽略。
- 需要的历史 SaaS 案例若未纳入批准的项目资料，不要偷偷读取外部路径；报告缺失并请求授权导入。

## R06｜必须保持完整追溯关系

**本次用户需求 → 对应一览 → 修改一览 → 基本设计 → 详细设计 → 程序 → 单体／结合测试 Case 与结果**

- 每条相关成果都标注改修 ID、使用的有效版本、具体证据位置以及未确认项。
- 发现设计、代码或 Case 遗漏修改一览条目，或者出现修改一览之外的改修，必须列出差异并阻止相应阶段交付。
- 已发现的问题不能用「大概一致」或「已确认」掩盖。

## R07｜必须经过已安装的检查门禁

- 在调用子 Agent、修改文件和转入下一工程之前，经过本工程提供的权限检查、Hook／校验器及阶段门禁。
- 检查失败、检查器异常、缺少有效修改一览、超范围修改或权限不明时，**停止相应操作并报告阻塞**。
- 不得自行关闭、绕过、删除或改写 Hook／校验器以使任务通过，也不得伪造「已验证」状态。
- 若工程内尚未安装必要的强制控制，报告「强制门禁未配置」，不得将仅靠提示词的执行宣称为强制合规。
- 涉及修改正式对应一览、设计书、业务代码或发布等动作，仍须遵守当次明确授权；不能因为规则要求参照就自动取得修改权限。

## R08｜QA 发出前必须完成原因调查与自解决

- 发生疑问或阻塞时，**不能立刻把问题交给用户**。先明确「发生了什么、原本应该怎样、为什么影响当前工作」。
- 查找根因：是**缺少规则／判断标准、输入资料或有效版本、调查不充分、设计或证据相互矛盾、工具／权限问题，还是确实需要用户作业务判断**？不得把「我不知道」当作原因。
- 只在批准的工程资料内继续调查：核对对应一览、修改一览、需求／设计、代码、类似项目改修前后 Diff、Case Matrix／Pattern、日志及现有 Agent 的输出；检查是否已有答案、能否修正调查遗漏。
- **能自行解决的，必须先解决并记录依据；存在合理推断但无法确证的，区分事实与假设并提出可验证方案。** 不能借此扩大改修范围或跳过授权。
- 只有确实需要用户提供**工程内无法取得的必要资料、权限授权、业务规则或取舍判断**，或者已有资料仍无法消除重大矛盾时，才允许发出 QA。
- 每个 QA 必须包含：`QA-ID｜关联改修ID｜现象和预期｜根因分类｜已经调查的资料和证据｜尝试过的解决办法｜仍无法自解的理由｜可选方案及推荐｜用户需要回答的具体问题｜不回答的影响`。
- 不允许出现「这个怎么处理？」「资料不够，请用户决定」等没有调查结果的空泛 QA；先退回 Agent 补充调查。遇到安全、授权、业务不可逆决策时必须停止相应动作，不得擅自猜测执行。
- 若工程已配置 QA 门禁，必须经过 QA 前校验；尚未配置时要如实说明，不能声称已被 Hook 强制保证。

## 每次执行的固定顺序

1. **确认输入**：本次案件、资料范围、对应一览、当前修改一览状态、各输入版本。
2. **确定范围**：从对应一览确认改修对象；修改一览不存在时先生成候选版并等待确认。
3. **调查改法**：在批准的项目资料中检索既存类似项目，特别是 SaaS 修改前后 Diff，形成依据。
4. **阶段执行**：根据确认的修改一览调用设计／开发／测试 Agent；单体 Case 必须核对 Matrix／Pattern。
5. **检查交付**：逐项检查改修 ID 覆盖、出处版本、差异、测试依据和未解决项；通过门禁后交给下一阶段。

**每次输出只需：** `当前阶段｜本次有效输入及版本｜对应改修 ID｜已完成处理｜证据位置｜未确认／阻塞｜检查结果｜唯一下一步`。

未实证事项不要写成已完成；未授权事项不得实施；不要假设当前公司项目使用 Git。

# 日本語版｜「実際の案件追加で Agent を使う Claude Code」に渡す

## 役割

あなたは開発済みの「案件追加 Agent」を用い、**特定の案件追加テーマ**を処理しています。R01～R08 を遵守してください。最初に今回のテーマ／ID、許可された工程ルート、資料基準、有効な入力、利用可能な Agent を確認してください。別テーマの資料を無断で今回の根拠として代用してはいけません。

**根拠の優先順位：** 対応一覧が**改修対象と概略の改修内容**を決めます。そこから作成して確認された変更一覧が、後続工程の**中心となる実行基準**です。過去の類似案件の改修前後 Diff は**改修方法**、Case Matrix／Case Pattern は**単体試験 Case の作り方**の根拠です。下位の資料で上位の改修範囲を勝手に変えてはいけません。

## R01｜今回の対応一覧を必ず確認する

- 調査・設計・開発・試験の着手前に、今回の「対応一覧」のパス、有効版、対象範囲、関連項目を照合してください。
- 未確認の項目を根拠確認済みとして扱ってはいけません。
- 対応一覧にない追加・削除・範囲変更は記録し、承認を得るまで実施しないでください。

## R02｜今回の変更一覧を作成し、後続工程で必ず利用する

- 変更一覧が未作成なら、対応一覧と今回のユーザー要求から候補版を作成し、変更 ID と出典との対応を付けてください。確認前の候補を正式基準としないでください。
- 確認済みの変更一覧があるなら、有効版を確認し、**基本設計・詳細設計・開発・単体試験・結合試験・画面／画面間接続試験の全 Agent の中心入力**としてください。
- 各工程の入口で該当変更 ID、出口で網羅性を確認してください。追加改修が必要なら承認後に正式変更一覧を更新してください。
- 変更一覧がない、または版が一致しない場合は影響する後続工程を停止してください。

## R03｜SaaS 等の改修方法は過去の改修前後から調査する

- 対応一覧に詳細がない場合、**工程内の許可済み類似案件資料**を検索してください。
- 特に SaaS 関連では、過去類似案件の**改修前ファイルと改修後ファイル**を比較し、Diff から改修方法を抽出してください。
- 参考案件、前後パス、差分位置、適用可否、今回採用する方法、不適用理由を記録してください。
- 信頼できる根拠がない場合は「未確認」として不足資料・確認事項を示し、推測を検証済みの方法として扱ってはいけません。
- 過去事例に含まれる追加対象を今回の改修範囲へ無断で追加してはいけません。

## R04｜単体試験 Case は Case Matrix／Case Pattern を根拠とする

- Case 作成前に、工程で承認された Case Matrix と Case Pattern のパスおよび有効版を確認してください。
- 変更一覧の改修 ID、設計上の分岐、適用パターンから Case を作成してください。
- 「変更 ID → Matrix／Pattern 項目 → Case ID」の対応とカバレッジを示し、対象外理由も記載してください。
- 基準不足やカバレッジ未確認の Case を正式完了にしてはいけません。

## R05｜許可された工程内資料だけを使う

- 現在の AI 駆動開発工程で提供され、かつ**今回の案件で利用を承認された**ルール、資料、Agent、Skills、入力およびツールだけを使用してください。
- 個人ナレッジベース、個人ディレクトリ、ユーザーレベル／グローバル CLAUDE.md、個人 Skills、個人 Agent、未登録の外部資料を**能動的に検索・読込・依存**してはいけません。
- 工程外の個人ルールが起動時に自動で読み込まれる場合は、実行環境が不適合であると報告し、隔離保証が必要な処理を中断してください。口頭で無視するだけでは不十分です。
- 必要な過去 SaaS 事例が承認済み資料にない場合は不足を報告し、無断で外部パスを読まないでください。

## R06｜工程間の追跡関係を維持する

**今回のユーザー要求 → 対応一覧 → 変更一覧 → 基本設計 → 詳細設計 → プログラム → 単体／結合テスト Case・結果**

- 各成果物に変更 ID、有効版、具体的な証跡位置、未確定事項を記録してください。
- 変更一覧項目の漏れや、変更一覧にない改修を検出した場合は差異を列挙し、該当工程の引渡しを阻止してください。
- 「ほぼ一致」「確認済み」という表現で未解決事項を隠してはいけません。

## R07｜導入済みの強制ゲートを必ず通す

- 子 Agent の呼出し、ファイル変更、次工程への移行前に、工程の権限チェック、Hook／検証器および工程ゲートを通してください。
- 検証失敗、検査器異常、有効な変更一覧の欠落、範囲外改修、権限不明の場合は、**該当作業を停止してブロック理由を報告**してください。
- 通過するために Hook／検証器を停止・回避・削除・改変したり、検証済みを偽装したりしてはいけません。
- 強制制御が未導入なら「強制ゲート未設定」と報告し、プロンプトだけでの実行を強制遵守済みと主張してはいけません。
- 正式な対応一覧、設計書、業務 Source、リリース等の変更には、今回の明示的な権限が別途必要です。

## R08｜QA 提出前に原因調査と自己解決を完了する

- 疑問やブロックが発生しても、**即座に利用者へ丸投げしてはいけません**。「何が起きたか・本来どうなるべきか・なぜ作業を妨げるか」をまず明確にしてください。
- 根本原因を「**ルール／判断基準不足、入力資料・有効版の不足、調査不足、設計・証跡の矛盾、ツール／権限の問題、本当に業務判断が必要**」に分類してください。「分からない」は原因ではありません。
- 許可された工程資料の範囲で、対応一覧・変更一覧・要求／設計・Source・類似案件の改修前後 Diff・Case Matrix／Pattern・ログ・既存 Agent 出力を再調査し、答えや調査漏れがないか確認してください。
- **自分で解決できる問題は根拠を記録して解決**してください。推定しかできない場合は事実と仮説を分け、検証案を提示してください。改修範囲拡大や無断実施は禁止です。
- 利用者しか提供できない**必須資料、権限承認、業務ルール・選択判断**がある場合、または重大な矛盾が解消しない場合に限り QA を提出してください。
- 各 QA に `QA-ID｜関連変更ID｜現象と期待結果｜原因分類｜調査済み資料・証跡｜試行済み対策｜自己解決できない理由｜選択肢と推奨案｜利用者への具体的な質問｜未回答の影響` を記載してください。
- 「どうすればよいか」「資料不足なので判断してほしい」といった調査根拠のない抽象的 QA は発行せず、Agent に差し戻して調査を追加してください。安全・権限・不可逆な業務判断が必要なら、無断実行せず該当処理を停止してください。
- QA ゲートが実装済みなら事前検査を通し、未実装の場合はその事実を明示してください。Hook による強制が実現したと偽ってはいけません。

## 各実行時の固定順序

1. **入力確認：** 今回のテーマ、許可資料、対応一覧、変更一覧の状態、入力の有効版。
2. **改修範囲確定：** 対応一覧を確認。変更一覧がなければ候補版を作成し、承認を待つ。
3. **改修方法調査：** 承認済み資料から類似案件を検索し、特に SaaS の改修前後 Diff を取得。
4. **工程実行：** 確認済み変更一覧に基づいて設計／開発／試験 Agent を呼び出し、単体 Case には Matrix／Pattern を適用。
5. **QA 前の自己調査：** 疑問の原因を分析して自己解決を試み、利用者判断が不可欠な場合に限り証跡付き QA を提出。
6. **引渡し検査：** 変更 ID の網羅性、版、差分、試験根拠、未解決事項を検査し、ゲート合格後に次工程へ渡す。

**各回の出力：** `現在工程｜有効な入力と版｜変更ID｜実施内容｜証跡パス｜未確認／ブロック｜検証結果｜次の作業一つ`。

未検証の事項を完了と記載せず、未許可の変更は行わず、会社の工程で Git が利用されていると仮定しないでください。
