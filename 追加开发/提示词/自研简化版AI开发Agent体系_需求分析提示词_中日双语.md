# 自研简化版 AI 开发 Agent 体系：需求分析提示词（日中双语）

> 用途：交给 Claude Code，先独立评估需求与技术路线，再决定是否调查和开发。  
> 状态：需求讨论用提示词，**不是已批准的实施方案**。  
> 使用方法：中文和日文是同一任务的两个语言版本，**选择其中一种发送一次即可**。

## 中文版

请你进入 AI Agent 架构专家、AI 驱动开发专家和大型系统开发专家模式，对我的需求进行深入分析，并提出专业、务实、可落地的建议。

### 一、背景

我目前正在参与证券系统的项目追加开发工作。

公司已有一套 AI 驱动开发 Framework，其中包含多个 Agent，分别负责：

1. 基本设计
2. 详细设计
3. 程序开发
4. 单体测试
5. 集成测试

但是领导要求我们不能直接使用这套现成的 Framework，而需要自己开发 Agent。

我的想法是：

**先由你调查和理解现有 Framework 中各 Agent 的设计、执行机制和工作流程，然后以其为参考，独立设计并实现一套功能相对简化、但能够实际用于项目追加开发的 Agent 体系。**

这里的“参考”不等于直接复制。必须遵守公司对现有 Framework 的访问、复用和知识产权限制。

### 二、我的核心目标

我希望最终实现：

- 尽可能让 AI 独立完成从基本设计到集成测试的一系列开发工作。
- 我主要负责提供必要 Input、确认重要事项以及验收成果。
- 各 Agent 之间能够自动传递成果，不需要我反复解释上下文。
- 处理过程完整、结果准确、证据可追溯。
- 能够防止遗漏、错误理解、擅自推测和未经确认的修改。
- 采用 PDCA 思想，形成执行、检查、改进的质量闭环。
- 方案尽可能简单、容易维护、容易扩展，不追求复杂架构。

我已经整理过项目追加所需的 Input，包括 Source 源头、本番设计书、テーマID及名称、追加对应一览、参考 テーマ、参考 Source 改修位置和必要的外部设计。

### 三、希望你重点思考的问题

1. 我的总体思路是否合理？有哪些风险和更好的替代方案？
2. 应该怎样调查现有 Framework，才能真正理解各 Agent 的运行原理，而不是只看表面的提示词？
3. 哪些能力必须保留，哪些可以合并、简化或取消？
4. 应该开发五个独立 Agent，还是采用其他更合理的架构？
5. 如何设计 Agent 之间的 Input、Output、执行状态和交接机制？
6. 如何保证 AI 不漏项、不虚构，并能够检查和纠正自己的错误？
7. 如何利用现有的 Box 设计书、本地 Source 和参考项目资料？
8. 怎样安排开发顺序，尽快做出一个可以验证实际效果的最小可用版本？
9. 哪些问题是我目前没有考虑到、但会影响项目成功的关键问题？

### 四、工作要求

请遵循以下原则：

- 先理解需求，再提出方案，不要急于编写 Agent。
- 不要为了迎合我的想法而直接赞同；发现不合理之处必须明确指出。
- 基于实际工程环境和可验证的技术事实进行分析。
- 区分已确认事实、假设和需要进一步调查的事项。
- 不要假定现有 Framework 的内部结构、实现技术或可复用范围。
- 现阶段只进行只读调查，不修改代码、配置或业务文件，不创建文件。
- 不擅自执行现有 Framework 的开发、测试或部署流程。
- 不直接复制现有 Framework 的实现内容。
- 对技术方案进行必要的可行性、风险和质量分析。

### 五、本次希望得到的回答

**这次先不要开发，也不要一次性输出大量详细设计。**

请先回答：

1. 你对我的真实需求和最终目标的理解。
2. 你对这个方案的专业评价。
3. 你建议采用的总体技术路线及理由。
4. 你认为最大的三个风险。
5. 下一步最应该进行的一项具体工作。

请用通俗中文说明，先给结论，再讲理由。

对于尚未实际调查的 Framework 内容，不得当作已确认事实。

我希望你像一名真正负责项目成败的技术负责人一样独立思考，而不是简单执行我的初步设想。

**回答完成后等待我的确认，再进入下一阶段。**

## 日本語版

あなたは AI Agent アーキテクチャ、AI 駆動開発、および大規模システム開発の専門家として、私の要件を深く分析し、専門的かつ実務的で実現可能な提案を行ってください。

### 一、背景

私は現在、証券システムの案件追加開発に携わっています。

社内には既存の AI 駆動開発 Framework があり、以下の工程を担当する複数の Agent が用意されています。

1. 基本設計
2. 詳細設計
3. プログラム開発
4. 単体テスト
5. 結合テスト

しかし、上司からは、この既存 Framework をそのまま利用せず、自分たちで Agent を開発するよう求められています。

私の考えは次のとおりです。

**まず既存 Framework の各 Agent について、設計、実行の仕組み、作業フローを調査・理解し、それを参考にしながら、案件追加開発に実際に利用できる、より簡素な Agent 体系を独自に設計・実装したいと考えています。**

「参考にする」ことは、そのままコピーすることではありません。既存 Framework の閲覧、再利用、知的財産に関する社内ルールを必ず遵守してください。

### 二、最終的に実現したいこと

- 基本設計から結合テストまでの一連の開発作業を、可能な限り AI が自律的に実施する。
- 私は主に必要な Input の提供、重要事項の確認、成果物の受入確認を担当する。
- 各 Agent が成果物と必要なコンテキストを自動的に引き継ぎ、毎回説明し直さなくて済むようにする。
- 作業の網羅性と正確性を確保し、判断根拠を追跡・検証できるようにする。
- 漏れ、誤解、根拠のない推測、未承認の変更を防止する。
- PDCA の考え方を取り入れ、実行・確認・改善の品質管理サイクルを構築する。
- 過度に複雑な構成を避け、保守・拡張しやすいシンプルな仕組みにする。

案件追加に必要な Input として、Source の基準・所在、本番設計書、テーマID と名称、追加対応一覧、参照先 テーマ、参照先 Source の改修箇所、必要に応じた外部設計を整理済みです。

### 三、重点的に検討してほしい事項

1. 私の基本方針は妥当か。リスクや、より優れた代替案はあるか。
2. 既存 Framework の表面的なプロンプトだけでなく、Agent の実際の動作原理を理解するには、どのように調査すべきか。
3. どの機能を必須として残し、どの機能を統合・簡素化・廃止できるか。
4. 五つの独立した Agent を開発すべきか、それとも別のアーキテクチャが適切か。
5. Agent 間の Input、Output、実行状態、引継ぎをどう設計すべきか。
6. 漏れや事実に基づかない生成を防ぎ、誤りを検出・修正する仕組みをどう実現するか。
7. 既存の Box 設計書、ローカル Source、過去の参照案件資料をどう活用するか。
8. 早期に実案件で検証できる最小実用版を作るには、どの順序で開発すべきか。
9. 私がまだ考慮できていない、プロジェクトの成否に関わる重要な課題は何か。

### 四、作業上の要求

以下を厳守してください。

- まず要件を理解し、その後に方針を提案する。すぐに Agent の実装を始めない。
- 私の考えに迎合せず、不合理な点があれば明確に指摘する。
- 実際の開発環境と検証可能な技術的事実に基づいて分析する。
- 確認済みの事実、仮説、追加調査が必要な事項を明確に区別する。
- 既存 Framework の内部構造、実装技術、再利用可能な範囲を推測で断定しない。
- 現段階では読み取り専用の調査に限定し、コード、設定、業務ファイルを変更せず、ファイルも作成しない。
- 既存 Framework の開発・テスト・デプロイ処理を無断で実行しない。
- 既存 Framework の実装をそのままコピーしない。
- 技術案について実現可能性、リスク、品質面を評価する。

### 五、今回求める回答

**今回は実装を行わず、大量の詳細設計も一度に提示しないでください。**

まず、以下の五点に回答してください。

1. 私の本当の要件と最終目標をどう理解したか。
2. この構想に対する専門的な評価。
3. 推奨する全体技術方針と、その理由。
4. 最も重大と考える三つのリスク。
5. 次に実施すべき、最も重要な具体的作業を一つ。

分かりやすい日本語で、結論を先に述べ、その後に理由を説明してください。

まだ実際に調査していない Framework の内容を、確認済みの事実として扱わないでください。

単に私の初期案に従うのではなく、プロジェクトの成功に責任を持つ技術責任者の立場で、独立して検討してください。

**回答後は私の確認を待ち、承認を得てから次の段階に進んでください。**
