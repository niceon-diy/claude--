# 中文版｜交给「开发 Agent 的 Claude Code」

## 任务

你负责开发用于「项目追加」的 AI Agent 系统。现在必须把下列 R01～R08 做成**开发期间与将来运行期间都有效的工程强制约束**，而不只是写成自然语言指示。

**首先只读调查**当前 AI 驱动开发工程的根目录、现有主／子／既存 Agent、调用流程、配置、参考资料及测试 Framework。不得假设其位置或已存在的功能。先报告确认事实与缺失项，再提出最小改动方案。在未得到修改业务文件的明确授权之前，不得修改业务 Source、正式对应一览或设计书。

## 必须实现的八条规则

**R01｜对应一览优先：** 本次项目追加的「对应一览（対応一覧）」决定改修对象及大致改法。开发每个 Agent 时都要设计「有效版本检查、适用条目确认、范围外拦截、异常提请确认」机制。不能让 Agent 擅自增删改修范围。

**R02｜修改一览强制传递：** 由对应一览和本次用户需求建立「修改一览（変更一覧）」。修改一览确认后，基本设计、详细设计、程序、单体、结合、画面／画面连接测试的每个 Agent 都必须以其为核心输入。开发稳定的修改 ID、版本校验、上游下游传递和覆盖校验；不得允许跳过或用旧版替代。

**R03｜既存改修前后对比：** 开发可复用的类似项目检索、SaaS 改修前后文件定位、Diff 提取及适用性判断流程。形成「前文件／后文件／差异／修改方法／采用理由」证据。历史案例仅指导**怎么改**，不能改变本次**改什么**。缺少可信样例时必须报告阻塞或待确认，不允许生成伪造证据。

**R04｜单体 Case 标准约束：** 单体测试 Agent 必须接收工程内有效的 Case Matrix／Case Pattern，能够追踪每个测试 Case 使用的模式，并校验对修改一览相关项的覆盖。缺少基准或覆盖未达标不得通过。

**R05｜项目独立运行：** 系统只能依赖「AI 驱动开发工程」内获批准的规则、Agent、Skills、工具、脚本和资料。设计项目专用启动与隔离机制，防止运行依赖用户级／全局 CLAUDE.md、个人知识库、个人 Agent 或私有路径。既存类似案例若在外部，应先获授权并导入工程的受控参考区。必须在无个人配置的干净环境验证；单纯写「禁止访问」不足以证明隔离。

**R06｜全链路追溯：** 建立「用户需求 → 对应一览 → 修改一览 → 基本设计 → 详细设计 → 程序 → 测试 Case／结果」的关联契约。关键成果必须带稳定修改 ID、来源版本、文件位置和未确认项。缺失映射或覆盖不足时不允许交付下阶段。

**R07｜不能只靠提示词：** 在可用的 Claude Code 版本上采用 Hook（例如 PreToolUse、SubagentStop、Stop）、独立校验器、权限／沙盒及阶段门禁。工具调用前验证必要输入与授权范围，交付前校验成果和证据。校验失败、检查器异常、必备资料缺失时**默认拒绝**。模型宣称「已阅读」不算程序化证据；自动化无法证明的语义正确性要有人工审核。

**R08｜QA 前必须先调查根本原因并尝试自解决：** 设计所有 Agent 共通的「QA 前分析门禁」，防止 Agent 将可自行调查的问题直接推给用户。发生疑问时必须先：①明确现象、目标及阻塞工程；②按「规则／判断标准缺失、输入资料缺失或版本错误、调查遗漏、资料矛盾、工具／权限／执行失败、确需用户作业务决策」分类查因；③仅在本工程授权范围内查阅对应一览、修改一览、设计书、代码、历史 Diff、Case Matrix／Pattern、日志，验证是否已有答案；④能自解决则解决并记录依据，不能自行确认则整理可选方案及推荐；⑤确实需要用户补充不可访问资料、授权或作业务判断时，才允许发出 QA。开发 QA 结构化记录／校验器，检查「问题ID、关联改修ID、现象、根因分类、已查资料和证据、已尝试解决动作、仍不能自解的原因、方案／推荐、具体需要用户决定的一件事、影响与紧急度」。资料缺失不等于直接问用户；检索未完成、只有笼统问题、缺乏根因和调查证据的 QA 应拒绝发出并退回调查。涉及权限／安全／不可逆业务判断时不得擅自操作，应在必要调查后请求授权。Hook 可以验证记录字段与证据存在，语义分析是否充分须配合复核，不能虚称完全自动保证。

## 落地要求

1. **开发时约束：** 在 Agent 设计、代码修改、调用既存 Agent、调试的各关键环节验证 R01～R08。
2. **运行时约束：** 提供可随 Agent 一起交付的规则、Hook／校验器、配置、项目参考目录、启动方式。**不要**要求使用者额外安装开发者个人环境。
3. **强制输入清单：** 对应一览、修改一览（或生成阶段必需的输入）、参考类似项目、Case Matrix／Pattern 等均须定义路径解析方式、版本和适用阶段；资料不存在时明确拦截，不得凭空补造。
4. **明确门禁：** 每条 R 规则列出触发时点、校验字段／证据、通过条件、拒绝信息、日志及人工作业节点。
5. **正反向测试：** 正常项目应放行；修改一览缺失或过期、无历史差异却宣称已调查、Case Matrix 未加载、个人目录访问、改修范围外文件修改、未调查即发出 QA 等情况必须拦截。
6. **交付测试：** 在不含个人规则／知识库的干净环境中运行，确认 Agent 及所调用的既存 Agent 无隐藏依赖。仅项目权限无法屏蔽的外部／全局配置，要写明额外环境隔离措施。
7. **禁止假完成：** 未安装、未验证、无法自动验证都逐项列为未完成／未确认。不得声称实现了绝对隔离或 100% 理解语义。
8. **权限边界：** 仅改动授权的 AI 驱动开发工程内容；公司项目没有采用 Git 时不要擅自执行 Git 操作。

## 输出（只需实用结果）

按 R01～R08 输出：`规则ID｜开发时约束位置｜运行时强制检查点｜阻止条件｜验证用例｜实施状态｜证据路径`。

然后明确**唯一的下一步**。只有测试通过才能写「已实施并验证」。

# 日本語版｜「Agent を開発する Claude Code」に渡す

## タスク

あなたは案件追加用 AI Agent システムの開発担当です。以下の R01～R08 を**開発時と将来の実行時の両方で有効となる強制制御**として実装してください。自然言語による指示の追加だけでは不十分です。

**最初に読み取り専用で**AI駆動開発工程のルート、親／子／既存 Agent、呼出しフロー、設定、参考資料、テスト Framework を調査してください。構成や機能の存在を仮定してはいけません。確認事実と不足事項を報告し、最小限の変更案を提示してください。明示的な許可なしに業務 Source、正式な対応一覧、既存設計書を変更してはいけません。

## 必ず実装する八つのルール

**R01｜対応一覧最優先：** 今回の案件追加の「対応一覧」が改修対象と概略の改修方針を定義します。各 Agent に有効版・対象項目の確認、範囲外変更の拒否、例外時の承認待ち処理を実装してください。Agent に無断で範囲を変更させてはいけません。

**R02｜変更一覧の必須引継ぎ：** 対応一覧と今回の要求から「変更一覧」を作成します。確定後、基本設計、詳細設計、プログラム、単体試験、結合試験、画面／画面間接続試験の全 Agent に最重要入力として渡してください。安定した変更 ID、版照合、引継ぎ・網羅性検証を設け、省略や旧版利用を阻止してください。

**R03｜過去の改修前後差分の調査：** 類似案件検索、特に SaaS の改修前／改修後ファイル特定、Diff 抽出、今回への適用判断を共通機能として整備してください。「変更前／変更後／差分／改修方法／採用理由」を証跡化してください。過去事例は**改修方法**の参考であり、今回の**改修範囲**を変更できません。根拠がなければ未確認として止めてください。

**R04｜単体 Case の規約：** 有効な Case Matrix／Case Pattern の参照を必須入力とし、各 Case がどのパターンに対応するかと、変更一覧の改修項目がカバーされているかを検査してください。基準不足・未達は不合格です。

**R05｜工程内だけで完結：** 許可済みの AI 駆動開発工程内のルール、Agent、Skills、ツール、スクリプト、資料のみで動作する構成にしてください。ユーザーレベル／グローバル CLAUDE.md、個人ナレッジベース、個人 Agent や私有パスへの依存は禁止です。外部の参考事例は承認後に工程内へ登録します。個人設定を持たないクリーン環境で検証し、指示文だけで隔離できたと判断しないでください。

**R06｜工程間のトレーサビリティ：** 「ユーザー要求 → 対応一覧 → 変更一覧 → 基本設計 → 詳細設計 → プログラム → テスト Case／結果」の対応契約を実装します。成果物には変更 ID、出典版、証跡位置、未確定事項を残し、対応漏れのある成果物を次工程へ渡さないでください。

**R07｜実効性のある強制制御：** 実際の Claude Code バージョンで利用可能な Hook（例：PreToolUse、SubagentStop、Stop）、独立検証プログラム、権限／サンドボックス、工程ゲートを組み合わせてください。必須資料不足、範囲外アクセス、検証失敗、検査器の異常時は**原則拒否（fail closed）**とします。Agent の「確認済み」という自己申告だけでは合格とせず、意味的判断が必要な場合は人手の承認を設けてください。

**R08｜QA 提出前に根本原因を分析し、自己解決を試みる：** すべての Agent に共通の「QA 提出前ゲート」を実装し、Agent が自ら調査できる問題をそのまま利用者へ丸投げしないでください。疑問が生じたら、①現象・期待結果・停止工程を明確化、②「ルール／判断基準不足、入力資料不足または版違い、調査不足、資料間矛盾、ツール／権限／実行エラー、業務判断が必要」のいずれかに分類して原因を分析、③本工程で許可された対応一覧・変更一覧・設計書・Source・過去 Diff・Case Matrix／Pattern・ログを調査し既存の答えを確認、④自己解決できれば根拠を記録して解決、できなければ選択肢と推奨案をまとめ、⑤必要な資料・権限・業務判断が本当に利用者にしか提供できない場合のみ QA を提出してください。「問題ID、変更ID、現象、原因分類、確認資料と証跡、試行済み対策、自己解決不能の理由、選択肢／推奨案、利用者に判断してほしい一事項、影響・緊急度」を必須とする QA 記録・検証器を実装してください。資料が足りないだけで即質問してはいけません。調査不足、抽象的な質問、原因や証跡のない QA は拒否し、調査へ差し戻してください。権限・安全・不可逆な業務判断は無断実施せず、必要な調査後に承認を求めてください。Hook によるフィールド・証跡確認だけで意味的な調査十分性が保証されると主張してはいけません。

## 実装・検証・引継ぎ

1. Agent の設計・改修・既存 Agent 呼出し・デバッグ時にも各ルールを適用してください。
2. 実行時に必要なルール、Hook／検証器、設定、参照ディレクトリ、起動方法を Agent と一緒に配布してください。開発者の個人環境を必須にしないでください。
3. 対応一覧、変更一覧、類似案件、Case Matrix／Pattern の保存場所・有効版・適用工程・欠落時の拒否条件を定義してください。
4. 各ルールの発火タイミング、検査項目、許可／拒否条件、ログ、人手レビューを明文化してください。
5. 正常系と、変更一覧欠落・旧版利用・過去 Diff 未調査・Case Matrix 未読込・個人ディレクトリアクセス・範囲外改修、調査なしで QA を提出するケースなどの異常系をテストしてください。
6. 個人設定なしのクリーン環境で、親／子／既存 Agent の依存関係を検証してください。プロジェクト設定だけで防げない外部設定には追加の隔離策を設けてください。
7. 未実装・未検証・自動検証不可は明示し、完全な隔離や意味理解を誇張してはいけません。
8. 許可された AI 駆動開発工程のみを変更し、会社の工程で Git を利用していると仮定しないでください。

## 出力

R01～R08 ごとに `ルールID｜開発時の制御箇所｜実行時チェックポイント｜拒否条件｜テストケース｜実装状態｜証跡パス` を簡潔に記載し、**次の作業を一つだけ**示してください。テストが成功したものだけ「実装・検証済み」としてください。
