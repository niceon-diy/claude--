# 中文版｜可直接交给 Claude Code

## 角色与任务

你负责在当前「AI驱动开发工程」中落实下列七条**强制规则**，适用于主 Agent、子 Agent、既存 Agent 的调用链，以及 Agent 的开发、调试和正式运行。

这些要求不是供参考的提示词。必须调查当前工程结构，将规则落实为可验证的输入契约、阶段检查、Hook／权限限制及输出校验。**不得仅把规则加入上下文或 CLAUDE.md 后就宣称完成。**

首先只读检查工程实际目录、现有 Agent、调用关系、输入文件、规则文件与 Hook 配置，列明「已确认／未确认」。不能假设文件已经存在；文件位置、项目结构和工具能力不明时，应报告缺口，不得编造。

## R01｜对应一览是改修范围的最高依据

1. 本次项目追加的「对应一览（対応一覧）」决定**哪些对象要改、各对象大致怎么改**。
2. 每个相关 Agent 开工前必须核对当前有效的对应一览版本、适用范围和关联条目。
3. 未经确认，不得自行增加、删除、替换或改变改修范围。
4. 如果发现漏项、依赖、矛盾或描述不足，应记录证据、提出确认事项；不得悄悄扩大范围。

## R02｜修改一览是后续工程的核心执行输入

1. 依据对应一览及相关用户需求生成本次项目追加的「修改一览（変更一覧）」。
2. 修改一览必须记录改修对象、改修内容、来源对应一览条目、需求关联、状态和版本。
3. 修改一览经确认后，**基本设计、详细设计、程序开发、单体测试、结合测试、画面及画面连接测试**等后续 Agent 都必须读取并核对其有效版本。
4. 后续工程不得跳过修改一览，也不得用自身推测或旧版本替代它。
5. 未被修改一览覆盖的新增改修，先登记待确认，取得确认后更新修改一览，再继续执行。

## R03｜修改方法必须先调查既存类似项目

1. 当对应一览只有改修方向、缺少细节时，必须优先调查工程内可访问的既存类似开发案例。
2. 特别是 **SaaS 相关开发**，应定位过去类似项目的**修改前、修改后**资料，比较差异（Diff），归纳具体修改方法。
3. 保存参考项目、前后文件路径、差异位置、适用条件，以及本次采用／不采用的理由。
4. 既存案例是**实现方法的参考依据**，不能覆盖本次对应一览和已确认修改一览所规定的范围。
5. 找不到可信类似案例、差异不明或适用性无法确认时，标记为未确认／阻塞；不得凭空推断已经核实的修改方法。

## R04｜单体测试 Case 必须依据既存测试标准

1. 编写单体测试 Case 之前，必须读取本工程内有效的 **Case Matrix** 和 **Case Pattern**。
2. 根据修改一览及设计内容选择适用模式，并记录 Case 与 Matrix／Pattern 条目的对应关系。
3. 必须核对测试覆盖修改一览中的相关修改项，说明不适用项和例外原因。
4. 缺少 Matrix／Pattern、版本不明或覆盖不足时，不得将测试 Case 标为完成；不得任意编造测试标准。

## R05｜禁止依赖工程外部的个人资料与全局规则

1. Agent 的开发、运行和交付必须**仅使用「AI驱动开发工程」内允许使用的规则、资料、Agent、Skills、脚本及配置**。
2. 禁止依赖个人知识库、用户级／全局 `CLAUDE.md`、个人 Skills、个人 Agent 或本机私有路径。
3. 既存类似项目和测试资料如原本不在工程内，须先按授权复制／登记为可移交的工程参考输入；不能运行时偷偷读取个人目录。
4. 应检查启动配置、继承规则、工具权限及文件访问范围；仅靠提示词声明不能视为隔离成功。
5. 必须在不含个人配置和个人知识库的干净环境中验证可移植性；不能将本机运行成功等同于他人环境可运行。

## R06｜需求到测试必须全程可追溯

必须保留以下关联：

**用户需求 → 对应一览 → 修改一览 → 基本设计 → 详细设计 → 程序 → 测试 Case／测试结果**

1. 为改修项保留稳定 ID，并记录所引用资料的版本／基准。
2. 各阶段成果须列明对应改修 ID、来源、证据位置和未解决事项。
3. 任何无法追溯来源、无法解释修改理由或与当前修改一览不一致的成果，不得直接进入下一阶段。

## R07｜必须有真正的强制执行与失败阻断

1. 将 R01～R06 逐一映射到**检查时点、检查输入、通过条件、拒绝条件、错误提示和证据记录**。
2. 对关键工具调用采用适当的 **PreToolUse** 等 Hook、权限／沙盒限制；对 Agent 结束及成果交付采用适当的 **SubagentStop、Stop** 或独立校验程序。具体能力和事件名称必须先核对本机 Claude Code 版本。
3. 在阶段入口检查必备文件及版本；在阶段出口验证修改 ID 覆盖、来源关联、文件差异和输出契约。
4. 缺少依据、越界访问、版本不一致、校验失败或检查程序自身报错时，采用**默认阻止（fail closed）**，禁止把阶段标记为成功。
5. 不能用“Agent 说自己已经阅读／确认”代替程序化检查；对无法自动判定的语义正确性，明确设置人工复核点。
6. 必须执行正向与反向测试：合规输入允许执行；缺失修改一览、跳过 Case Matrix、访问个人目录、超范围修改等情形必须被拦截。

## 执行顺序与交付要求

按以下顺序处理，不得跳步：

1. **现状调查**：确认工程根目录、既存 Agent、实际输入路径和现有强制机制。
2. **规则落地方案**：列出 R01～R07 分别放在哪里、由什么 Hook／校验器执行、何时拒绝。
3. **实施**：仅在当前工程内、已授权范围中创建或修改规则、Hook、校验器及测试；**未经明确授权，不修改业务 Source、正式对应一览或既存设计书**。不要假设公司工程已使用 Git。
4. **验证**：逐条出示通过／拒绝测试的结果、证据位置，以及尚未覆盖的限制。
5. **交接**：写明其他人在干净环境下的启动方法、必要输入、通过条件与失败处理。

**输出格式（简洁）：** `规则ID｜控制位置｜检查条件｜拒绝条件｜验证结果｜证据位置`。

任何一项未实际实施或未验证，均标为「未完成／未确认」，不得声称七条规则已经强制生效。

# 日本語版｜Claude Code にそのまま渡せる実行プロンプト

## 役割とタスク

あなたは現在の「AI駆動開発工程」において、以下の七つの**強制ルール**を実装する担当者です。対象は、親 Agent・子 Agent・既存 Agent の呼び出し経路、および Agent の開発・デバッグ・本番実行の全段階です。

これらは参考用の指示ではありません。現行の工程構成を調査したうえで、検証可能な入力契約、工程ゲート、Hook／権限制限、成果物検証として実装してください。**コンテキストや CLAUDE.md に記載しただけで完了と判断してはいけません。**

最初に工程の実ディレクトリ、既存 Agent、呼び出し関係、入力ファイル、ルールおよび Hook 設定を読み取り専用で確認し、「確認済み／未確認」を区別してください。ファイルや機能が存在するものと仮定せず、不明点は不足事項として報告してください。

## R01｜追加対応一覧を改修範囲の最上位根拠とする

1. 今回の案件追加における「対応一覧」は、**何を改修するか、概ねどのように改修するか**を定めます。
2. 各 Agent は着手前に、対応一覧の有効版・適用範囲・該当項目を必ず照合してください。
3. 承認なしに改修対象を追加・削除・置換したり、改修範囲を変更したりしてはいけません。
4. 漏れ、依存関係、矛盾、記述不足を発見した場合は根拠を記録して確認事項を提示し、無断で範囲を広げてはいけません。

## R02｜変更一覧を後続工程の最重要入力とする

1. 対応一覧および関連するユーザー要求から、今回の案件追加用の「変更一覧」を作成してください。
2. 変更一覧には、改修対象・改修内容・元の対応一覧項目・要求との関連・状態・版を記録してください。
3. 確認済みの変更一覧は、**基本設計、詳細設計、プログラム開発、単体試験、結合試験、画面および画面間接続試験**など、後続すべての Agent が参照・照合しなければなりません。
4. 変更一覧の参照を省略したり、推測や旧版で代用したりしてはいけません。
5. 変更一覧にない改修が必要になった場合は、確認待ちとして登録し、承認後に変更一覧を更新してから進めてください。

## R03｜改修方法は既存類似案件の改修前後から調査する

1. 対応一覧に改修方針しか書かれておらず詳細が不足する場合、工程内で利用可能な既存類似案件を優先して調査してください。
2. 特に **SaaS 関連開発**では、過去の類似案件について**改修前・改修後**の資料を特定し、差分（Diff）から具体的な改修方法を抽出してください。
3. 参考案件、改修前後のファイルパス、差分箇所、適用条件、今回の採否理由を記録してください。
4. 既存案件は**実装方法の参考**であり、今回の対応一覧・確認済み変更一覧が定める改修範囲を上書きしてはいけません。
5. 信頼できる類似案件がない、差分が不明、適用可否を確認できない場合は、未確認／ブロックとして扱い、検証済みの方法であるかのように推測してはいけません。

## R04｜単体試験 Case は既存テスト基準を根拠とする

1. 単体試験 Case の作成前に、工程内の有効な **Case Matrix** と **Case Pattern** を必ず読み込んでください。
2. 変更一覧および設計内容に対応するパターンを選定し、各 Case と Matrix／Pattern 項目の関連を記録してください。
3. 変更一覧の該当改修項目がテストでカバーされていることを確認し、対象外・例外は理由を明示してください。
4. Matrix／Pattern の欠落、版の不明、カバレッジ不足がある場合、Case を完了扱いにしてはいけません。基準を勝手に作ってはいけません。

## R05｜工程外の個人資料およびグローバルルールへの依存を禁止する

1. Agent の開発・実行・配布では、**「AI駆動開発工程」内部で利用を許可されたルール、資料、Agent、Skills、スクリプト、設定のみ**を使用してください。
2. 個人ナレッジベース、ユーザーレベル／グローバルの `CLAUDE.md`、個人 Skills、個人 Agent、ローカル固有パスに依存してはいけません。
3. 既存類似案件や試験資料が工程外にある場合は、許可を得て工程内の引継ぎ可能な参照入力として複製・登録してください。実行時に個人ディレクトリを無断参照してはいけません。
4. 起動設定、継承ルール、ツール権限およびファイルアクセス範囲を検査してください。プロンプトで禁止を宣言するだけでは、隔離の達成とはみなしません。
5. 個人設定と個人ナレッジベースのないクリーン環境で移植性を検証してください。自分の端末での成功だけをもって他者環境でも動作すると判断してはいけません。

## R06｜要求からテストまでの追跡可能性を確保する

次の関連付けを維持してください。

**ユーザー要求 → 対応一覧 → 変更一覧 → 基本設計 → 詳細設計 → プログラム → テスト Case／テスト結果**

1. 改修項目に安定した ID を設定し、参照資料の版・基準を記録してください。
2. 各工程の成果物に、対応する改修 ID、出典、根拠箇所および未解決事項を記載してください。
3. 出典を追跡できない、改修理由を説明できない、現行の変更一覧と不整合がある成果物は、次工程へ渡してはいけません。

## R07｜強制制御と失敗時のブロックを実装する

1. R01～R06 それぞれに、**検査タイミング、入力、合格条件、拒否条件、エラーメッセージ、証跡**を定義してください。
2. 重要なツール呼び出しには適切な **PreToolUse** 等の Hook と権限／サンドボックス制限を、Agent 終了時と成果物引渡し時には適切な **SubagentStop、Stop** または独立検証プログラムを使用してください。利用可能なイベントと動作は、導入済み Claude Code のバージョンで確認してください。
3. 工程開始時に必須ファイルと版を検査し、工程終了時に改修 ID の網羅性、根拠との関連、ファイル差分および出力契約を検証してください。
4. 根拠不足、許可範囲外へのアクセス、版の不一致、検証失敗、検査プログラム自体のエラーが発生した場合は、**原則として拒否（fail closed）**し、成功扱いにしてはいけません。
5. 「Agent が読んだ／確認したと回答した」ことを機械的検査の代わりにしてはいけません。意味上の正確性を自動判定できない場合は、人によるレビューを必須としてください。
6. 正常系と異常系の両方を試験してください。正しい入力は通過し、変更一覧の欠落、Case Matrix の未参照、個人ディレクトリへのアクセス、改修範囲外の変更は阻止できなければなりません。

## 実行順序と成果物

次の順序で実施し、省略してはいけません。

1. **現状調査**：工程ルート、既存 Agent、実際の入力パス、既存の強制制御を確認する。
2. **実装方針**：R01～R07 の配置先、適用する Hook／検証器、拒否条件を一覧化する。
3. **実装**：現工程内の許可された範囲でルール、Hook、検証器、テストを作成・修正する。**明確な許可なく業務 Source、正式な対応一覧、既存設計書を変更しない**。会社の工程で Git が使われていると仮定しない。
4. **検証**：ルール別の許可／拒否テスト結果、証跡場所、未対応の制約を示す。
5. **引継ぎ**：他者がクリーン環境で起動する手順、必須入力、合格条件、異常時の対処を記載する。

**出力形式（簡潔）：** `ルールID｜制御箇所｜検査条件｜拒否条件｜検証結果｜証跡場所`。

未実装・未検証の項目は必ず「未完了／未確認」とし、七つのルールが強制的に有効になったと主張してはいけません。
