# 中文版｜交给公司 Claude Code 的执行提示词

## 0. 任务定位
本次任务为**Step5 QA 全量逆向追踪 + 对应一览与 Step3 改修一览生成机制的质量整改评审**。

注意：当前用户称 Step3 为「制作改修一览」阶段，Step5 为「发生不明点／QA」阶段，但不同历史版本的 Step 编号可能不同。你必须**先只读核对实际 Agent、脚本及处理流程中 Step3/Step5 的定义**，按实际职责映射处理，不得擅自假定。

**本次必须先做完整报告并供用户审核；未得到明确批准，不得修改公司正式对应一览、改修一览、设计书、程序或现有 Agent 代码。** 可只读调查、生成候选差分与新报告；若获得对具体文件的写入授权，仍须执行备份／版本记录与变更后验证。

## 1. 必须完成的检查范围
1. 全量搜索 Step5 QA、不明点、保留、TODO/TBD、错误、警告、Agent 日志、子 Agent 返回文本及未映射对象，**不得抽样或仅扫描 QA 文件**。
2. 对每项设立 QA-ID，并保留发现位置、受影响对象、关联対応ID／改修ID、版本、原始描述、复现条件及证据路径。
3. 回溯对应一览 → Step3 输入 → Step3 生成及校验 → 改修一览 → 下游 Agent 交接 → Step5。逐项判定究竟是上游清单漏写、Step3 误生成、交接失败，还是 Step5 独立问题。
4. 发 QA 前必须独立查阅可访问的需求、设计、Source、类似案件修改前后 Diff、IF/API、画面、画面关联 CSV、日志和标准。先找根因并自解决；不能把可自行调查的问题原封不动交给用户。
5. 用**正向＋反向覆盖矩阵**保证 Step5 每项都有归属、上游每项都被接收；未确认的不能冒充已解决。

## 2. 对应一览（対応一覧）拟改方案：先论证，再提出精确差分
以本次项目的正式对应一览为最高范围基准，核对既存模版和实际版本。

### 2.1 分类及排序
优先检查以下用户既定分类是否已在正式模板实现，**仅缺失或错误时提出最小修订**：
01 DB（主要表优先 → 相关表 → VIEW／设定数据）；
02 外部 API；
03 IF；
04 画面；
05 画面关联 CSV；
06 OL 机能；
07 BT 机能。
**不擅自新增「帳票」分类。** Source、类、方法、SQL 等作为改修对象索引／关联清单，不重复登记为新的业务需求。现有正式分类与此不同时，写明差异及实际影响，不得直接覆盖。

### 2.2 主表字段保留、补充追踪能力
优先保留业务人员易读的核心字段：**ID｜名称｜概要説明｜改修内容**，不要为治理而将正文表格无限加宽。
建议建立同文件中的「追踪／证据 Sheet」或同目录配套表，至少包含：
対応ID、对象区分、正式对象键／文件、对应一览版本、来源章节／证据、确定状态（確定／要確認）、关联改修ID、关联QA-ID、最后复核日期。
若现有模板已有同等字段，复用，不重复新增；若现有环境不适合增加 Sheet，提出兼容性更好的索引方案。

### 2.3 内容质量修订
逐项检查：① DB 主表项目新增是否为起点；② API、IF、画面／CSV、OL／BT 是否遗漏；③ 对象及关联 ID 是否唯一；④ 现行与改修后差异是否表达清楚；⑤ 是否将设计实现方法误当业务范围；⑥ 未确认事项是否有明确位置、影响和待定责任；⑦ 是否重复登记同一改修。
如对应一览本身遗漏、矛盾或需要扩大／缩小范围，只能提出**变更前／变更后／理由／证据／影响／审批要求**的候选差分，业务决策批准后才能写入正式清单。

## 3. Step3（改修一览生成）拟改方案：必须审查和设计的 8 个节点
请先画出**实际** Step3 处理链，列出输入、调用 Agent、输出、检查器、现状和缺陷证据。然后分别审查：

S3-01 **输入基准冻结**：对应一览、业务需求、设计书、稳定 Source、类似项目与外部定义的路径、版本、hash、适用范围；旧版或缺失时阻断。
S3-02 **全量对象读取**：读取各分类及子表，多 Sheet／多文件不漏项，保留所有対応ID；覆盖 DB→API→IF→画面→CSV→OL→BT。
S3-03 **影响展开**：针对每项追踪 DB 字段→引用／更新 SQL→Source／程序→接口／画面／CSV→测试条件，区分影响あり／なし／要確認并附证据，不在无证据时推断。
S3-04 **原子化改修项**：同一业务要求涉及多个对象时拆成可执行最小改修项；稳定改修ID、唯一对象、改修前／后、改修理由、文件／类／方法／DB／IF、来源対応ID、依赖项、证据、确认状态。
S3-05 **类似案件差分验证**：从获授权的既存类似项目查改修前／后文件，提取 Diff、适用前提、采用或不采用理由；仅决定“怎么改”，不能自行扩大“改什么”。
S3-06 **双向覆盖及矛盾验证**：对应ID→改修ID 无漏项、改修ID→对应ID 无孤儿；冲突、重复、缺证据、待确认、适用范围外均可检出，不能静默略过。
S3-07 **QA 前根因分析**：任何不明点先核对输入、版本、设计、代码、日志、Agent 交接与遗漏；可解决的在授权范围内修正并留证；真正业务决策／权限／必要资料不可访问才形成结构化 QA。
S3-08 **Step3 出口门禁和下游交接**：输出版本化改修一览、覆盖矩阵、未决项、证据索引、Agent 交接清单；下游逐项确认已读取相同版本和改修ID；失败则停止交接，不把“已生成文件”当“内容正确”。

**审查每个节点时必须报告：当前实现、发现证据、风险、建议改法、变更文件／Agent、必要权限、预期效果、验收方法、是否待审批。禁止直接声称某节点目前缺失。**

## 4. Step5 的每条 QA 如何回写
每条 QA 以以下唯一主因分类，并注明多个次因：
A 对应一览缺失／矛盾 → 提交对应一览候选修订，批准后同步改修一览；
B Step3 抽取／判断／生成错误 → 修正 Step3 逻辑或规则、重新生成受影响改修项；
C Step3→Step5 传递／版本错误 → 修复交接，不乱改业务范围；
D 下游或 Step5 独立错误 → 当前阶段修复并标明不回写理由；
E 资料冲突 → 证据比对并作差异评审；
F 工具／权限错误 → 按批准边界处理，阻塞时保留；
G 业务规则必须决定 → 给出选项、证据、推荐及一个明确待决问题，不可擅断。

为每个 QA 给出：
QA-ID｜Step5 原始位置｜根因与证据｜对应ID｜改修ID｜需改文件／Sheet／行｜**对应一览准备怎么改**｜**Step3 准备怎么改**｜变更前／后｜权限／审批｜复验结果｜状态。
只要未实际审批、修改及验证，必须写“建议／待确认”，不可写“已反映”。

## 5. 必须先提交完整 HTML 评审报告
请生成一个**独立可打开、可打印**的 HTML 文件，标题《Step5 不明点全量检查与对应一览／Step3 改修方案评审报告》。报告中文在前，日文在后；至少有：

1. 结论摘要与调查范围、证据基准、实际 Step3／Step5 定义；
2. Step5 QA 全量数量、分类、去重和证据索引，未读取范围；
3. **对应一览现状→问题→详细修改提案**：分类、字段、追踪 Sheet、逐项修改前后、影响、审批；
4. **Step3 现状→问题→详细修改提案**：S3-01～08 每个节点的实际 Agent／脚本／文件、改修方法、门禁、证据、复测；
5. QA-ID ↔ 对应ID ↔ 改修ID 的**双向追踪矩阵**及每项回写去向；
6. 对应一览与改修一览的拟修订差分表（不得仅写原则）；
7. 正反向测试案例、成功标准、失败与阻断条件；
8. 风险／权限边界／回退方式、变更顺序与工时依赖（未知则不编造）；
9. 待用户逐项审核的决定、正式验收清单和 Step5 PASS／BLOCKED／NOT_VERIFIED 结论；
10. 日文版对应结论和关键差分，必要时完整译出供团队审查。

任何看不到的实际文件、问题数量、代码位置或测试结果用**「未取得／未验证」**标明，禁止虚构。报告应能独立阅读，正文不依赖聊天记录。

## 6. 正式验收与交付限制
- **Step5 的“零残留 QA”是零未归属、未调查、未处理 QA，而不是删除真实阻塞。** 有未获业务批准的关键 QA 时，Step5 结果必须为 BLOCKED。
- 本次先输出**评审报告与候选 Patch**，等待明确批准再动正式清单、规则、脚本／Agent；不得改业务 Source 或设计书。
- 通过后要重新运行 Step3，校验版本与双向覆盖，再运行／复核 Step5，证明同一问题不再出现。没有复验就不能标 PASS。
- 不假设公司使用 Git；所有公司工程内路径、证据存储和版本机制以现实环境为准。项目成果放项目内 document／output，跨项目输出目录只放共通成果。
- 汇总必须包含：QA总数｜A～G根因分布｜对应一览拟改数｜Step3拟改节点数｜已批准数｜已实际修订数｜已复验数｜保留阻塞数｜Step5最终判定。
- 最终给出**唯一下一步**及所需用户审批点，不要抛回可自行调查的 QA。

# 日本語版｜社内 Claude Code への実行プロンプト

## 0. 位置付け
本件は **Step5 の QA／不明点の全件遡及調査、対応一覧および Step3 の改修一覧生成処理の品質改善レビュー**です。

利用者は現時点で Step3 を「改修一覧の作成」、Step5 を「QA／不明点の発生工程」と呼んでいます。ただし旧版と工程番号が異なる可能性があるため、**実際の Agent／スクリプトの定義を読み取り専用で確認し、工程の役割を確定**してください。

**最初に正式な HTML レビュー報告書を提出してください。利用者の明示的な承認前に、社内の正式な対応一覧、改修一覧、設計書、業務 Source、既存 Agent 実装を変更してはいけません。** 読み取り専用調査、差分案、レポート作成は可能です。許可を得た変更には版管理と事後検証が必要です。

## 1. Step5 の不明点を全件調査
Step5 の QA 台帳だけでなく、要確認、保留、TODO/TBD、エラー、警告、Agent／Subagent 応答、ログ、対応 ID 不明の出力まで全量調査してください。抽出範囲と未調査範囲を明記してください。

各課題に QA-ID を付し、原文の所在、対象、対応 ID／改修 ID、入力版、再現条件、証跡を記録します。**対応一覧 → Step3 入力 → Step3 の抽出／生成／検証 → 改修一覧 → 後続 Agent 引継ぎ → Step5** を逆向きに追跡し、漏れ、誤判定、版不一致、引継ぎ不備、Step5 固有の問題を区別してください。

QA 提出前に設計書、Source、IF/API、画面関連 CSV、既存案件の改修前後 Diff、ログ等を調べ、自力で解決できる事項は根拠とともに解決してください。安易に利用者へ調査を丸投げしないでください。

## 2. 対応一覧の改訂提案
**対応一覧が改修範囲の最上位基準**です。現行テンプレートを確認し、不足している点のみ最小限の改訂を提案してください。

推奨される並び（正式版との相違は必ず示す）：
01 DB（主要テーブル→関連テーブル→VIEW／設定データ）
02 外部 API
03 IF
04 画面
05 画面関連 CSV
06 OL 機能
07 BT 機能

「帳票」を無断追加しないでください。Source／クラス／メソッド等は原則として参照索引であり、業務上の改修要求を重複登録しません。

主たる表示列 **ID｜名称｜概要説明｜改修内容** は極力維持してください。対応ID、対象区分、正式対象キー、版、根拠箇所、確定／要確認状態、関連改修ID、QA-ID、レビュー日付を管理する追跡 Sheet または付属索引を提案し、既存項目があれば再利用してください。

各提案は「現行→修正案→必要理由→証跡→影響→承認要否」を記載します。改修範囲や業務判断の変更は、承認があるまで**候補差分**にとどめてください。

## 3. Step3 の改修一覧生成処理：8 つの検討点
実際の Step3 の入出力、起動 Agent、呼出し先、スクリプト、検証器、成果物を調べた上で、次の 8 点をそれぞれ検討してください。

- **S3-01 入力ベースライン固定**：対応一覧、要求、設計、安定 Source、参照案件のパス・版・ハッシュ・適用範囲を確認。欠落／旧版は停止。
- **S3-02 全件取込み**：全カテゴリ・全 Sheet・全ファイル・全対応 ID を取得し、DB→API→IF→画面→CSV→OL→BT の漏れを防止。
- **S3-03 影響調査**：DB 項目から SQL・Source・プログラム・IF／API・画面／CSV・試験条件まで追跡。「影響あり／なし／要確認」を証跡付きで明示。
- **S3-04 改修項目の原子化**：安定した改修 ID、変更前／後、対象、理由、出典対応 ID、依存、証跡、確定状態をもつ実行可能な単位へ展開。
- **S3-05 類似案件 Diff**：承認済み過去案件の改修前後を比較し適用可否を証跡化。実装方法の参考として使用し、勝手に改修範囲を拡大しない。
- **S3-06 双方向網羅性検証**：対応 ID→改修 ID、改修 ID→対応 ID を照合。漏れ、重複、根拠不足、矛盾、対象外を検出。
- **S3-07 QA 発行前の原因分析**：入力・版・設計・Source・ログ・引継ぎの調査と自己解決を先行。本当に業務判断／権限／入手不能資料が必要な時のみ根拠付き QA。
- **S3-08 出口ゲート／引継ぎ契約**：版管理された改修一覧、対応マトリクス、未決事項、証跡索引を出力し、下流 Agent が同一版・全改修 ID を受領したことを検証。失敗時は次工程へ渡さない。

各項目を「現状の実装｜証跡｜実際の不備｜具体的改修箇所｜承認要否｜正常／異常系テスト｜結果」で報告してください。存在しない不備を推測で断定してはいけません。

## 4. QA の上流フィードバックルール
原因を次の区分で分類してください。

A 対応一覧の欠落／矛盾 → 修正案を提出し、承認後に対応一覧・改修一覧を同期。
B Step3 の抽出／判断／生成ミス → Step3 の処理を修正し、影響項目を再生成。
C Step3→Step5 の版／引継ぎミス → 引継ぎを修正し、業務範囲を無用に変更しない。
D Step5 または後続工程固有の問題 → 当該工程で修正し、上流に反映しない理由を記録。
E 参考資料間の矛盾 → 証跡比較と差分レビュー。
F ツール／権限の問題 → 承認範囲内で対処し、必要なら BLOCKED。
G 業務判断が不可欠 → 選択肢、推奨根拠、具体的質問、影響を提示し、無断決定しない。

各 QA について
「QA-ID｜Step5 発見箇所｜根本原因｜対応ID｜改修ID｜改訂対象／位置｜**対応一覧をどう直すか**｜**Step3 をどう直すか**｜変更前／後｜根拠｜承認要否｜再検証｜状態」
を必須としてください。未承認や未反映は「提案／承認待ち」と区別してください。

## 5. 先に提出する HTML 評審報告書
単独で表示・印刷できる HTML「Step5 不明点全量点検と対応一覧／Step3 改修方針レビュー報告書」を生成してください。**中国語を前半、日本語を後半**にします。

必須章：要約、調査範囲と資料版、実際の Step 定義、全 QA 台帳と分類、対応一覧の現状／不備／詳細差分、Step3 の S3-01～08 の現状／改修箇所／実装案、QA-ID ↔ 対応ID ↔ 改修ID 双方向マトリクス、修正前後の比較、テストケースと出口判定、承認が必要な事項、影響と復旧手段、レビュー用チェックリスト、次の作業。

確認できない件数、ファイル、行番号、テスト成否は **未取得／未検証** と明記し、架空の実績を書いてはいけません。抽象的な方針だけでなく、実際に確認した対象ごとの修正前／修正後の候補差分を示してください。

## 6. 出口条件と報告
「Step5 の残留 QA ゼロ」とは未分類・未調査・放置された QA がゼロという意味であり、必要な業務判断事項を削除する意味ではありません。重要な承認待ちがあれば Step5 は **BLOCKED** です。

最初は調査結果・HTML 報告書・候補 Patch を提出し、明示承認まで正式な成果物や Agent を変更しないでください。承認後は Step3 の再生成、双方向の網羅性検証、Step5 の再実行／再評価により再発防止を検証してください。再検証前の PASS は不可です。

会社工程で Git を使用していると仮定しないでください。プロジェクト成果は当該プロジェクトの document／output に記録し、元資料と QA 原本を保全してください。
