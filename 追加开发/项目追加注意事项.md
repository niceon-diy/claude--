# 项目追加注意事项

整理日期：2026-11-01

本文件记录项目追加时需要准备的 Input、追加对应一览的确认事项，以及 Source 开发所依据的资料。实际项目的路径、テーマID、Source 和 Object 内容由具体公司项目填写，不能将本资料集目录当作业务工程的实际路径。

## 1. Input：项目追加所需资料

| 输入项 | 需要提供的内容 | 用途 |
| --- | --- | --- |
| Source 源头 | 本次开发所基于的 Source 来源及位置 | 确定开发使用的 Source 基础 |
| 本番设计书的位置 | 现行本番设计书的存放位置 | 查阅现行设计内容 |
| テーマID 和名称 | 本次追加对应的 テーマID、名称 | 识别本次 テーマ，并用于建立新 テーマ 的 Box |
| 追加对应一览（核心） | 本次需要追加、修改的项目及具体对应内容 | 明确本次要做什么，作为 Source 开发的主要依据 |
| 过去参考 テーマ 的位置 | 可参考的过去 テーマ 及其资料位置 | 查阅过去的对应资料 |
| 过去参考 テーマ 的 Source 改修位置 | 过去 テーマ 中具体修改过的 Source 及其改修位置 | 为本次 Source 开发提供参考 |
| 外部设计（按需提供） | 尤其是新增项目的说明、具体设计内容 | 补充新增项目的详细要求 |

### 新 テーマ Box 的建立

根据 **Source 源头、本番设计书的位置、テーマID 和名称**等基础信息建立新 テーマ 的 Box。

新 テーマ Box 是接收基础信息后建立的资料容器，不作为独立的 Input 字段。

## 2. 追加对应一览需要确认的内容

### 2.1 以参考 テーマ 的发布模块一览检查 Source 漏项（最关键）

追加对应一览完成后，以参考 テーマ 的 **リリースモジュール一覧（发布模块一览）**为正确资料和核对基准，检查对应一览中的 Source 是否存在遗漏。

确认时需要：

1. 找到参考 テーマ 的リリースモジュール一覧。
2. 按其中列出的 Source，逐项核对追加对应一览。
3. 找出未列入追加对应一览的 Source，确认其与本次追加的关系；属于本次对应范围的，必须在后续经确认的对应一览正式版本更新中补齐。
4. 对范围或对应关系尚不明确的项目，记录待确认内容。

本次新增的 Source，也要结合本次追加要求及外部设计确认，并在该后续正式版本更新中列入对应一览。

本节说明追加开发的一般确认与补齐流程。正式补入属于后续经确认的对应一览版本更新，确认应对应的漏项必须补齐。执行配套 P002“14 个项目追加对应一览核对与参考 Source 差分整理”时，本轮仅调查、保存 Input 和补充建议，不覆盖原对应一览或其他原件；不得把本轮的补充建议误认为正式一览已经更新完成。

**重点：对应一览完成后必须回到参考 テーマ 的リリースモジュール一覧检查，不能仅凭已经写出的对应一览判断没有漏项。**

### 2.2 调查每个 Source 的用途

对应一览中的每个 Source，都要调查清楚：

- 用在什么地方。
- 承担什么具体处理。
- 与本次追加或改修内容有什么关系。

例如，需要区分该 Source 是否用于**文件作成、DB 改修**等处理，并将调查结果记录到对应一览。不能只列 Source 名称而没有用途说明。

### 2.3 结合数据库 Object 一览和 DB 改修内容确认环境

需要准备并对照：

- **数据库的 Object 一览**。
- **DB 改修内容**。

据此确认：

1. 本次涉及哪些数据库 Object。
2. 哪些环境需要改修，例如**休日、LKN**等。
3. 各环境分别涉及哪些 Object。
4. 每个环境、每个 Object 具体需要修改什么内容。

环境范围应逐项确认，不能只写“需要 DB 改修”而没有说明对象、环境和具体内容。“休日”“LKN”沿用项目中的名称，其他环境按实际项目补充。

## 3. Source 开发的依据

Source 开发主要依据以下两项资料开展：

1. **追加对应一览**：说明本次要追加或修改什么。
2. **过去参考 テーマ 的 Source 改修位置**：提供过去类似对应中具体改了哪里、如何改修的参考。

涉及新增项目时，同时结合**外部设计中的新增项目说明和具体设计内容**。

开发前，应先完成对应一览的 Source 漏项检查、用途调查，以及数据库 Object 和改修环境的确认。

## 4. 检查清单

- [ ] Source 源头、本番设计书位置、テーマID 和名称已明确。
- [ ] 新 テーマ 的 Box 已建立。
- [ ] 追加对应一览、过去参考 テーマ 位置及其 Source 改修位置已准备。
- [ ] 已按需准备外部设计，并确认新增项目的说明和具体设计内容。
- [ ] 已以参考 テーマ 的リリースモジュール一覧核对 Source 漏项。
- [ ] 每个 Source 的使用位置、处理用途及本次对应内容已调查并记录。
- [ ] 已结合数据库 Object 一览和 DB 改修内容确认改修对象。
- [ ] 已逐项确认休日、LKN 等实际涉及环境及各环境的具体改修内容。
- [ ] 尚未明确的范围、用途、Object 或环境已列为待确认事项。

## 5. 配套执行提示词

- [14 个项目追加对应一览核对与参考 Source 差分整理](14个项目核对/中文/P002_14个项目追加对应一览核对与参考Source差分整理.md)：分派子智能体核对各项目的 Source 漏项，并保存参考改修差分作为后续开发 Input。

# 案件追加時の確認事項

整理日：2026-11-01

本書は、案件追加に必要なInput、追加対応一覧の確認事項、Source開発の根拠資料を整理したものです。実際の案件のパス、テーマID、Source、Objectの具体的な内容は、該当する会社案件の情報で埋めてください。この資料集のディレクトリを業務工程の実パスとみなさないでください。

## 1. Input：案件追加に必要な資料

| 入力項目 | 必要な情報 | 用途 |
| --- | --- | --- |
| Sourceの源頭 | 今回の開発の基準となるSourceの出所と場所 | 開発に使うSource基準を定める |
| 本番設計書の場所 | 現行本番設計書の保存場所 | 現行の設計内容を調べる |
| テーマIDと名称 | 本次追加に対応するテーマIDと名称 | 本次テーマを識別し、新しいテーマ Boxを作る |
| 追加対応一覧（中心資料） | 今回追加・変更する項目と具体的な対応内容 | 本次の実施内容を定め、Source開発の主要根拠とする |
| 過去の参考テーマの場所 | 参考にする過去テーマと資料の場所 | 過去の対応資料を調べる |
| 過去の参考テーマのSource改修位置 | 過去テーマで実際に修正したSourceと改修位置 | 今回のSource開発の参考にする |
| 外部設計（必要に応じて） | 特に新規項目の説明と具体的な設計内容 | 新規項目の詳細要求を補う |

### 新テーマ Boxの作成

**Sourceの源頭、本番設計書の場所、テーマIDと名称**などの基礎情報を使って、新しいテーマ Boxを作成します。

新テーマ Boxは、基礎情報を受け取った後に作る資料の容器です。独立したInput項目として扱いません。

## 2. 追加対応一覧で確認する内容

### 2.1 参考テーマのリリースモジュール一覧からSource漏れを確認する（最重要）

追加対応一覧を作成した後、参考テーマの**リリースモジュール一覧**を正しい資料・照合基準として、対応一覧にSourceの漏れがないか確認します。

確認手順：

1. 参考テーマのリリースモジュール一覧を探す。
2. そこに列挙されたSourceから、追加対応一覧を一件ずつ照合する。
3. 追加対応一覧にないSourceについて、本次追加との関係を確認する。本次対象であれば、後続の確認済み正式版への更新で必ず漏れを補う。
4. 範囲や対応関係がまだ明確でない項目は、確認事項として記録する。

本次の新規Sourceも、本次追加要求と外部設計に照らして確認し、その後続の正式版更新で対応一覧へ記載します。

本節は追加開発における一般的な確認・補充の流れを示します。正式な追記は後続の確認済み対応一覧の版更新として行い、対象と確認した記載漏れは必ず補います。関連する P002「14案件の追加対応一覧の照合と参考Source差分の整理」を実行する今回の範囲は、調査、Inputおよび補充提案の保存までです。元の対応一覧や他の原本を上書きせず、今回の補充提案を正式一覧の更新完了と取り違えないでください。

**重要：対応一覧ができたら、必ず参考テーマのリリースモジュール一覧へ戻って確認します。すでに作成した対応一覧だけを根拠に、漏れがないとは判断しません。**

### 2.2 各Sourceの用途を調査する

対応一覧の各Sourceについて、以下を明らかにします。

- どこで使われるか。
- どの具体的な処理を担当するか。
- 本次の追加・改修内容とどのような関係があるか。

例えば、**ファイル作成、DB改修**のどちらの処理に使われるかなどを区別し、結果を対応一覧へ記録します。Source名だけを列挙し、用途を説明しない状態にしないでください。

### 2.3 DB Object一覧とDB改修内容を照合して環境を確認する

以下の資料を準備し、照合します。

- **DB Object一覧**。
- **DB改修内容**。

それらを基に、次を確認します。

1. 今回どのDB Objectが関係するか。
2. **休日、LKN**など、どの環境を改修する必要があるか。
3. 各環境にどのObjectが関係するか。
4. 環境ごと・Objectごとに、具体的に何を変更するか。

環境の範囲は一件ずつ確認します。「DB改修が必要」とだけ記し、対象・環境・具体内容を省略しないでください。「休日」「LKN」は工程内の原名称を維持します。他の環境は実案件の情報に応じて補ってください。

## 3. Source開発の根拠

Source開発は、主に以下の二つを根拠として進めます。

1. **追加対応一覧**：今回何を追加・変更するかを示す。
2. **過去の参考テーマのSource改修位置**：過去の類似対応で、どこを、どのように修正したかを示す参考。

新規項目がある場合は、**外部設計の新規項目説明と具体的な設計内容**も合わせて使います。

開発に入る前に、対応一覧のSource漏れ確認、用途調査、DB Objectと対象改修環境の確認を完了してください。

## 4. チェックリスト

- [ ] Sourceの源頭、本番設計書の場所、テーマIDと名称が明確。
- [ ] 新テーマ Boxを作成済み。
- [ ] 追加対応一覧、過去の参考テーマの場所、そのSource改修位置を用意済み。
- [ ] 必要に応じた外部設計を用意し、新規項目の説明と具体的な設計内容を確認済み。
- [ ] 参考テーマのリリースモジュール一覧を基準にSource漏れを照合済み。
- [ ] 各Sourceの使用位置、用途、本次対応との関係を調査・記録済み。
- [ ] DB Object一覧とDB改修内容を照合し、対象Objectを確認済み。
- [ ] 休日、LKNなど、実際に関係する環境と各環境の具体的な改修内容を個別に確認済み。
- [ ] 不明な範囲、用途、Object、環境を確認事項として記録済み。
