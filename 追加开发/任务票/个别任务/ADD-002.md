### ADD-002｜从参考 Release 一览反向核对追加对应一览中的 Source 漏项

优先级：最高优先：追加开发  
业务状态：未开始（尚未在公司工程执行）  
GitHub：https://github.com/niceon-diy/claude--/issues/3

### 目的

以参考 Thema 的リリースモジュール一覧为基准，保留明细，核实追加对应一览的 Source 漏列。

### 前置任务

- [ADD-001｜建立公司工程、追加项目、资料及 Source 基准索引](https://github.com/niceon-diy/claude--/issues/1)

按每个实际目标项目判断必要成果是否齐全，或是否有不适用依据；不是要求等待前置任务的全部项目一起完成。

### 输入

- 目标项目与参考 Thema 索引
- 相关全部 Release 的模块一览，以及补列前的追加对应一览

### 实际执行步骤

1. 确认两份资料的项目、版本、Release 范围及 Source 与生成物的区别，保留原文和文件指纹。
2. 用脚本等提取全部相关工作表、表格、续行和一行多个对象，为每条记录附原文件、工作表、行等位置；保留无法提取的部分。
3. 从 Release 侧逐条查追加对应一览。生成物名称与 Source 名称不同时，以实际构建／Release 资料核实映射，不凭相似名称认定相同。
4. 保留双向差异和重复。Release 有而对应一览没有的先标疑似漏列，再按本次范围分为确认漏列、范围外、待确认；本次新增 Source 另行确认。
5. 已有程序清单比对工具可用时，先读说明并复用。保存数量、实际命令、结果和未解析部分。

### 成果物

- 两侧原始记录、提取脚本及提取记录
- Source 覆盖明细、双向差异、重复、确认漏列／疑似漏列／范围外／待确认清单

### 完成条件

- [ ] 明确全部相关 Release 范围及提取限制
- [ ] 每条差异都有原文位置和判断依据
- [ ] 没有为消除差异而覆盖原对应一览

### 修改范围

交付调查版和补充建议。原资料的正式更新在 ADD-007 中处理。

### 缺失或失败时

保存缺失项、实际已检查范围、受影响结论／对象、确认人或资料及最短补充方式，并继续可独立完成的工作。重要规格矛盾不能擅自消解；没有执行、没有生成或没有测试的内容不得报告完成。

本任务须在公司内部实际可访问的业务工程中执行。本仓库提供的是任务要求和模板，不代表公司调查、实现或测试已经完成。

- 先读取实际生效的工程规则、当前任务和已有成果，不要求用户重复提供已经能查到的信息。历史资料中的权限或特定环境，不自动作为当前授权。

## 日本語（単独でコピーして実行可能）

### ADD-002｜参考Release一覧から追加対応一覧のSource漏れを逆照合する

優先区分：最優先：追加開発  
業務状態：未着手（会社工程で実行前）  
GitHub：https://github.com/niceon-diy/claude--/issues/3

### 目的

参考Themaのリリースモジュール一覧を基準に、追加対応一覧のSource記載漏れを明細付きで確認する。

### 前提チケット

- [ADD-001｜会社工程・追加案件・資料・Source基準の索引を作る](https://github.com/niceon-diy/claude--/issues/1)

各実案件について必要な成果が揃うか、不適用の根拠があるかを判定する。前提チケットの全案件が一斉に完了するまで待つ意味ではない。

### 入力

- 対象案件と参考Themaの索引
- 関連する全Releaseのモジュール一覧と、補列前の追加対応一覧

### 実際に行う手順

1. 両資料の案件、版、Release範囲、Sourceと生成物の区別を確認し、原本と指紋を残す。
2. 全関連シート、表、続き行、一行複数記載をスクリプト等で抽出し、各記録に元ファイル・シート・行などの位置を付ける。抽出不能箇所も残す。
3. Release側の各記録から対応一覧を調べる。生成物名とSource名が異なる場合は実際のビルド・Release資料で対応を確認し、似た名前だけで同一視しない。
4. 両方向の差分と重複を残す。Releaseにあり対応一覧にないものはまず疑似漏れとし、今回範囲を確認して確認漏れ・範囲外・未確認に分類する。新規Sourceも別に確認する。
5. 既存のプログラム照合ツールが利用可能なら説明を読み再利用する。件数、実行コマンド、結果、未解析部分を保存する。

### 成果物

- 両側の原記録、抽出スクリプトと抽出記録
- Sourceカバレッジ明細、双方向差分、重複、確認漏れ／疑似漏れ／範囲外／未確認一覧

### 完了条件

- [ ] 全関連Release範囲と抽出の限界が明示されている
- [ ] 全差分に原文位置と判断根拠がある
- [ ] 元の対応一覧を差分解消のために上書きしていない

### 変更範囲

調査版と補充提案を出す。原本の正式更新はADD-007で行う。

### 不足・失敗時

不足項、実際に調べた範囲、影響する結論／対象、確認先・資料と最短の補充方法を保存し、独立して進められる作業は続ける。重要な仕様矛盾を勝手に解消せず、未実行・未生成・未試験の内容を完了と報告しない。

### 会社Claudeへの共通実行条件

この作業は、会社内で実際にアクセスできる業務工程に対して実行する。本リポジトリは依頼とテンプレートを提供するもので、会社の調査・実装・試験が完了した証拠ではない。

- まず実工程で有効なルール、現在タスク、既存成果を読む。すでに調べられる情報をユーザーへ再入力させない。歴史資料にある権限や特定環境を現在の承認とみなさない。
- 必要な前提が揃う通常作業は連続実行する。結果を左右する重要な業務判断・権限・アクセス不足だけを具体的に確認し、それに依存しない作業は続ける。
- 案件単位で前提を判定する。目標14案件がすべて揃うまで、準備済み案件の設計・開発を止めない。数を合わせるための架空案件を作らない。
- 正式要求、今回の対応一覧、現行設計、歴史参考を区別する。参考Source Diffを今回の正式仕様の代わりにしない。
- 重要結論に実ファイル・版・行／章／シート等の位置を付ける。事実、推測、未読、アクセス不能、未確認、不適用を区別し、不適用には理由を残す。
- 会社工程の既存成果ディレクトリを優先する。決まりがなければ `調査結果/追加開発/<実際の実行日時>/<確認済み案件ID>/<チケットID>/` を使う。案件IDが不明な間は架空の対象を作らない。
- 会社資料の本文、実業務データ、認証情報をGitHubへ転載しない。必要な成果は会社内に保存し、Issueには機密を含まない進捗と定位方法だけを残す。
- 実際の完了条件を満たしてからIssueを終了する。コピー、スクリプト成功、用例生成、Source保存だけで調査や試験全体の完了としない。

成果と引継ぎには、実案件／対象、入力と版、実施内容、成果の完全なパス、実際の検証結果、未完了／未確認事項、次の一手を残す。最後は写真で共有しやすい約10行で実結果を報告する。
