## 中文（可单独复制执行）

### ADD-001｜建立公司工程、追加项目、资料及 Source 基准索引

优先级：最高优先：追加开发  
业务状态：未开始（尚未在公司工程执行）  
GitHub：https://github.com/niceon-diy/claude--/issues/1

### 目的

确定追加改修的对象和正式输入，使公司既有工程具备开始工作的条件。

### 前置任务

- 无；可从已有资料直接确认。

按每个实际目标项目判断必要成果是否齐全，或是否有不适用依据；不是要求等待前置任务的全部项目一起完成。

### 输入

- 公司实际工程根目录、已有规则及当前任务记录
- Source 来源、本番设计书、Thema ID／名称、追加对应一览、参考 Thema 及 Source 改修位置，以及必要的外部设计

### 实际执行步骤

1. 确认当前工程、Source 版本／分支／提交或文件指纹、未提交差分及适用环境。区分手头的环境模板与公司业务工程。
2. 从既有记录查找目标项目及各自的参考 Thema。原有任务要求的目标数量为 14 个，但只登记实际确认的项目，不虚构项目补足 14 个。
3. 按项目登记追加对应一览、参考 Folder、相关 Release、リリースモジュール一覧、现行设计、Source 和 DB 资料的实际位置及版本。多个参考先和多个 Release 分开记录。
4. 优先使用已有成果保存位置，确定本次运行目录。按公司流程需要建立新 Thema Box 时，以基础信息为依据；Box 不作为独立输入资料计数。
5. 按已确认项目拆分本组 Issue 的子任务。可调用子智能体时按项目分工并分离写入目录；不能调用时也按相同项目单位推进。

### 成果物

- 项目总索引：项目 ID、Thema、Source 基准、各资料位置与版本、确认状态、负责人、成果目录
- 资料缺失及未确定范围清单、供恢复工作的任务记录

### 完成条件

- [ ] 说明实际确认项目数量与目标 14 个之间的差额
- [ ] 区分正式输入和历史参考，不混用各项目的 Source 与参考先
- [ ] 无法确定项目时，也保存搜索范围、缺失信息及影响

### 修改范围

不修改业务 Source。整理资料索引和公司流程需要的工作资料容器。

### 缺失或失败时

保存缺失项、实际已检查范围、受影响结论／对象、确认人或资料及最短补充方式，并继续可独立完成的工作。重要规格矛盾不能擅自消解；没有执行、没有生成或没有测试的内容不得报告完成。

### 公司 Claude 的共同执行条件

本任务须在公司内部实际可访问的业务工程中执行。本仓库提供的是任务要求和模板，不代表公司调查、实现或测试已经完成。

- 先读取实际生效的工程规则、当前任务和已有成果，不要求用户重复提供已经能查到的信息。历史资料中的权限或特定环境，不自动作为当前授权。
- 必要前提齐全的通常工作连续执行。只有影响结果的重要业务判断、权限或访问缺失才具体询问，同时继续不依赖缺失答案的工作。
- 按项目判断前提。不能因目标14个项目未全部齐备，就阻止准备好的项目进入设计和开发；也不能虚构项目补足数量。
- 区分正式要求、本次对应一览、现行设计和历史参考。参考Source Diff不能替代本次正式规格。
- 关键结论附实际文件、版本、行／章／工作表等位置；区分事实、推测、未读、无法访问、待确认和不适用，不适用须有理由。
- 优先沿用公司工程既有成果目录；没有约定时，使用 `調査結果/追加開発/<实际运行时间>/<已确认项目ID>/<任务票ID>/`。项目ID未确定前不创建虚假对象。
- 公司资料正文、真实业务数据及认证信息不转载到GitHub。必要成果保存在公司内部，Issue只记录不含机密的进度和定位方式。
- 实际完成条件满足后才可结束Issue。复制、脚本成功、用例生成、Source保存不能单独证明调查或测试整体完成。

成果与交接记录必须写明实际项目／对象、输入及版本、实际操作、成果完整路径、真实验证结果、未完成／未确认事项和下一步。最后用适合拍照反馈的约10行报告实际结果。

## 日本語（単独でコピーして実行可能）

### ADD-001｜会社工程・追加案件・資料・Source基準の索引を作る

優先区分：最優先：追加開発  
業務状態：未着手（会社工程で実行前）  
GitHub：https://github.com/niceon-diy/claude--/issues/1

### 目的

追加改修の対象と正式入力を特定し、会社の既存工程で作業を開始できる状態にする。

### 前提チケット

- なし。既存資料から直接確認できる。

各実案件について必要な成果が揃うか、不適用の根拠があるかを判定する。前提チケットの全案件が一斉に完了するまで待つ意味ではない。

### 入力

- 会社工程の実際のルートと既存ルール、現行タスク記録
- Sourceの入手元、本番設計書、Thema ID／名称、追加対応一覧、参考ThemaとSource改修位置、必要な外部設計

### 実際に行う手順

1. 現在の工程、Sourceの版・ブランチ・コミットまたは指紋、未コミット差分、適用環境を確認する。手元の環境テンプレートと会社の業務工程を区別する。
2. 既存記録から対象案件と各参考Themaを探す。既存依頼の目標件数は14だが、実際に確認できた案件だけ登録し、14に足りない分を架空の案件で補わない。
3. 案件ごとに追加対応一覧、参考先Folder、関連Release、リリースモジュール一覧、現行設計、Source、DB資料の実際の場所と版を登録する。複数参考先・複数Releaseを別記する。
4. 既存の成果保存場所を優先し、今回の実行用ディレクトリを決める。会社の運用に従い新Thema Boxを用意する場合は基礎情報を根拠とし、Boxを独立した入力資料と数えない。
5. 確認できた案件ごとに本Issue群の子作業を切り出す。子エージェントを使える場合は案件単位で分担し、書込み先を分離する。使えない場合も同じ案件単位で進める。

### 成果物

- 案件総索引：案件ID、Thema、Source基準、各資料の場所・版、確認状態、担当、成果ディレクトリ
- 資料不足と未確定範囲の一覧、再開用タスク記録

### 完了条件

- [ ] 実際に確認した案件数と目標14件との差が説明されている
- [ ] 正式入力と歴史参考が区別され、各案件のSourceと参考先が混在していない
- [ ] 案件を特定できない場合も検索範囲・不足情報・影響を保存している

### 変更範囲

業務Sourceは変更しない。資料索引と会社手順で必要な作業用容器を整える。

### 不足・失敗時

不足項、実際に調べた範囲、影響する結論／対象、確認先・資料と最短の補充方法を保存し、独立して進められる作業は続ける。重要な仕様矛盾を勝手に解消せず、未実行・未生成・未試験の内容を完了と報告しない。

### 会社Claudeへの共通実行条件

この作業は、会社内で実際にアクセスできる業務工程に対して実行する。本リポジトリは依頼とテンプレートを提供するもので、会社の調査・実装・試験が完了した証拠ではない。

- まず実工程で有効なルール、現在タスク、既存成果を読む。すでに調べられる情報をユーザーへ再入力させない。歴史資料にある権限や特定環境を現在の承認とみなさない。
- 必要な前提が揃う通常作業は連続実行する。結果を左右する重要な業務判断・権限・アクセス不足だけを具体的に確認し、それに依存しない作業は続ける。
- 案件単位で前提を判定する。目標14案件がすべて揃うまで、準備済み案件の設計・開発を止めない。数を合わせるための架空案件を作らない。
- 正式要求、今回の対応一覧、現行設計、歴史参考を区別する。参考Source Diffを今回の正式仕様の代わりにしない。
- 重要結論に実ファイル・版・行／章／シート等の位置を付ける。事実、推測、未読、アクセス不能、未確認、不適用を区別し、不適用には理由を残す。
- 会社工程の既存成果ディレクトリを優先する。決まりがなければ `調査結果/追加開発/<実際の実行日時>/<確認済み案件ID>/<チケットID>/` を使う。案件IDが不明な間は架空の対象を作らない。
- 会社資料の本文、実業務データ、認証情報をGitHubへ転載しない。必要な成果は会社内に保存し、Issueには機密を含まない進捗と定位方法だけを残す。
- 実際の完了条件を満たしてからIssueを終了する。コピー、スクリプト成功、用例生成、Source保存だけで調査や試験全体の完了としない。

成果と引継ぎには、実案件／対象、入力と版、実施内容、成果の完全なパス、実際の検証結果、未完了／未確認事項、次の一手を残す。最後は写真で共有しやすい約10行で実結果を報告する。
