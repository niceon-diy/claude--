### ADD-004｜保存参考 テーマ 改修前后 Source 与 Diff，形成开发 Input

### 目的

保留真实历史改修差分与 Source，使后续开发能够可靠参考。

### 前置任务

- [ADD-002｜从参考 Release 一览反向核对追加对应一览中的 Source 漏项](https://github.com/niceon-diy/claude--/issues/3)

按每个实际目标项目判断必要成果是否齐全，或是否有不适用依据；不是要求等待前置任务的全部项目一起完成。

### 输入

- 本次追加内容及包含确认漏列的目标 Source
- 参考 テーマ 的改修前后版本、历史、已有 Diff、改修说明

### 实际执行步骤

1. 核实与参考 テーマ 的关系，选择与本次追加有关的 Source 和改修位置，不将 Folder 内所有变更无条件列入本次范围。
2. 确认 before／after 的真实文件、版本、比较方向及改名／新增／删除，不无依据地用当前本番或最新分支替代 before。
3. 按原相对目录和编码保存 before／after，保留真实 Diff 与比较条件。缺 before 时保存已确认 after 和缺口，不伪造可确认的 Diff。
4. 解释每项改修改了什么、可参考于本次哪项要求，不能把旧 テーマ 固有值当作本次直接采用的依据。
5. 建立 Input ID、原位置、保存位置、版本、校验值、说明、确认状态索引，区分实际复制保存与仅记录位置。

### 成果物

- Source_Input 索引、before／after／diff、比较记录、保存文件及校验值清单
- 缺失版本及关联不明 Source 清单

### 完成条件

- [ ] 可以从索引打开实际保存的文件
- [ ] 比较方向和两侧版本明确，没有混入推测 Diff
- [ ] 说明本次追加与参考改修的关系

## 日本語（単独でコピーして実行可能）

### ADD-004｜参考テーマの改修前後SourceとDiffを開発Inputとして保存する

優先区分：最優先：追加開発  
業務状態：未着手（会社工程で実行前）  
GitHub：https://github.com/niceon-diy/claude--/issues/5

### 目的

歴史参考の実際の改修差分とSourceを、後続開発で確実に参照できる形で残す。

### 前提チケット

- [ADD-002｜参考Release一覧から追加対応一覧のSource漏れを逆照合する](https://github.com/niceon-diy/claude--/issues/3)

各実案件について必要な成果が揃うか、不適用の根拠があるかを判定する。前提チケットの全案件が一斉に完了するまで待つ意味ではない。

### 入力

- 今回追加内容と確認漏れを含む対象Source
- 参考テーマの改修前後版、履歴、既存Diff、改修説明

### 実際に行う手順

1. 参考テーマとの関係を確認し、今回追加に関連するSourceと改修位置を選ぶ。Folder内の全変更を無条件に今回対象としない。
2. 比較するbefore／afterの実在、版、比較方向、改名・追加・削除を確認する。現在本番や最新ブランチを根拠なくbeforeに代用しない。
3. 元の相対ディレクトリと文字コードを維持してbefore／afterを保存し、実Diffと比較条件を残す。beforeがない場合は確認済みafterと不足を保存し、信頼できるDiffを捏造しない。
4. 各改修が何を変え、今回どの追加要求の参考になるか説明する。旧テーマ固有の値をそのまま採用する根拠にはしない。
5. Input ID、元の場所、保存先、版、チェックサム、説明、確認状態を索引化し、コピー保存済みと位置記録だけのものを分ける。

### 成果物

- Source_Input索引、before／after／diff、比較記録、保存ファイルとチェックサムの一覧
- 不足版・関連不明Sourceの一覧

### 完了条件

- [ ] 索引から実際に保存したファイルを開ける
- [ ] 比較方向と両版が分かり、推測Diffが混在しない
- [ ] 今回追加と参考改修の関係が説明されている

### 不足・失敗時

不足項、実際に調べた範囲、影響する結論／対象、確認先・資料と最短の補充方法を保存し、独立して進められる作業は続ける。重要な仕様矛盾を勝手に解消せず、未実行・未生成・未試験の内容を完了と報告しない。

### 会社Claudeへの共通実行条件

この作業は、会社内で実際にアクセスできる業務工程に対して実行する。本リポジトリは依頼とテンプレートを提供するもので、会社の調査・実装・試験が完了した証拠ではない。

- まず実工程で有効なルール、現在タスク、既存成果を読む。すでに調べられる情報をユーザーへ再入力させない。歴史資料にある権限や特定環境を現在の承認とみなさない。
- 必要な前提が揃う通常作業は連続実行する。結果を左右する重要な業務判断・権限・アクセス不足だけを具体的に確認し、それに依存しない作業は続ける。
- 案件単位で前提を判定する。目標14案件がすべて揃うまで、準備済み案件の設計・開発を止めない。数を合わせるための架空案件を作らない。
- 正式要求、今回の対応一覧、現行設計、歴史参考を区別する。参考Source Diffを今回の正式仕様の代わりにしない。
- 重要結論に実ファイル・版・行／章／シート等の位置を付ける。事実、推測、未読、アクセス不能、未確認、不適用を区別し、不適用には理由を残す。
- 会社工程の既存成果ディレクトリを優先する。決まりがなければ `調査結果/追加開発/<実際の実行日時>/<確認済み案件ID>/<チケットID>/` を使う。案件IDが不明な間は架空の対象を作らない。
- 会社資料の本文、実業務データ、認証情報をGitHubへ転載しない。必要な成果は会社内に保存し、Issueには機密を含まない進捗と定位方法だけを残す。
- 実際の完了条件を満たしてからIssueを終了する。コピー、スクリプト成功、用例生成、Source保存だけで調査や試験全体の完了としない。

成果と引継ぎには、実案件／対象、入力と版、実施内容、成果の完全なパス、実際の検証結果、未完了／未確認事項、次の一手を残す。最後は写真で共有しやすい約10行で実結果を報告する。
