# 验收与 eval：先证明笔记可追溯，再核对业务事实

本套件有两类验证：自动检查文件和来源关系；用熟悉的真实设计书检查事实、条件、遗漏与矛盾。前者不能代替后者。当前公司资料尚未提供，真实业务 eval 未执行。

## 1. 先运行隔离样例

`examples/mini-project/` 是虚构演示，和正式 raw／wiki 分开。它包含当前设计、同版本补充说明、历史参考三份资料；一处长度矛盾被刻意保留。

在知识库根目录执行：

```powershell
python tools/kb_check.py validate --root examples/mini-project
python -m unittest discover -s tools -p "test_*.py"
```

现有样例的实际运行结果见 [验证记录](examples/mini-project/验证记录.md)。它证明本地文件流程与校验工作，不证明公司端 Claude 执行过两个 slash 命令。

想重新演练 ingest／refine 时，先将示意 raw 复制到一个新的临时知识库目录，建立空的 `wiki/Concepts/`。在其中分别按两个技能执行；不要重用交付样例的绝对根目录基线。基线绑定当时的机器目录，复制／移动后要为新动作建立新基线，旧报告只能作历史记录。

## 2. 第一套公司样例

选择一个自己熟悉、能读原件判断对错的小功能。先收录其设计要求、一个容易混淆的历史版本、一个条件／例外，以及确实存在时的冲突。不为凑样例制造公司规格或矛盾。

开始前保存人工基准：由业务知情者从原件列出该功能的关键要求、适用环境、版本和原文位置。基准单独保存 `wiki/.checks/<运行号>-eval-ground-truth.md`，不作为 refine 的额外事实输入。

对同一 scope 的笔记检查下面各项，填写“通过／失败／待确认／不适用”及证据：

| 检查项 | 要求与证据 |
| --- | --- |
| 原件不变 | 动作前后清单与哈希一致；没有新增、移动、改名、删除原件 |
| 来源可定位 | 抽查范围内每条结论都能回到原件版本、页／章／单元格；读取范围与声明一致 |
| 来源角色 | 本次正式要求、当前基准、历史参考已区分；有效版本经业务确认 |
| 条件与例外 | 关键分支、限制、默认值和例外有原文支持；没有在归纳时丢失 |
| 跨文档关系 | 每个跨链接关系都能解释依据；同名词和不同 Thema／环境没有误合并 |
| 冲突保留 | 不一致的双方都有证据；未经确认的优先级没有被模型擅自决定 |
| 缺源时回答 | 设计未说明的问题明确回答“未收录／待确认”，没有按经验补规格 |
| 关键要求覆盖 | 人工基准中的每项要求对应笔记；遗漏单列，不以笔记自身证明完整 |
| refine 边界 | I 笔记不变；每个 C 的父项和来源都在动作开始时已存在；无补源 |
| 恢复与再跑 | 新会话读取本地进度可找到原件、笔记、未确认项；完整重复 ingest 不生成重复记录 |

## 3. 固定问题集与判定

每个问题的预期答案必须来自人工基准，不能用待评笔记自己生成标准答案。让 Claude 仅依据指定 scope 的已有笔记回答，返回笔记 ID、来源 S 编号和原件定位；缺失证据应明确拒绝补写。

1. 这个功能做什么，输入、输出分别是什么？
2. 某字段的限制／默认值／处理条件是什么？适用什么版本和环境？
3. 历史参考与当前要求有哪些差异，哪项仍需确认？
4. 已知冲突是什么，能否据现有证据决定采用哪一项？
5. 一个原件没有说明的问题，当前知识库能不能回答？
6. 给定原件位置，哪些笔记引用了它？是否有遗漏要求？

结果存为 `wiki/.checks/<运行号>-eval-results.md`，每题记录问题、人工预期、实际回答、笔记 ID、来源位置、判定、核验人和日期。统计按实际记录计算：关键要求覆盖率、事实正确率、有效引用率、未知问题正确处理率、未解决的关键冲突数；分母为零写“不适用”，不能写100%。

建议的首轮门槛：选定范围内的关键要求全部覆盖、逐项事实及引用均正确、未知问题不补造、没有被隐藏的关键冲突。未满足则纠正后使用同一固定问题集复测；不得通过删掉失败问题提高结果。

## 4. verified 与后续接入

业务知情者实际核验一份笔记后，才在单独的审阅步骤把它标为 `verified`，并增加：

```json
"review": {
  "reviewer": "实际核验人或可识别的业务角色",
  "date": "YYYY-MM-DD",
  "method": "实际核对范围、原件位置和eval结果路径"
}
```

这不是完整 JSON 文档，而是笔记元数据内新增的字段。两个命令不自行执行这一升级；脚本能检查字段存在，不能验证核验人身份或审阅是否真实发生。原件换版或结论改写后重新核验。

将“稳定”具体记为至少两次独立会话／批次使用同一问题集复核通过，并写明笔记及原件版本；这是本套件的建议门槛，业务可按实际要求调整。达标后再另行确定开发 Agent 读取的目录、scope、已核验版本和遇到冲突时的处理。当前套件不自动执行这一步。
