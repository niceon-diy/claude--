# Claude Code 项目协作实施模板

**定位**：项目执行细则，不是第二份核心工作总则。唯一核心总则为 [CORE-001｜专家工作模式与 PDCA 质量闭环](../../核心规则/CORE-001_专家工作模式与PDCA质量闭环_已发送Claude.md)。

> 使用时须将 CORE-001 的有效内容按实际工程的规则加载方式接入并验证；本相对链接仅供仓库内阅读，复制本模板到其他工程后不保证链接有效。不得因引用本模板就声称 CORE-001 已被加载。

## 1. 任务接入

- 开始或接续时读取本工程任务、进度、交接记录，核对实际文件状态；复杂任务按已有约定使用 `当前任务.md`。
- 沿用已确认决定。用户用日常语言提出需求时，由 Claude 整理目标、输入、范围、成果及验收方法；只对关键缺口提问，每次至多 3 个。
- 简单任务直接处理；不能继续的部分标记阻塞，不依赖该问题的部分可在授权范围内推进。

## 2. 资料基准与调查方法

- 区分本次要求、当前版本基准、历史项目、既有成果；按任务约定使用知识库、外部设计目录和项目 DOC。
- 历史设计不得自动当作当前规格；设计、程序、历史结论冲突时列明双方依据及待确认项。“最新”目录名不等于已验证版本。
- 功能调查按需沿「业务目的 → 入口 → 关键调用 → 数据变化 → 输出结果」展开；调用处与被调用对象均应可定位。
- 对动态调用、条件分支、运行时行为说明成立条件及实际验证范围；不能凭名称或单次搜索断言关系完整。

## 3. 实施与校准

- 优先复用工程已有结构和工具，不为执行单个任务随意重建目录或框架。
- 对方向不明确的大任务，先在授权范围内给代表性样例，确认后扩展；目标、资料基准或修改范围发生重大变化时请求确认。
- 检查方法随成果类型确定：调查核对原始依据，代码变更运行相关检查，界面工作查看实际效果；明确报告未运行或未覆盖的部分。
- 用户指出偏差时区分需求理解、实现与说明问题，修正后重新核对原问题及关联部分。根因分析与通用改进遵循 CORE-001。

## 4. 任务记录与交接

- 复杂任务在实质阶段结束或交接前，按工程既有位置记录：当前目标、已完成内容、成果位置、关键决定、证据索引、待确认事项、下一步。
- 新会话先读记录，再核对资料变化；只有仍适用的成果才能复用。
- 长期知识按已有知识管理规范及授权保存；普通问答无需逐条归档。

## 5. 日常反馈格式

日常阶段反馈优先简短（约 10 行），必要证据与限制不得省略。专项报告的完整内容和格式遵循适用的专项规范（如 B001），不因简短反馈模板而省略必需字段。

```text
任务：本轮目标
阶段：当前做到哪里
完成：实际成果
依据：可定位资料或成果位置
验证：实际检查与结果
待确认：未解决问题；没有则写“无”
下一步：后续动作
继续指令：用户下一次可直接发送的一句话
```
