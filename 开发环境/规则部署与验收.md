# 规则部署与验收／ルールの配置と検証

[中文：部署与验收](#deployment) · [中文：版本备份](#version-backup) · [日本語：配置と検証](#deployment-ja) · [日本語：版とバックアップ](#version-backup-ja)

本文件提供可复用的操作方法，不代表任何机器已完成部署、加载或行为验收。实际路径、版本、权限和执行状态须在本次环境核实。
この文書は再利用できる手順です。いずれのマシンについても、配置・読込み・動作検証が完了したことを示しません。実際のパス、版、権限、実施状況は今回の環境で確認してください。

## 中文：规则部署与验收

### 1. 适用范围与维护来源

- 只在当前任务已确定的范围内维护规则。个人偏好放在实际用户的个人规则中；业务范围、Source 基准、资料路径、输出目录和项目命令保留在项目规则中。
- 表达与交付使用已定稿的 [B001](../通用提示词/B001_把话说清楚与输出格式.md)；项目协作参考 [项目协作总则](模板/CLAUDE.md#working-rules)，任务范围与确认节点记录在 [当前任务](模板/当前任务.md#task-request)。按适用范围合并，不把整份项目规则安装为所有项目的个人规则。
- 既有方式已满足需要时，确认实际位置与依据即可。规则整理不是追加开发的统一前提；只处理与本次目标直接有关的重复、缺失和冲突。
- 历史指令里的单次授权、机器状态和路径不作为当前授权或事实。不得顺带修改业务 Source、设计、共享或组织规则、账号、权限、模型、插件及无关设置。

### 2. 部署步骤

1. **核实执行环境。** 记录实际机器、登录用户、用户目录、工作目录及 Claude Code 版本，区分本机 Windows 与 SSH 目标。核对 `CLAUDE_CONFIG_DIR` 等实际配置来源和会话能确认的规则路径；不要仅凭默认路径推定生效位置。存在多种可能且无法核实时，记录缺口，只暂停依赖该位置的写入。
2. **读取相关现行规则。** 检查目标个人文件、个人 `rules/`，以及实际适用的项目和组织规则。只读取必要配置，不导出凭据、环境变量全集或业务源码。模型、模式和其他设置仅在与问题有关时只读核对，不擅自调整。
3. **核实真实修改对象。** 修改前解析符号链接及实际目标。目标属于共享或组织管理范围、超出当前任务范围时，只报告冲突、位置和影响，不沿链接修改目标。
4. **先保存可恢复的版本。** 使用下方[版本备份规范](#version-backup)。个人规则备份须放在不会被作为规则加载的位置，不能放进 `rules/`；可复用既有备份机制，或在实际个人配置目录的 `backups/` 下使用时间戳和唯一标识。记录原文件与备份的对应关系；原先不存在的文件明确登记。
5. **最小合并。** 保留无关内容，更新已有同义条款，不重复追加；直接冲突的个人偏好只做必要修改。检查“每一步等继续”与当前确认节点、“过度简写”与 B001 完整交付的冲突。项目或组织规则的实质冲突保留依据并报告，不用一句“新规则优先”掩盖矛盾，也不清理无关历史内容。
6. **核对实际结果。** 检查真实 Diff、重复条款、目标范围及备份可恢复性，确认未改动无关文件。随后按三阶段验收分别登记；无法执行的阶段写明原因、剩余工作和下一步。

### 3. 三阶段验收

| 阶段 | 需要的实际证据 | 不能替代它的现象 |
| --- | --- | --- |
| 文件已写入 | 实际完整路径、修改位置、写入内容或真实 Diff、备份及文件检查结果 | 只提供计划、候选正文或“已理解” |
| 新会话已加载 | 修改后新建的目标环境会话，及其实际加载文件列表中的目标路径 | 当前旧会话的路径、规则复述或仅列出可编辑文件 |
| 实际行为已验收 | 下列样例和一项真实任务的输入、实际输出、检查结果及限制 | 只看到文件存在、加载成功或样例部分通过 |

新会话中可运行 `/context`，检查 Memory files 中实际加载的规则；`/memory` 用于查看和编辑位置，其列表不能单独证明已加载。具体命令与显示以实际版本为准；不能核实时标为“待验证”，不要关闭权限检查或绕过会话保护来制造通过结果。[官方加载与记忆说明](https://code.claude.com/docs/en/memory)

### 4. 三个行为验收样例

以下都是虚构样例，只验证回答行为，不能当作真实工程结论或业务执行授权。输入、完整实际回答及判定依据应一起保存。

| 样例 | 交给 Claude 的输入 | 预期检查点 |
| --- | --- | --- |
| 证据与边界 | “只读了入口 Shell，知道它调用 PCO，但尚未读取 PCO；能否认定整个 Shell 可以直接再运行？” | 区分已确认与未确认；不宣称可直接再运行；指出仍需检查被调用处理、副作用及适用条件。 |
| 表达完整性 | “批处理收到营业日参数，校验成功后调用汇总程序，把结果写入输出文件；校验失败时终止。请向初学者解释。” | 讲清主体、参数、触发条件、顺序、结果和失败分支；按 B001 保留必要格式，未知路径及业务原因标明未知，不编造。 |
| 完整执行与连续推进 | 在专用临时目录准备两个小文件，要求“只读这两个输入，生成比较表；两个文件均覆盖且差异可定位才完成”。 | 实际读取两份输入，生成可定位的比较表并说明检查结果；输入保持不变，输出单独保存；不只返回计划，不在普通步骤后反复等待“继续”，遵守已约定验收节点。 |

再选一项真实近期任务，对照原始要求、成果、证据及说明检查。记录实际通过、失败、未执行和未确认内容；样例通过不保证其他任务都正确。规则属于上下文要求，应以实际行为和可复查结果判断效果。[官方说明](https://code.claude.com/docs/en/memory)

### 5. 验收与交接记录

至少保留：实际环境及版本、确认的规则路径、改动范围与原因、备份和恢复方法、冲突及处理、三阶段各自的结果、样例与真实任务证据、未完成事项及下一步。不能核实的模型、模式或状态写“未知”，不以历史记录补填。

<a id="version-backup"></a>

### 6. 版本保存与备份规范

1. **优先既有方式。** 先检查工程已有的 Git、构成管理、备份与恢复机制，按实际方式保存；不为整理规则重复建立一套系统，不强制增加 Hooks、后台服务或新目录。
2. **保存真实 before／after。** 修改前保留实际原版，包括原有未提交变更；修改后保留对应新版。维持原相对路径，避免同名覆盖。可以引用可准确恢复的既有版本或保存副本，但必须能定位到实际两侧内容；原先不存在、新增、删除和改名分别记录，不能用当前 HEAD 代替尚未保存的修改前内容。
3. **保持原始内容可核验。** 记录来源位置、版本或提交号（如有）、编码、换行方式、校验算法及 before／after 校验值。副本保留原始字节；分析时若转换编码或换行，另存并注明转换方式，不覆盖原始备份。
4. **保存真实 Diff 和变更索引。** 每次记录时间、原因、任务或 Issue、目标文件、before／after 位置、版本、校验值及 Diff 位置和比较方向。二进制文件采用合适的比较方式，注明其差异及工具；不能把文字概述当作真实 Diff。缺少一侧或无法比较时如实标记，不生成伪造差分。
5. **核实恢复方法。** 检查备份是否可读取、版本是否对应，说明恢复对象和步骤；需要试恢复时使用独立临时位置。不覆盖其他人的工作，不改写共享历史，也不把未实际试过的恢复称为已验证。

## 日本語：ルールの配置と検証

### 1. 適用範囲と保守元

- 今回の依頼で定められた範囲だけを保守します。個人の好みは実際のユーザーの個人ルールへ、業務範囲、Source 基準、資料パス、出力先、工程のコマンドはプロジェクトルールへ置きます。
- 表現と引渡しは確定済みの [B001](../通用提示词/B001_把话说清楚与输出格式.md) に従います。共同作業の手順は [プロジェクト作業規範](模板/CLAUDE.md#working-rules)、タスク範囲と確認点は [現在タスク](模板/当前任务.md#task-request) を参照します。適用範囲を判断して統合し、プロジェクトルール全体をすべてのプロジェクトに適用する個人ルールとして導入しません。
- 既存の方法で十分な場合は、その場所と確認根拠を記録します。ルール整理を追加開発全体の前提にせず、今回の目的に直接関係する重複、不足、矛盾だけを扱います。
- 過去の指示にある一回限りの承認、マシン状態、パスを今回の承認や事実とみなしません。業務 Source、設計、共有・組織ルール、アカウント、権限、モデル、プラグイン、無関係な設定は変更しません。

### 2. 配置手順

1. **実行環境を確認します。** 実マシン、ログインユーザー、ユーザーディレクトリ、作業ディレクトリ、Claude Code の版を記録し、Windows 本機と SSH 接続先を区別します。`CLAUDE_CONFIG_DIR` など実際の設定元と、セッションで確認できるルールのパスを調べ、既定の場所だけで有効な配置先を決めません。候補が複数あり確定できない場合は不足を記録し、その場所に依存する書込みだけを保留します。
2. **関係する現行ルールを読みます。** 対象の個人ファイル、個人の `rules/`、実際に適用されるプロジェクト・組織ルールを確認します。必要な設定だけを読み、認証情報、環境変数の全量、業務 Source を出力しません。モデルやモードなどは問題に関係する場合だけ読み取りで確認し、勝手に変更しません。
3. **変更対象の実体を確認します。** 変更前にシンボリックリンクと実際の参照先を確認します。共有・組織管理の対象、または今回の範囲外へ書き込む場合は、矛盾、場所、影響を報告し、リンク先を変更しません。
4. **復元可能な版を先に保存します。** 下記の[版とバックアップの規範](#version-backup-ja)に従います。個人ルールのバックアップはルールとして読み込まれない場所へ置き、`rules/` 内には保存しません。既存の仕組みを利用するか、実際の個人設定ディレクトリの `backups/` に日時と一意な識別子で保存します。元ファイルとの対応を残し、元から存在しないファイルも明記します。
5. **最小範囲で統合します。** 無関係な内容を保持し、同義の既存条項を更新して重複追記を避けます。直接矛盾する個人の好みだけを必要最小限で修正します。「毎回続行を待つ」と今回の確認点、「過度な省略」と B001 の完全な引渡し要件を照合します。プロジェクト・組織ルールの実質的な矛盾は根拠とともに報告し、「新ルール優先」の一文で隠したり、無関係な履歴を整理したりしません。
6. **実結果を照合します。** 実 Diff、重複条項、変更範囲、バックアップの復元可能性を確認し、無関係なファイルを変更していないか調べます。その後、三段階を別々に検証し、実施できない段階は理由、残作業、次の一手を記録します。

### 3. 三段階の検証

| 段階 | 必要な実際の証拠 | 代わりにならないもの |
| --- | --- | --- |
| ファイルへの書込み済み | 実際の完全パス、変更位置、記載内容または実 Diff、バックアップ、ファイル確認結果 | 計画、候補本文、「理解しました」という回答だけ |
| 新しい会話での読込み済み | 変更後に対象環境で開始した新規セッションと、その実際の読込み一覧にある対象パス | 変更前の会話のパス、ルールの復唱、編集可能なファイルの一覧だけ |
| 実際の動作を検証済み | 次の例と実タスク一件の入力、実出力、確認結果、制限 | ファイルの存在、読込み成功、一部の例の成功だけ |

新規セッションで `/context` を実行し、Memory files 内の実際に読み込まれたルールを確認できます。`/memory` は場所の閲覧・編集に使うもので、その一覧だけで読込み済みとは判断しません。コマンドと表示は実際の版で確認し、検証できない場合は「未検証」とします。権限確認を無効化したり、セッション保護を回避したりして成功結果を作りません。[公式の読込み・メモリ説明](https://code.claude.com/docs/en/memory)

### 4. 三つの動作検証例

以下は架空の例で、回答の動作だけを確認します。実工程の結論や業務実行の承認には使いません。入力、実際の回答全文、判定根拠を一緒に保存します。

| 例 | Claude への入力 | 確認点 |
| --- | --- | --- |
| 証拠と適用範囲 | 「入口 Shell だけを読み、PCO を呼ぶことは分かっていますが、PCO は未読です。Shell 全体をそのまま再実行できると判断できますか。」 | 確認済みと未確認を区別し、そのまま再実行できるとは断言しません。呼出先、副作用、成立条件の確認が必要であることを示します。 |
| 説明の完全性 | 「バッチは営業日を引数で受け取り、検証成功時は集計プログラムを呼んで出力ファイルへ書き込み、検証失敗時は終了します。初心者向けに説明してください。」 | 主体、引数、起動条件、順序、結果、失敗分岐を説明します。B001 の形式を保ち、不明なパスや業務理由は不明と記載して捏造しません。 |
| 完全な実行と継続 | 専用の一時ディレクトリに小さいファイルを二つ用意し、「この二入力は読取りのみで比較表を作成し、両方を網羅して差異の位置を特定できたら完了」と依頼します。 | 二入力を実際に読み、差異の位置を特定できる比較表と確認結果を作成します。入力は保持して出力を別保存します。計画だけで終わらず、通常手順ごとに続行を求めず、合意済みの検証点を守ります。 |

さらに最近の実タスク一件を選び、元要求、成果、証拠、説明を照合します。合格、不合格、未実行、未確認を実際の状態で記録します。例の成功は他の全タスクの正しさを保証しません。ルールはコンテキスト上の指示であり、効果は実際の動作と再確認できる結果で判断します。[公式説明](https://code.claude.com/docs/en/memory)

### 5. 検証と引継ぎの記録

最低限、実環境と版、確認したルールのパス、変更範囲と理由、バックアップと復元方法、矛盾と対応、三段階それぞれの結果、例と実タスクの証拠、未完了事項、次の一手を残します。確認できないモデル、モード、状態は「不明」とし、過去の記録で埋めません。

<a id="version-backup-ja"></a>

### 6. 版の保存とバックアップの規範

1. **既存の方法を優先します。** 工程の Git、構成管理、バックアップ、復元の仕組みを先に調べ、実際の方式を使います。ルール整理のために別の仕組みを重複導入せず、Hooks、常駐サービス、新規ディレクトリを必須にしません。
2. **実際の before／after を保存します。** 変更前には既存の未コミット変更も含む実際の原版、変更後には対応する新版を保管します。元の相対パスを保ち、同名上書きを避けます。正確に復元できる既存版の参照かコピーの保存を利用できますが、実際の両側の内容を特定できることが必要です。元から存在しないもの、新規、削除、改名を区別し、未保存の変更前内容を現在の HEAD で代用しません。
3. **元の内容を検証可能に保ちます。** 入手元、版やコミット番号（ある場合）、文字コード、改行形式、チェックサムのアルゴリズム、before／after のチェックサムを記録します。コピーは元のバイト列を保ちます。分析用に文字コードや改行を変換する場合は別保存して方法を記録し、元のバックアップを上書きしません。
4. **実 Diff と変更索引を残します。** 変更ごとに日時、理由、タスクまたは Issue、対象ファイル、before／after の場所・版・チェックサム、Diff の場所と比較方向を記録します。バイナリは適切な方式で比較し、差異と使用ツールを記載します。説明文を実 Diff の代わりにしません。片側が不足する場合や比較できない場合は、その状態を明記し、差分を捏造しません。
5. **復元方法を確認します。** バックアップが読めるか、版が対応するかを調べ、復元対象と手順を説明します。復元を試す必要がある場合は独立した一時場所を使います。他者の作業を上書きせず、共有履歴を書き換えず、実際に試していない復元を検証済みとは呼びません。
