# 010｜现行 CLAUDE.md 结构分析与三级回答方案（v0.1）

**状态**：根据用户提供的 10 张 Windows VS Code 截图整理的分析文件。不是从原始 `CLAUDE.md` 文件全文解析所得，故仅代表截图可见内容。**未修改**用户远程 VM 上的 `CLAUDE.md`。

## 一、先给结论
- 原版已经包含“概要一句话 → 5W1H → 具体说明 → 文件交付”等完整输出流程。
- 实际过长的主因：**B001 的后续条款要求“概要、5W1H 后不能省略必要事项”，且强调“回答内完结”**，这使详细解释、状态清单、代码和证明材料容易全部出现在聊天窗口。
- 不是单纯缺少“要简短”指令，而是**缺少默认停止条件和“详细内容单独存入文件”的强制分流规则**。
- 用户希望：**一级极简结论；二级按需展开 10～20 行；三级完整 Markdown 报告文件，通常与分析同步生成并给出链接**。

## 二、现行文件的功能结构（按截图顺序归纳；不是原文件章节编号）

### 1. 全局设置
**为了什么**：每个适用 Claude Code 会话拥有统一指导。  
**做了什么／怎么做**：声明 `CLAUDE.md` 的适用范围与指导角色；截图标题为「グローバル設定」。

### 2. 工作心态
**为了什么**：保持专注、冷静、善于协商、不回避问题。  
**做了什么／怎么做**：通过七条「仕事のマインドセット」约束工作方式，强调不遗漏、正确率目标等。

### 3. 抓住核心
**为了什么**：避免不理解问题就机械执行。  
**做了什么／怎么做**：「方法論の大原則：コアを見抜く」要求先把握目的与本质，再选择方法、验证和形式。

### 4. 专家与 PDCA
**为了什么**：让调查分析更可靠、更有可重复性。  
**做了什么／怎么做**：「作業の上位原則：専門家基準とPDCA (CORE-001)」规定专业视角、P/D/C/A 和第一性原理的思考方式。

### 5. 状态与异常
**为了什么**：防止把“写了”“加载了”“实际运行成功”混为一谈。  
**做了什么／怎么做**：「状態の言い方は B001 に統一する」和「問題を見つけたときの扱い」规定执行状态、遇到异常时的自查和审批边界。

### 6. 正本与同步
**为了什么**：避免资料版本不一致、误把派生副本当正本。  
**做了什么／怎么做**：「資料の修正は『本書から、順に』」要求先改正本、再按确认过的流程反映到派生成果或外部系统。

### 7. 修改留档
**为了什么**：保证文件变化可追溯和必要时可恢复。  
**做了什么／怎么做**：「AIによる変更のバージョン管理」定义 before/after 备份、CHANGELOG、README，以及 hooks 脚本。

### 8. 调查标准
**为了什么**：减少大规模调查中的遗漏、片面解释和无法复核。  
**做了什么／怎么做**：「調査ルール」包含调查理念、MECE 五原则、证据记录及代码与设计书双向调查。

### 9. 知识检索
**为了什么**：重用已有知识、避免重复调查。  
**做了什么／怎么做**：「調査開始前 必須チェック」强制读取 `knowledge_store/INDEX.md` 并 grep 查询；**根据用户最新要求，此无条件强制规则需要删除，改 DEV 按需可用、RUN 禁止访问**。

### 10. 共通操作
**为了什么**：用户要求“教我”“给我看”时获得可验证来源。  
**做了什么／怎么做**：「共通操作ルール」要求给完整路径，并在文件存在时先实际读取，不要只给概要。

### 11. 回答与输出
**为了什么**：确保用户第一眼知道目的、处理方式、结果和文件位置。  
**做了什么／怎么做**：「回答・出力の基本原則 (B001)」规定概要一句、5W1H、具体说明、输出格式、文件交付信息、完工三阶段和发送检查清单。**现阶段最大冲突在此部分**。

### 12. 异常归档
**为了什么**：让同类问题不在后续任务或会话中重复发生。  
**做了什么／怎么做**：「イレギュラーケースの対応制約」要求汇报状况、原因、对策并归档到知识库；与用户最新的 RUN 禁访知识库规则冲突。

### 13. 目录分工
**为了什么**：防止输入、临时、结果和代码资料混杂。  
**做了什么／怎么做**：「ディレクトリ利用ルール」指定 input/output/work/temp/bin/data 等；**现行统一 output 需要改为根级成果归根级、项目成果归自身的 document/output、temp 共用且任务隔离**。

### 14. 禁止操作
**为了什么**：防止误运行生产脚本、写库、改动设计原件。  
**做了什么／怎么做**：「操作上の制約」禁止未经批准执行 shell/COBOL 批处理、数据库更新和修改受保护文件，包含权限前置检查。

### 15. 项目与外部系统
**为了什么**：让 Claude 知道代码资料具体在哪、外部系统如何处理异常。  
**做了什么／怎么做**：「リポジトリ構成」「外部システムアクセス」列出 `/data/` 的代码分区、Box/Jira/Confluence 及 Box 401 等异常处理要求。

## 三、为什么旧版回答容易过长：准确定位

以下为截图可见的规则思想及其冲突：

1. **B001，原則1：固定の回答順序**：先概要、后 5W1H，再进入「具体的な内容と説明」。第三段写的是概要与 5W1H 之后不能省略必要事项，任务详情／进度报告／交接时尤其必须。
2. **B001，原則2：回答内で完結させる**：要求代码、设计书、多对象对应等内容在回答中完整给出（仅给路径被视作不够），强化了屏幕上展开的倾向。
3. **B001，原則3：出力形式を情報量で選ぶ**：内容多时选择 MD/HTML/Excel，但没有明确说“只在文件里、聊天不能展开正文”。
4. **B001，原則4／送信前チェックリスト**：新增/变更文件要完整路径、变更理由、前后差异等；这是质量要求，但如果不限定展现层级，会不断叠加文本。
5. **进度与交接模板**：任务目标、资料基准、进度、剩余事项、下一步等全部写出来十分长。应当写入报告，聊天中保留最重要的一句话。

**结论**：应修改 B001 的输出分层与显示边界，而非删除现有信息完整性要求。原始细节仍保存，不应丢掉，只是不在聊天正文堆叠。

## 四、建议替换的输出协议（日本語・CLAUDE.md 用草案）

```md
# B001：3段階応答ルール（最優先）

## 第1段階：通常回答（デフォルト）
- 回答冒頭に、「目的・実施内容・方法・結論」を理解できる極めて短い概要で示す。
- 必要最小限の 5W1H を簡潔に示し、成果物のファイルパス／リンクと完了状態を添える。
- 詳細な分析、証拠一覧、長い手順、差分、ログ、長い引継ぎ文をチャット本文に展開しない。
- 原則として短い一画面で回答を止める。未実行を実行済みと報告しない。
- ただし、重要な危険・制限・未確認点は短く明示する。

## 第2段階：「もう少し詳しく」「展開して」
- ユーザーが望んだ場合のみ、チャット本文に 10～20 行以内で要点を展開する。
- 結論→理由→実施内容→方法→結果→未確認→次の一手、の順にまとめる。
- 詳細分析や全証拠はチャットに貼らない。

## 第3段階：詳細 Markdown 報告ファイル
- 調査・分析・設計・開発など詳細の裏付けが必要な成果タスクでは、
  実作業の中で完全な Markdown レポートを成果物として保存する。
- 第1段階の回答時点で既に作成したレポートのリンクを提示する。
  同じ情報をチャットで再掲しない。
- ファイルには目的、5W1H、調査対象と基準、事実と証拠、方法、
  解析、未確認・制限、結論、差分、必要な引継ぎ情報を記録する。
- 一時的な雑談・単純な一問一答で必要がない場合は、
  大げさなレポートの自動作成は不要。
- ファイルを作成できない場合は、できないことを正直に短く記す。

## 旧 B001 との整合
- 従来の「概要・5W1H の後に必要事項を省略せず回答する」は、
  「必要事項は詳細レポートファイルに保存し、チャットでは概要のみ」と読み替える。
- 「回答内で完結させる」は、チャット全文展開の意味には適用せず、
  回答＋参照可能な成果物の組み合わせで完結させる。
- タスク詳細・進捗報告・引継ぎの全項目は詳細レポートに記録し、
  第1段階の画面には必要最小限だけ残す。
- この表示制約は、他の章の詳細記載指示より優先する。
```

## 五、三段階の具体例

**第1段階（通常の画面）**  
「調査結果：回答が長い主因は B001 の“5W1H 後も詳細説明必須”の指定。表示規則を三段階に分け、詳細は MD 保存に変更する案を作成しました。調査対象はユーザー提供の現行 CLAUDE.md スクリーンショット。詳細：[報告リンク]」

**第2段階（ユーザーが『展開』と言った時）**  
10～20 行で、衝突箇所 3 点、原因、改訂方針、影響、残る確認事項を要約する。

**第3段階（リンクを開いた時）**  
本書のような完全な説明、対応表、具体的な修正案、根拠、除外事項を見る。
