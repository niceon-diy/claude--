# QA-001：既存类似案件优先参照规则

## 中文版

### 目的与基本方针
开发、设计、调查、测试中发生不明确事项时，不得未经调查就向用户提出QA。原则上优先参照过去同类案件的**实际改修内容**，保持既存系统的设计思想、实现方式与改修惯例一致。既存案例是优先依据，但不能代替适用性验证或必要的业务授权。

### 强制处理流程
1. **明确问题**：记录不明确的具体事项、涉及对象、待判断内容及影响。
2. **检索过去类似案件**：优先调查过去项目追加对应一览、设计书、实际修改的程序/DB/IF/画面/测试资料、改修履历、调查报告及ノウハウ。记录检索范围与未找到的内容。
3. **核对实际改修**：不得仅凭说明文字判断。尽可能核对过去实际改了什么、为什么改、如何改、关联对象及证据位置（文件路径、章节、行号、版本/时间戳等）。
4. **判断适用性**：比较当前案件与历史案件的业务条件、对象、系统版本和约束。说明可复用部分、差异、限制与潜在影响；禁止机械照搬。
5. **确定方针并执行**：有充分证据且在授权范围内时，优先采用既存实绩的改修方式，并记录依据、处理方法、结果与验证。无须为普通不明确事项中断工作。
6. **必要时才QA**：若充分检索后仍无可参照案例、历史案例冲突无法判定、当前案件关键差异导致不适用，或涉及新的业务规则/授权决定，则向用户提出QA。QA必须包含问题、已调查范围、案例与证据、无法判断的原因、候选方案及建议。关键事项未确认前不得擅自变更业务逻辑。

### 禁止事项
- 未调查既存案例就向用户转交判断责任。
- 未核对实际改修便仅凭设计说明或AI推测确定方案。
- 将表面相似但条件不同的案例作为确定依据。
- 因首次检索失败就认定无案例；应核查检索范围。
- 将未经验证的推断描述为已确认事实。

### 输出要求
简要说明：**为了什么目的 → 依据哪个过去案件的什么证据 → 如何比较及处理 → 产出什么、在哪里 → 如何验证 → 尚存什么问题/是否需要QA**。明确区分事实、推断与建议。

**执行顺序：问题明确 → 既存类似案件调查 → 实际改修核对 → 适用性判断 → 解决方针 → 必要时QA。**

## 日本語版

### 目的・基本方針
開発・設計・調査・テストで不明点が発生した場合、十分な調査を行わずにユーザーへQAを提出してはならない。原則として、過去の同種・類似案件における**実際の改修実績**を優先的な判断根拠とし、既存システムの設計思想・実装方式・改修慣例との整合性を確保する。ただし、類似実績の存在だけで適用可能と判断せず、適用条件と必要な承認を確認する。

### 必須処理手順
1. **不明点の明確化**：対象、判断すべき事項、影響範囲を特定する。
2. **過去の類似案件の調査**：過去のプロジェクト追加対応一覧、設計書、実際に改修されたプログラム・DB・IF・画面・テスト資料、改修履歴、調査報告書、ノウハウを優先的に確認する。検索範囲と未確認事項を記録する。
3. **実改修内容の確認**：説明文だけで判断せず、何を、なぜ、どのように変更したかを実物で照合する。ファイルパス、章・行番号、版数、タイムスタンプ等の根拠を残す。
4. **適用可否の判断**：現案件との業務条件、対象、システム版数、制約の差異を比較し、流用可能範囲・相違点・制限・影響を明示する。安易なコピーは禁止する。
5. **対応方針の決定・実行**：十分な根拠があり権限の範囲内であれば、既存の改修実績に沿った方式を優先して採用し、根拠・処理内容・結果・検証を記録する。通常の不明点だけを理由に作業を停止しない。
6. **必要な場合のみQAを提出**：十分に調査しても参照事例がない、事例間に解消不能な矛盾がある、現案件の重要な差異により適用できない、または新たな業務判断・承認が必要な場合に限る。QAには不明点、調査範囲、参照事例と根拠、判断不能な理由、候補案と推奨案を含める。重要事項が未確定のまま業務ロジックを変更してはならない。

### 禁止事項
- 既存事例を調べずに判断をユーザーへ丸投げすること。
- 実改修を確認せず、設計書の記述やAIの推測のみで確定すること。
- 表面的に似ているだけの事例を根拠として流用すること。
- 一度の検索失敗だけで参照事例がないと判断すること。
- 未検証の推測を確認済みの事実として扱うこと。

### 結果説明
**目的 → 参照した過去案件・根拠 → 比較・処理方法 → 成果物と保存先 → 検証方法 → 残課題・QA要否** の順で簡潔に説明し、確認済み事実・推測・提案を区別する。

**実行順序：不明点の明確化 → 類似案件の調査 → 実改修の確認 → 適用可否判断 → 対応方針決定 → 必要時のみQA。**
