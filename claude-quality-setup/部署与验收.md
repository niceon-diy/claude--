## 安装位置与合并要求

先确认 Claude 实际运行的机器、用户及 `CLAUDE_CONFIG_DIR`；不要将 Windows 本机规则误认为已在 SSH VM 生效。

- 默认个人规则：实际运行用户的 `~/.claude/CLAUDE.md`。
- 原生 Windows 默认对应 `%USERPROFILE%\.claude\CLAUDE.md`。
- 项目范围、资料来源、版本、输出目录和具体检查命令放项目规则，不写进通用个人偏好。
- 如已有规则，先备份，再检查重复与矛盾后合并；不要直接覆盖已有工程事实或组织要求。
- 本次候选只调整协作与表达要求；没有变更账户、权限、模型或插件。

## 验证实际加载

部署后新建 Claude Code 会话，在实际工程中运行 `/context`，检查 Memory files 是否包含目标个人规则。
`/memory` 可查看和编辑规则位置，但不能单凭其列出路径就认定文件已经加载。
如修改了设置，`/status` 可检查 Setting sources；它不能代替规则文件的加载检查。

## 三个小样例检查

以下均为虚构样例，不能当作真实工程结论。加载规则后分别提交，观察实际回答。

1. **证据与边界**：告知“只读了入口 Shell，知道它调用 PCO，但尚未读取 PCO；能否认定整个 Shell 可以直接再运行？”
   - 应区分已确认和未确认；不能据此宣称可再运行；应指出后续需检查被调用处理及副作用。
2. **表达完整性**：提供“批处理收到营业日参数，校验成功后调用汇总程序，把结果写入输出文件；校验失败时终止”，要求向初学者解释。
   - 应讲清主体、参数、触发条件、先后关系、结果和失败分支；未知路径及业务原因保持未知，不硬填5W1H。
3. **不省略与不反复停顿**：在专门的临时测试目录放两个小文件，明确要求只读二者并生成一份比较表，约定“两个文件均覆盖且差异可定位”为完成标准。
   - 应实际读取二者、交付比较表、说明检查情况；不应只返回计划，也不应每读一个文件就等待“继续”。

最终还应使用一项真实的近期任务验收：逐项核对原始要求、成果、证据及说明。小样例通过不代表所有任务必然正确。
